## 1. Summary

- **Magic Context is the only one of the five that manages the context window itself** and the only one designed around a provider prompt cache. Its memory layer is comparatively simple: short project facts, exact-hash dedupe, linear FTS/vector score blending, no reranker, no entity model. Its strongest memory feature, verifying memories against the code files that back them, has no equivalent in any of the four.
- **Our promotion gate is the weakest of the five.** A historian fact becomes an active project memory in the publish transaction if its category is promotable and its normalised hash is new (`mc:src/features/magic-context/memory/promotion.ts:57-91`). Every other system either makes writes explicit (Engram), stages extracted facts and consolidates them into a separate derived layer with an LLM create/update/delete decision (Hindsight, Honcho), or resolves each extraction to a schema-defined identity and patches the existing record (OpenViking).
- **Hindsight has the most complete retrieval pipeline:** four parallel arms (vector, BM25, entity/semantic/causal link expansion, temporal), reciprocal-rank fusion, then a local cross-encoder reranker with small multiplicative recency and evidence boosts. Our own search study found cross-source score calibration is `ctx_search`'s dominant loss (`mc:docs/reports/ctx-search-empirical-study.md:12-22`); a cross-encoder over the fused pool is the standard fix for exactly that.
- **None of them keeps memories true against a code base.** Hindsight and Honcho reconcile new statements against old ones (consolidation, deduction), Engram asks the agent to judge conflicts, OpenViking patches entity cards. All of that is "newer statement wins". Only Magic Context checks claims against the files they describe.
- **Recommended adoption, highest value per cost first:** (1) stage historian facts as candidates and promote on recurrence or on a batched create/update/skip adjudication; (2) embedding near-duplicate detection at write time, feeding the same adjudication; (3) a local cross-encoder reranker for explicit `ctx_search` calls; (4) provenance from each memory to the compartments that produced it; (5) optional identity keys so config and naming facts upsert instead of accumulating; (6) a pair-verdict table so curate and verify stop re-judging the same pairs. An entity graph, per-turn auto-recall injection and LLM query rewriting are not recommended. Details and fit are in section 10.

## 2. Magic Context baseline

This section is short because `ARCHITECTURE.md`, `docs/architecture/memory-and-search.md`, `docs/architecture/dreamer.md` and `docs/architecture/historian.md` cover it; it only fixes the facts the comparison relies on.

**What is stored.** Compartments: historian summaries of a stretch of a session, each with four detail tiers, an importance score, facts and events (`mc:docs/architecture/historian.md:50-56`). Project memories: short facts in five write categories, `PROJECT_RULES`, `ARCHITECTURE`, `CONSTRAINTS`, `CONFIG_VALUES`, `NAMING` (`mc:src/features/magic-context/memory/constants.ts:9-15`). A memory row carries a normalised hash, importance, scope (`project | ecosystem | universe`), shareability, source type, seen and retrieval counts, status (`active | permanent | archived`), `expires_at`, verification status (`unverified | verified | stale | flagged`), `superseded_by_memory_id` and `merged_from` (`mc:src/features/magic-context/memory/types.ts:22-69`). Also session notes and smart notes, primers, a cross-project user profile (`src/features/magic-context/user-memory/`), a git-commit index, a raw-message FTS index, and the mural, a deterministic image of memory cues (`src/features/magic-context/mural/`). All of it lives in one SQLite database; embeddings are blobs compared in memory with cosine similarity (`mc:docs/architecture/memory-and-search.md:42-44`).

**How memories are created.** Three writers: historian fact promotion, the agent via `ctx_memory`, and the dreamer (`mc:docs/architecture/memory-and-search.md:27`). Historian promotion is on by default (`mc:src/config/schema/magic-context.ts:1534`). The code gate is: skip empty content, skip non-promotable categories, and on an exact normalised-hash match in the same project and category bump `seen_count` instead of inserting (`mc:src/features/magic-context/memory/promotion.ts:57-91`). The only other gate is in the historian prompt: skip facts that overlap `<project_memory>` and keep only high-signal ones (`mc:src/hooks/magic-context/historian-prompt.source.md:399-416`). That prompt also describes `<project_memory>` as facts "promoted to stable project memory by the dreamer (after consolidation across sessions)" (`historian-prompt.source.md:58`), which does not match the code: promotion happens at publish, before any consolidation. Two legacy categories carry a TTL (`WORKFLOW_RULES` 90 days, `KNOWN_ISSUES` 30 days); the five current categories have none (`constants.ts:67-70`). The brief for this study reports roughly 90 promoted memories per project per day, many volatile or later superseded; this report did not re-measure that, because doing so needs the live store.

**Dedupe, supersession, forgetting.** Exact hash at write time. Everything else is the dreamer's job, after the memory is already live: `curate` consolidates, tightens and archives one category per run, `verify` updates or archives claims whose backing files changed, `classify-memories` scores importance and scope (`mc:docs/architecture/dreamer.md:55-61`). Non-additive changes reach running sessions as `<memory-updates>` deltas in `m[1]` (`mc:docs/architecture/memory-and-search.md:31-36`).

**Retrieval.** Baseline memories are rendered into `m[0]` and new ones into `m[1]`; which memories survive a bounded render budget is decided by permanent-first, then importance, then the newest of `last_seen_at` and `verified_at` (`mc:src/features/magic-context/memory/memory-selection.ts:21-42`). `ctx_search` queries memories, raw messages, git commits, compartment chunks, primers and notes. Memory scores are `0.7 × semantic + 0.3 × FTS`, a 0.8 penalty when only one lane hit, and per-source boosts of 1.2 to 1.3 (`mc:src/features/magic-context/search.ts:39-54`, `:791-859`); message probes are RRF-fused with k = 60 (`search.ts:1151-1344`). There is no reranker and no LLM in the search path. Auto-search appends a short hint to the new user message rather than injecting results, so the cached prefix is untouched (`mc:docs/architecture/memory-and-search.md:63`).

**Verification against ground truth.** `map-memories` records which repository files back each memory (`mc:src/features/magic-context/memory/storage-memory-verifications.ts:40-62`); `verify` re-checks only memories whose backing files have commits newer than their last verification, falling back to checking everything when git is unavailable (`mc:src/features/magic-context/dreamer/verify-gate.ts:174-207`); host-side safety checks refuse to rewrite process rules or to cut more than half a memory's text (`mc:docs/architecture/dreamer.md:56`). The cost is real: verify, verify-broad and map-memories were 69.4% of 1.48 billion recorded dreamer and historian tokens over 14 days (`mc:docs/reports/dreamer-token-usage.md:7`).

**Scoping.** Memories are per project, identified by the repository's root commit (`mc:docs/architecture/memory-and-search.md:25`); workspaces share selected categories read-only across projects (`:40`); the user profile is cross-project.

## 3. Engram

Engram is a Go binary with a local SQLite store, an MCP server, an HTTP server, a TUI and optional cloud sync. It is agent-driven: the agent decides what to save.

**Stores.** `observations` rows with `type`, `title`, `content`, `tool_name`, `project`, `scope`, `topic_key`, `normalized_hash`, `revision_count`, `duplicate_count`, `last_seen_at`, `pinned`, soft-delete `deleted_at` (`engram:internal/store/store.go:1195-1215`); a later migration adds `review_after` (`store.go:1448`). Types are free text suggested by the tool schema: decision, architecture, bugfix, pattern, config, discovery, learning, manual (`engram:internal/mcp/mcp.go:519-521`). Also `sessions` with an agent-written `summary` (`store.go:1183-1192`), raw `user_prompts` (`store.go:1234-1242`), and `memory_relations`, a pair table with verbs, confidence, evidence, the actor and model that judged it, and its own supersession chain (`store.go:1465-1483`). The content format is episodic-plus-semantic: the save tool asks for **What / Why / Where / Learned** (`mcp.go:493-508`). There are no entities and no vectors: search is SQLite FTS5 with a trigram tokenizer over title, content, tool, type, project and topic key (`store.go:1222-1232`).

**Creation and gating.** Explicit writes through `mem_save` (`mcp.go:477-546`), plus `mem_capture_passive`, which splits a `## Key Learnings:` section of agent output into one observation per bullet (`mcp.go:933-961`), and `mem_session_summary`. The only quality gate is instruction: the server tells the agent to "call mem_save immediately after ANY decision, bug fix, discovery, or convention" (`mcp.go:373-375`), and the OpenCode plugin appends a save nudge to the system prompt when the project has had no save for a while (`engram:plugin/opencode/engram.ts:741-800`). `<private>` tags are stripped before anything is stored, and an empty title or content is rejected (`store.go:3470-3483`).

**Dedupe, supersession, decay.** Three mechanisms, all deterministic except the last:
1. **Topic-key upsert.** A save with a `topic_key` overwrites the newest live observation with the same key, project and scope and increments `revision_count` (`store.go:3501-3543`); `mem_suggest_topic_key` proposes a stable key such as `architecture/auth-model` (`mcp.go:611-635`).
2. **Duplicate window.** Without a topic key, a save with the same normalised hash, project, scope, type and title inside 15 minutes only bumps `duplicate_count` (`store.go:3550-3582`, default window at `store.go:789`).
3. **Conflict surfacing.** After each save, `FindCandidates` runs an FTS query from the new title, keeps up to three candidates under a BM25 rank bound, and inserts a `pending` relation row for each (`engram:internal/store/relations.go:358-493`). The save response sets `judgment_required`, and the agent is told to call `mem_judge` once per candidate with one of `related | compatible | scoped | conflicts_with | supersedes | not_conflict`, and to ask the user when confidence is below 0.7 or when a `supersedes`/`conflicts_with` verdict touches an architecture, policy or decision (`mcp.go:381-388`, vocabulary at `relations.go:32-59`). A `not_conflict` verdict is persisted so the pair is never re-evaluated (`mcp.go:1089-1110`). An offline `engram conflicts scan --semantic` shells out to `claude` or `opencode` to judge pairs (`engram:internal/llm/runner.go:1-8`). Judged relations are printed with search results as `supersedes: #id` / `superseded_by: #id` (`mcp.go:1341-1380`); superseded rows are annotated, not hidden.

Decay is a review date, not deletion: decisions get `review_after` six months out, policies twelve, preferences three (`store.go:360-384`, set on insert at `store.go:3602-3613`); `mem_review` lists overdue rows and resets them (`mcp.go:590-607`). Nothing expires automatically.

**Retrieval.** A query containing `/` is first tried as an exact topic key (`store.go:4683-4737`). Otherwise FTS5 BM25 with column weights title 5, content 1, topic key 3, multiplied by a composite of +10% pinned, up to +6% recency (half-score at 30 days) and up to +4% for revision and duplicate counts (`store.go:366-375`, `:4964-5008`); terms under three characters fall back to an escaped `LIKE` scan (`store.go:4741-4742`, `:5011-5021`). No vectors, no reranker, no query rewriting beyond FTS sanitising. Results reach the model two ways: `mem_context` renders recent sessions, pinned and recent observations and recent prompts into a markdown block with a 16 KB default budget (`store.go:5259-5320`, `mcp.go:724-750`), which the Claude Code, Codex, Pi and OpenCode plugins fetch at session start and after compaction (`engram:plugin/claude-code/hooks/hooks.json`, `plugin/opencode/engram.ts:826-841`); and `mem_search` / `mem_timeline` / `mem_get_observation` as tools, a search-then-expand disclosure pattern.

**Verification.** None against code or files. Truth is maintained only by the agent's conflict verdicts and the review dates.

**Scoping.** Per project (normalised name, detected from the repository), with `scope` of `project | personal | global` (`mcp.go:525-527`); cross-project search is an explicit flag (`mcp.go:454-456`). Sharing is via cloud sync with per-project enrollment, sync mutations and tombstones (`store.go:1284-1330`, `internal/cloud/`).

**Integration, cost, locality.** MCP server with 23 tools, several deferred-loaded to save tool-definition tokens (`mcp.go:437-1110`); plugins for Claude Code, Codex, OpenCode, Pi and Obsidian (`engram:plugin/`). Every operation is a local SQLite call with no model cost; the only LLM work is the agent's own judging and the optional semantic scan. Fully local-first; cloud is optional.

**Evaluation.** No published benchmark. There are Go benchmarks for the MCP judge path (`engram:internal/mcp/judge_bench_test.go:214`) but no retrieval-quality evaluation.

## 4. Hindsight

Hindsight is a Python service (FastAPI, PostgreSQL with pgvector, optionally an embedded Postgres through `pg0`, `hindsight:pg0.py:20`) with a large integrations catalogue. It is extraction-driven: raw conversation goes in, an LLM pipeline decides what is kept.

**Stores.** A bank-scoped `memory_units` table holds sentence-level facts with an embedding (HNSW cosine index), `fact_type` of `world | experience | observation`, and three time fields: `occurred_start`, `occurred_end` (when it happened) and `mentioned_at` (when it was said) (`hindsight:models.py:120-192`). `entities` carry a canonical name, first and last seen, and a mention count; `unit_entities` links facts to entities; `entity_cooccurrences` caches pair counts (`models.py:195-278`). `memory_links` is a typed, weighted edge table: `temporal`, `semantic`, `entity`, and causal `causes | caused_by | enables | prevents` (`models.py:281-323`). `documents` keep the source text (`models.py:99-117`). Observations are the consolidated layer and carry `proof_count`, `source_memory_ids` and a JSONB change `history` (`hindsight:engine/consolidation/consolidator.py:1-16`). Mental models are user-defined questions whose answers reflect regenerates (`consolidator.py:13-15`; MCP tools at `hindsight:mcp_tools.py:1754-2400`). Banks carry a disposition (skepticism, literalism, empathy) and a background text used by reflect (`models.py:326-339`).

**Creation and gating (retain).** Text is chunked (`engine/retain/fact_extraction.py:761-874`) and each chunk goes through one LLM extraction call that returns facts with `what / when / where / who / why`, a `fact_kind` (event or conversation), a `fact_type` (world or assistant), entities and optional causal links to earlier facts (`fact_extraction.py:255-294`). The default "concise" prompt says "Be SELECTIVE - only extract facts worth remembering long-term", lists what to keep and what never to extract (greetings, filler, process chatter, repeats), forces relative dates to absolute ones and resolves coreference (`fact_extraction.py:1052-1135`; default mode at `config.py:1644`). Banks can add a retain mission that steers extraction (`fact_extraction.py:1764`). Entity resolution is not an LLM call: names are matched by trigram similarity plus co-occurrence and recency, with an intra-batch merge threshold of 0.5 and a minimum of 0.3 against existing entities (`engine/entity_resolver.py:498-535`).

**Dedupe, merge, supersession.** Raw facts are not deduplicated at insert. The dedupe and truth-maintenance work happens in **consolidation**, a background job after each retain (`consolidator.py:1-7`, reconcile loop in `engine/maintenance.py:1-20`). For each batch of new facts it recalls nearby existing observations and asks an LLM for `creates / updates / deletes` under explicit rules: prefer UPDATE over CREATE, one observation per facet, match by entity not topic, rewrite state changes concisely ("owned a Civic; sold it on March 15"), cascade a state change to every affected observation, never do arithmetic, delete only exact restatements, and omit purely ephemeral facts (`engine/consolidation/prompts.py:37-55`, `:101-106`). Two guards follow the LLM: a CREATE whose text exactly matches a shown observation or an UPDATE in the same response is dropped (`consolidator.py:127-156`), and, when enabled (default threshold 0.97 cosine, `config.py:1750`), each new or updated observation is compared with its five nearest neighbours and a second, focused LLM call decides `merge` (writing one text that keeps every detail) or `keep` if any number, entity, negation or condition differs (`consolidator.py:159-214`). Provenance is enforced: an observation is only written from source facts that still exist, under a `FOR SHARE` lock, and a batch is discarded if any source fact was edited while the LLM was deciding (`consolidator.py:732-792`). Time ranges merge by widening, never by replacement (`consolidator.py:230-273`). There is no TTL or forgetting of memories; the maintenance loop only expires audit and LLM-request logs (`engine/maintenance.py:1-8`).

**Retrieval (recall).** One store call runs four arms for each fact type: vector, BM25, graph, and temporal (`engine/search/retrieval.py:795-904`). Temporal constraints come from `dateparser` over the query, not from an LLM (`engine/query_analyzer.py:14-50`, `retrieval.py:854-872`). The graph arm picks up to 20 semantic seeds and expands through shared entities (capped per entity), precomputed semantic kNN links and causal links, the last boosted by +1 (`engine/search/link_expansion_retrieval.py:1-26`, `:47`). Arms are fused with RRF, k = 60 (`engine/search/fusion.py:29-110`), then reranked by a cross-encoder, by default the local `cross-encoder/ms-marco-MiniLM-L-6-v2` (`config.py:1273-1283`, `engine/search/reranking.py:307-313`). The final score is the normalised cross-encoder score times bounded boosts: ±10% recency, ±10% temporal proximity, ±5% for an observation's `proof_count`; the RRF score is dropped after reranking (`reranking.py:174-305`). Deployments without a cross-encoder use a passthrough that seeds the base score from the RRF rank so the boosts do not become the only signal (`reranking.py:227-261`, `engine/cross_encoder.py:1255`). Recall returns up to a token budget, 4,096 by default, with a graph-traversal budget of 100 / 300 / 600 units for low / mid / high (`engine/memory_engine.py:8243-8294`). Reflect is a separate agentic loop over tools such as `search_mental_models`, `search_observations`, `recall` and `expand` (`engine/reflect/tools.py:112-532`).

Results reach the model as injected context: the Claude Code plugin recalls on every `UserPromptSubmit` and returns it as `additionalContext` (`hindsight:hindsight-integrations/claude-code/scripts/recall.py:15`, `:275`) and retains on `Stop`; the OpenCode plugin recalls once per session and prepends it to `system[0]` (`hindsight-integrations/opencode/src/hooks.ts:5`, `:296-341`). MCP tools (`retain`, `recall`, `reflect`, mental models, knowledge pages) are also exposed (`mcp_tools.py:991-2918`).

**Verification.** None against an external source. Truth maintenance is consolidation's "newest statement wins, keep history" rule plus provenance liveness.

**Scoping.** Everything is per bank; tags and tag groups filter recall and consolidation scopes (`retrieval.py:804-806`; scope rules at `consolidator.py:577-730`). Integrations map a bank to an agent, a project or a session (`hindsight-integrations/claude-code/README.md`, "Dynamic bank IDs").

**Integration, cost, locality.** HTTP API, MCP, Python and TypeScript clients, and about 55 integration directories including Claude Code, Codex, OpenCode, Cursor, Cline, Aider, Roo Code, Zed and many agent frameworks (`hindsight:hindsight-integrations/`). Per operation: retain costs one LLM call per chunk, one consolidation call per batch, and one extra call per near-duplicate observation; recall costs one embedding plus a local cross-encoder pass and no LLM call; reflect is an LLM tool loop. It can run locally with the embedded Postgres, local `BAAI/bge-small-en-v1.5` embeddings (`config.py:1212`) and a local reranker, but extraction still needs an LLM; the Claude Code plugin can borrow Claude Code's own model (`claude-code/README.md`, option C).

**Evaluation.** The README claims state-of-the-art LongMemEval results as of January 2026, says an independent group at Virginia Tech and The Washington Post reproduced them, and notes other vendors' scores are self-reported (`hindsight:README.md:44-50`). The evaluation code has moved to a separate repository, AMB, which owns datasets, answer model, judge and scoring (`hindsight:hindsight-dev/benchmarks/README.md`). Credibility is better than most vendor claims (an external reproduction and a separate harness), but it is still an LLM-judged conversational benchmark run by the vendor's own harness; it says nothing about coding-agent memory.

## 5. OpenViking

OpenViking (ByteDance Volcano Engine) is a "context database": a virtual filesystem under `viking://` that holds resources, skills and memories, with generated summaries per directory. Python server with a C++ vector engine and Rust crates.

**Stores.** Memories are markdown files whose type, directory, filename and fields are defined by YAML schemas: `profile`, `preferences`, `entities`, `events`, `cases`, `experiences`, `trajectories`, `skills`, `tools`, `identity`, `soul` (`ov:openviking/prompts/templates/memory/`; loader at `ov:openviking/session/memory/memory_type_registry.py`). Every directory has an L0 abstract and L1 overview generated from its contents, with L2 being the full file (`ov:README.md:45-60`). An entity is a card at `entities/<category>/<name>.md` whose identity is "the referenced real-world object, not its category or semantic similarity" (`ov:openviking/prompts/templates/memory/entities.yaml:1-11`). `experiences` are agent-only procedural memories in a fixed Situation / approach / rationale shape that is later injected into agent prompts (`experiences.yaml:1-30`); `cases` are task-plus-rubric records for a training pipeline (`cases.yaml:1-40`). Storage is a local vector index by default (`ov:examples/ov.conf.example:62-66`) with other backends in `openviking/storage/vectordb_adapters/`; the embedder interface supports dense, sparse or hybrid vectors (`ov:openviking/models/embedder/base.py:246-262`).

**Creation and gating.** Sessions are committed in two phases: phase 1 archives the raw messages and enqueues work; phase 2 extracts memories from a persistent queue (`ov:openviking/session/session.py:1236-1281`). Commits happen on an auto-commit token threshold from the agent plugins (`ov:examples/claude-code-memory-plugin/scripts/auto-capture.mjs:12`). Extraction is a ReAct loop in which the model can `read`, `search` and `ls` existing memory files before emitting operations (`ov:openviking/session/memory/extract_loop.py:1-5`, tools at `openviking/session/memory/tools.py:118-329`). Gating is per schema: `cases` are extracted "ONLY when the conversation contains a concrete user task plus enough ... evidence" (`cases.yaml:8-12`); preferences must be topic-specific (`preferences.yaml:2-7`). A phase-2 "working memory" document, a seven-section structured summary of the session, is also written per archive (`ov:openviking/session/working_memory.py:1-18`), which is the closest thing to our historian among the four.

**Dedupe, merge, supersession.** Identity comes from the filename template: two extractions that resolve to the same entity name write the same file, so dedupe is by schema identity rather than by similarity. Each field declares a merge operation: `patch` (search/replace blocks), `replace`, `sum`, `immutable` (`ov:openviking/session/memory/merge_op/base.py:121-126`; entity content is `patch`, `entities.yaml:66`; an experience name is `immutable`, `experiences.yaml:21`). Before an upsert, the loop re-reads any existing file the model has not read in this run, so an overwrite is never blind (`extract_loop.py:1286-1304`). A shared policy says similarity only nominates candidates; merge only on same identity; before deleting a source, place every atomic fact in a surviving memory; split mixed memories; never drop a fact to meet a length target (`ov:openviking/session/memory/merge_policy.py:4-20`). "Hotness" (`sigmoid(log1p(access_count)) × 2^(−age/7 days)`) classifies memories as hot, warm or cold for a health statistics API; it does not delete anything (`ov:openviking/retrieve/memory_lifecycle.py:1-30`).

**Retrieval.** At this commit the retriever is one global vector search with an optional reranker: it fetches twice the requested limit, reranks, and applies the score threshold only after reranking because "a low vector score can still rerank highly" (`ov:openviking/retrieve/hierarchical_retriever.py:1-5`, `:50`, `:87-230`). Directory scoping is a filter resolved before vector ranking (README and paper reference at `ov:README.md:59`, `:290-295`). `search`, as opposed to `find`, first runs an LLM intent analysis over the session to produce a query plan, with fine-tuned small planner models available (`ov:openviking/retrieve/intent_analyzer.py:1-25`). The Claude Code plugin injects recalled memories on every `UserPromptSubmit` via `additionalContext` (`ov:examples/claude-code-memory-plugin/scripts/auto-recall.mjs:37`); agents can also browse with `ls`, `tree`, `read` and `grep`.

**Verification.** None against ground truth. Provenance is strong, though: memories trace back to archive diffs and session messages, and a read-only troubleshooting skill walks that chain (`ov:agent-plugins/README.md`, `ov-memory-troubleshoot`).

**Scoping.** User space, agent space, account and session namespaces (`viking://user/{{ user_space }}/memories/...` in every schema); multi-tenancy with accounts and API keys (`ov:openviking/server/api_keys/`).

**Integration, cost, locality.** HTTP server, CLI, MCP endpoint (`ov:openviking/server/mcp_endpoint.py`), an Agent Plugins 1.0 package, and plugins for Claude Code, Codex, OpenCode, OpenClaw, Hermes, Pi and others (`ov:examples/`). Costs: each commit runs one or more LLM extraction turns plus summary generation for touched directories; each `search` runs an LLM planner call; `find` is embedding plus optional rerank. The sample configuration points at hosted Doubao embedding, VLM and VikingDB rerank endpoints (`ov.conf.example:125-216`); local operation is possible with other providers but is not the default path.

**Evaluation.** README reports LoCoMo accuracy of 80–83% for three agent integrations with OpenViking versus 24–57% with their native memory, plus tau2-bench gains and 34–91% fewer input tokens (`ov:README.md:110-119`), with scripts in `ov:benchmark/locomo/` including mem0 and supermemory comparisons. It is vendor-run and LLM-judged; the "native memory" baselines of general agents are weak comparators for a dedicated memory system.

## 6. Honcho

Honcho (Plastic Labs) is a user-modelling service: FastAPI, PostgreSQL with pgvector, a background deriver and a dreamer. It models peers (users or agents) from each other's point of view.

**Stores.** Workspaces, peers, sessions and messages (`honcho:src/models.py:103-269`). Memory documents belong to a directed `(observer, observed)` collection and carry a `level` of `explicit | deductive | inductive | contradiction`, an embedding, an optional session and a soft-delete time (`src/models.py:390-414`); `DocumentSource` rows link derived documents to their premises (`src/models.py:546`). Peer cards (short biographical lists) live in peer metadata and session summaries in session metadata (`src/crud/peer_card.py:22-52`, `src/utils/summarizer.py:40-58`).

**Creation and gating.** Every message enqueues deriver work; batches of about 1,024 input tokens, or older than 30 minutes, are processed together (`src/config.py:950-970`). The deriver prompt extracts only **explicit** atomic facts about the target peer from that peer's own messages, uses other peers' messages only as context, and forbids deriving facts about the user from agent turns or tool output (`src/deriver/prompts.py:80-110`). Deductive and inductive knowledge is produced later by the dreamer.

**Dedupe, supersession, contradiction.** At write time, exact normalised-content dedupe never crosses levels, and for explicit documents never crosses sessions (`src/crud/document.py:479-510`); semantic dedupe rejects a new document whose nearest neighbour at the same level is within cosine distance 0.05 (`document.py:235-250`, `:1369-1467`; on by default, `src/config.py:934`). The **dreamer** runs per collection when at least 50 explicit documents have accumulated, the collection has been idle 60 minutes and at least 8 hours have passed since the last dream (`src/config.py:1357-1365`, `src/dreamer/dream_due.py`). Optional surprisal sampling picks the top 10% most geometrically unusual observations as hints (`src/dreamer/surprisal.py:1-50`, `src/config.py:1347-1351`). A deduction specialist, a tool loop capped at 12 iterations, looks for knowledge updates ("meeting moved to Thursday": create a deductive update and delete the outdated observation), logical implications and contradictions, and must cite `source_ids` that exist or its output is discarded (`src/dreamer/specialists.py:523-625`); an induction specialist generalises patterns and a card-refresh specialist maintains the peer card (`specialists.py:658-899`). There is no time-based forgetting; deletion is the dreamer's call.

**Retrieval.** Observation search is vector-only over pgvector (`src/crud/document.py:334-470`); message search is hybrid, FTS plus vector fused with RRF k = 60 (`src/utils/search.py:36-70`, `:317-449`). There is no reranker. The main read path is the dialectic endpoint (`peer.chat`), an agentic tool loop whose model and iteration cap depend on a reasoning level from `minimal` to `max` (`src/dialectic/core.py:54-173`, levels at `src/config.py:68`); it prefetches 25 observations of each type (10 at minimal) and can call `search_memory`, `search_messages`, `grep_messages`, date-range and temporal message search, and `get_reasoning_chain` (`dialectic/core.py:231-241`, `src/utils/agent_tools.py:555-874`). Applications either ask the dialectic a question as a tool or inject `get_session_context` (summary plus representation) themselves.

**Verification.** None against an external source; `source_ids` and premises give an auditable reasoning chain.

**Scoping.** Workspace, then observer/observed peer pairs, then session; "scopes" are pseudo-peers that aggregate member sessions, with backfill and removal (`src/crud/scope.py:1-15`, `:386-503`).

**Integration, cost, locality.** REST API, Python and TypeScript SDKs, an MCP server with about 40 tools including `chat`, `search`, `get_session_context` and `schedule_dream` (`honcho:mcp/src/tools/`), a Hermes plugin and a shared harness-plugin core (`honcho:hermes-plugin-honcho/`, `harness-plugin-core/`). Costs: one LLM call per deriver batch, one embedding per document, dreams of up to 12 tool iterations per specialist, and an LLM tool loop per dialectic query. Self-hostable; the managed service is the documented default (`harness-plugin-core/README.md`, `baseUrl: https://api.honcho.dev`).

**Evaluation.** README cites LongMemEval, LoCoMo and other long-conversation benchmarks and a "Pareto frontier" claim, with methodology on an external evals page (`honcho:README.md:23`, `:335-337`); harnesses for BEAM, LoCoMo, LongMemEval and OOLONG, each with a no-memory baseline, are in `honcho:tests/bench/`. Vendor-run and LLM-judged; the in-repo harnesses with baselines make it the most reproducible of the three published claims, but, like the others, it measures conversational user memory, not project knowledge.

## 8. What each does better than Magic Context

**Engram**
- *Identity-keyed upsert.* A `topic_key` makes an evolving decision one row with a revision count instead of a trail of near-duplicates (`engram:internal/store/store.go:3501-3543`). Our `CONFIG_VALUES` and `NAMING` facts are exactly this shape and accumulate instead.
- *Conflict detection at write time, with a memo of settled pairs.* Candidates are found the moment a memory is written, and a `not_conflict` verdict is stored so the same pair is never judged again (`engram:internal/store/relations.go:358-493`, `engram:internal/mcp/mcp.go:1089-1110`). Our curate re-lists whole categories and re-judges them each run; the token study found 75 of 112 `ctx_memory_list` calls in retained curate children repeated identical arguments (`mc:docs/reports/dreamer-token-usage.md:63`).
- *Explicit review dates by kind.* Decisions, policies and preferences get different re-check horizons (`store.go:360-384`). Coarse, but it expresses "this kind of fact goes stale" as data.
- *Zero model cost.* Every operation is a SQLite call.

**Hindsight**
- *A separate derived layer with provenance.* Raw extracted facts and consolidated observations are different rows; an observation knows its sources, its evidence count and its history, and is only written if its sources still exist (`hindsight:engine/consolidation/consolidator.py:1-16`, `:732-792`). Our memories are the raw extraction.
- *Consolidation rules that encode state change.* "Prefer update over create", "one facet per observation", "cascade a state change", "never compute" and "omit ephemeral facts" (`hindsight:engine/consolidation/prompts.py:37-55`, `:101-106`) directly target the failure the brief describes: volatile and superseded memories.
- *Near-duplicate adjudication with a conservative rule.* Merge only if the two assert the same fact; keep both if any number, entity, negation or condition differs (`consolidator.py:195-214`).
- *Cross-encoder reranking with bounded boosts.* Relevance comes from one model scoring query and candidate together, so candidates from different arms end up on one scale, and recency or evidence can move a result by at most ±10% / ±5% (`hindsight:engine/search/reranking.py:174-305`).
- *Temporal model.* When something happened and when it was said are separate fields and are merged by widening (`hindsight:models.py:133-140`, `consolidator.py:230-273`).

**OpenViking**
- *Schema-defined memory types with per-field merge semantics* (`ov:openviking/session/memory/merge_op/base.py:121-126`, `ov:openviking/prompts/templates/memory/entities.yaml:1-66`). A config value can be `replace`, a list of facts `patch`, a name `immutable`.
- *Read-before-write for updates.* The extractor cannot overwrite a memory it has not read in the same run (`ov:openviking/session/memory/extract_loop.py:1286-1304`).
- *An explicit fact-conservation rule for reorganisation* (`ov:openviking/session/memory/merge_policy.py:4-20`), which is sharper than our "refuse updates that drop more than half the text" heuristic.
- *Procedural memory as a first-class type.* `experiences` are reusable situation-approach-rationale instructions distilled from executed tasks (`ov:openviking/prompts/templates/memory/experiences.yaml:1-30`). Our closest analogues are primers and retrospective learnings.
- *Inspectable storage.* Memories are files an agent or a person can `ls`, `read` and edit.

**Honcho**
- *Explicit-first extraction.* The deriver only records what the target said, and inference is deferred to a dreamer that must cite premises (`honcho:src/deriver/prompts.py:80-110`, `honcho:src/dreamer/specialists.py:602-625`). That separation is the cleanest answer in this set to "the historian inferred something plausible and it became a rule".
- *Dream gating by accumulated evidence.* A dream runs only after 50 new explicit documents, an idle hour and an 8-hour gap (`honcho:src/config.py:1357-1365`), so maintenance cost tracks new information rather than the calendar.
- *Semantic dedupe on insert* at cosine distance 0.05, never across levels (`honcho:src/crud/document.py:235-250`).
- *Contradiction as a stored level,* so conflicting statements are visible rather than silently overwritten (`honcho:src/models.py:397`).

## 9. What Magic Context does better

- **It manages the window.** Tags, reduction, the historian, decayed compartment rendering and the pressure bands have no counterpart in Engram, Hindsight or Honcho. OpenViking's commit archives and working-memory document are the nearest thing (`ov:openviking/session/working_memory.py:1-18`), but they are rewritten per commit and are not cache-aware.
- **It is built around the provider prompt cache.** Memories reach the prompt through a frozen `m[0]` and a delta `m[1]`, and background writes never force a bust (`mc:ARCHITECTURE.md`, m[0]/m[1] section). Hindsight and OpenViking's Claude Code plugins inject recalled text on every user prompt; that text is different each turn, so it can never sit in a cached prefix. Hindsight's OpenCode plugin recalls once per session into `system[0]` (`hindsight:hindsight-integrations/opencode/src/hooks.ts:296-341`), which is cache-friendly but frozen at session start.
- **It checks memories against the code.** File mapping plus change-gated re-verification (`mc:src/features/magic-context/dreamer/verify-gate.ts:174-207`) is the only ground-truth mechanism in the five. The others only reconcile statements with later statements; a code change nobody talked about never reaches their memory.
- **Search spans more sources.** One `ctx_search` covers memories, raw history, compartments, git commits, primers and notes, with date bounds and suppression of what the agent can already see (`mc:docs/architecture/memory-and-search.md:57-63`). Engram searches observations only; Honcho's dialectic reaches messages and observations but not code history.
- **Nothing is lost.** `ctx_expand` recovers any original from raw history. Hindsight keeps source documents, OpenViking keeps archives, but only we can restore the exact dropped bytes into the live session.
- **No model call on the read path,** and zero added model calls on the write path for historian facts. Hindsight, OpenViking and Honcho spend LLM calls per write, and OpenViking and Honcho per read.
- **Project identity is robust.** Root-commit identity with merge tooling (`mc:docs/architecture/memory-and-search.md:25`) beats Engram's normalised directory name and the bank or workspace IDs the others leave to the integrator.

## 10. What to consider adopting

Ranked by expected value over cost. Each sketch respects four constraints: nothing may change `m[0]` bytes outside a HARD fold; background writes reach sessions only through `m[1]` deltas; memory-changing dreamer tasks share the `memory:<project>` lease; and the transform itself makes no model calls.

### 10.1 Stage historian facts; promote on recurrence or adjudication (high value, low-to-medium cost)

**Problem.** Promotion accepts any promotable, hash-new fact (`mc:src/features/magic-context/memory/promotion.ts:57-91`). Paraphrases pass the hash; volatile facts (current branch state, a version in flux, a task-local tactic) pass the category check; superseded facts pile up until curate or verify notices them, and each of those dreamer runs costs far more tokens than preventing the write would have (`mc:docs/reports/dreamer-token-usage.md:7`, `:63`).

**Borrowed from.** Honcho's explicit-first/derive-later split, Hindsight's facts-then-observations consolidation, and our own user-memory path, which already promotes an observation only after it has been seen three times (`mc:docs/architecture/dreamer.md:64`).

**Sketch.**
1. In the historian publish transaction, write `<facts>` to a `memory_candidates` table (project, category, content, normalised hash, source session, source compartment ids, first/last seen, seen count) instead of `memories`. The exact-hash path stays: a candidate that matches an existing memory still bumps that memory's `seen_count`.
2. A candidate is promoted without a model call when it recurs: seen in at least two compartments from at least two sessions, or its hash or near-duplicate (10.2) matches another candidate. Recurrence is the cheapest available signal that a fact is durable rather than task-local.
3. Everything else goes to a new single-shot manifest task, `promote-facts`, under the `memory:<project>` lease. The host renders a batch of candidates, each with its top three nearest existing memories in the same category, and the model returns one verdict per candidate: `create`, `update <id>` (with text), `skip-volatile`, `skip-duplicate`, `skip-task-local`. Use Hindsight's rules nearly verbatim: prefer update over create, one facet per memory, a state change rewrites the existing memory, never compute, omit ephemeral facts (`hindsight:engine/consolidation/prompts.py:37-55`, `:101-106`). Parsing fails closed like the other manifest tasks.
4. Creates are inserted and reach sessions through the `maxMemoryId` watermark; updates go through `memory_mutation_log` as `<memory-updates>`. Neither touches `m[0]` until the next natural HARD fold, exactly as today.
5. Candidates that are never promoted expire after a window (for example 30 days) and are deleted.
6. Fix the historian prompt's description of `<project_memory>` so it matches whichever behaviour ships (`mc:src/hooks/magic-context/historian-prompt.source.md:58`).

**Cost.** One schema migration, one table in the publish transaction, one single-shot task (tool-free, like `classify-memories`), and a gate count in `task-gates.ts`. The token cost of a batched tool-free manifest over short texts is small next to one verify batch.

**How to tell it worked.** Promotions per project per day (target: well under the current ~90); the share of memories created in a week that curate or verify archives or supersedes within 30 days; and `ctx_search` memory hit rate on the existing known-answer fixture, which should not fall.

### 10.2 Embedding near-duplicate detection at write time (high value, low cost)

**Borrowed from.** Honcho (reject at cosine distance ≤ 0.05, `honcho:src/crud/document.py:235-250`) and Hindsight (probe the five nearest at cosine ≥ 0.97 and adjudicate, `hindsight:engine/consolidation/consolidator.py:159-214`).

**Sketch.** Memories are already embedded right after they are written (`mc:src/features/magic-context/memory/promotion.ts:100-144`). Embed candidates the same way, and compare each one against the active memories and pending candidates in the same project and category using the existing in-memory cosine code. At or above a high threshold (start around 0.95 and calibrate on real data), treat it as a paraphrase: bump the matched row's `seen_count` and record the candidate as evidence. Between a lower threshold and the high one, hand the pair to the adjudication task in 10.1 with Hindsight's "merge only if nothing important differs" rule. Agent writes through `ctx_memory write` can report the near-duplicate to the agent in the tool result, and suggest `update`, instead of silently inserting it.

**Cost.** Small: the vectors and cosine code exist, and the pool per project and category is small enough for a linear scan. Thresholds depend on the embedding model and must be keyed by the model identity the registry already tracks.

### 10.3 A local cross-encoder reranker for explicit `ctx_search` calls (high value, medium cost)

**Problem.** The measured loss in `ctx_search` is cross-source score calibration: notes are rescored into a linear band that beats good chunk cosine, and conversation recall drops from 80% in the isolated lane to 50% at rank 10 overall (`mc:docs/reports/ctx-search-empirical-study.md:12-22`). Hand-tuned source boosts cannot fix scores that live on different scales.

**Borrowed from.** Hindsight: fuse candidates with RRF, rerank the pool with a cross-encoder, then apply only small multiplicative boosts (`hindsight:engine/search/reranking.py:174-305`); OpenViking: over-fetch twice the limit before reranking, and apply thresholds only after reranking (`ov:openviking/retrieve/hierarchical_retriever.py:50`, `:215`).

**Sketch.** Keep every current lane. Take the union of each lane's top candidates (for example 50 in total), replace the linear blend and per-source boosts with RRF across lanes, and rerank that pool with a small local cross-encoder over `(query, preview text)`. Transformers.js can run the same ONNX export of `ms-marco-MiniLM-L-6-v2` that Hindsight defaults to, through the runtime we already use for local embeddings (`mc:docs/architecture/memory-and-search.md:46-50`). Apply bounded boosts afterwards: recency, and for memories verification status and seen count, each worth at most ±5–10%. Run it only for explicit tool calls; auto-search hints keep the current cheap path because they run on every new user message. When the model is unavailable, fall back to RRF order, as Hindsight's passthrough does (`reranking.py:227-261`).

**Cost.** A model download of roughly 20–90 MB depending on quantisation, and some tens of milliseconds of CPU per call for about 50 short pairs (an estimate to verify on the known-answer fixture before shipping). It is read-path only, so it cannot affect the cache. The existing fixture and harness (`scripts/ctx-search-benchmark.ts`) give a direct before/after measurement.

### 10.4 Provenance from memories to compartments (medium value, low cost)

**Borrowed from.** Hindsight's `source_memory_ids` and its rule that an observation needs live sources (`consolidator.py:732-792`); Honcho's `DocumentSource` premise links (`honcho:src/models.py:546`); OpenViking's archive-diff tracing.

**Sketch.** Store the source compartment ids (and message ordinal range) for each promoted memory, and for each candidate that later reinforces it. Three uses. Verify and curate can read the originating conversation through `ctx_expand` instead of guessing why a memory exists. When `/ctx-recomp` rebuilds compartments, memories whose only evidence came from the rebuilt range can be queued for re-verification. Evidence count (distinct sessions) becomes a ranking and render-selection signal alongside importance and verification (`mc:src/features/magic-context/memory/memory-selection.ts:21-42`).

**Cost.** A join table written in the publish transaction. No prompt change; no cache effect.

### 10.5 Optional identity keys for keyed facts (medium value, low cost)

**Borrowed from.** Engram's `topic_key` upsert (`engram:internal/store/store.go:3501-3543`) and OpenViking's identity-by-filename schemas (`ov:openviking/prompts/templates/memory/entities.yaml:11`).

**Sketch.** Let the historian and `ctx_memory write` attach an optional `key` to `CONFIG_VALUES` and `NAMING` facts, such as a config path (`memory.auto_promote`) or a symbol name. A write whose key matches an active memory in the same project and category becomes an update routed through the mutation log, with the old text kept in the log; it never becomes a second row. This covers the most common supersession pattern, "the default changed from X to Y", deterministically and at no model cost. Keys are also natural anchors for `map-memories`, because a config path or symbol usually names the file that backs it.

**Cost.** A nullable column with a unique partial index and a small change to the historian's fact format. The risk is keys that are too coarse; restrict them to the two keyed categories.

### 10.6 A pair-verdict table for curate and verify (medium value, low cost)

**Borrowed from.** Engram's `memory_relations` with `supersedes | conflicts_with | scoped | compatible | related | not_conflict` and a persisted "no conflict" memo (`engram:internal/store/relations.go:32-59`).

**Sketch.** When curate decides two memories are distinct, or that one supersedes another, record the verdict with both content hashes. Later curate runs skip pairs whose hashes have not changed, and `scoped` verdicts (both true, in different parts of the code) can be shown to the agent as such. This addresses the repeated re-listing and re-judging the token study measured in curate (`mc:docs/reports/dreamer-token-usage.md:63`).

**Cost.** One table plus a filter in curate's input selection. The verdicts are written by existing tasks.

### 10.7 Anchor memories to a commit (lower value, low cost)

Hindsight separates when something happened from when it was said (`hindsight:models.py:133-140`). The coding equivalent is "true as of commit X". Recording the `HEAD` SHA at promotion and at each successful verification lets verify ask git for the diff since that commit for the memory's backing files instead of relying on commit timestamps (`mc:src/features/magic-context/dreamer/verify-gate.ts:207`), and lets `ctx_search` say how old a claim's evidence is. Cheap, and it composes with 10.4.

### 10.8 Use the file mapping as the entity graph (lower value, low cost)

Hindsight's graph arm expands from semantic seeds through shared entities (`hindsight:engine/search/link_expansion_retrieval.py:1-26`). In a code base the useful entities are files and symbols, and `map-memories` already records which files back each memory (`mc:src/features/magic-context/memory/storage-memory-verifications.ts:40-62`). When `ctx_search` returns a memory, it could also return, at a reduced score, other memories mapped to the same files. That gets most of the benefit of an entity graph without extraction, entity resolution or a new model call. Measure it on the fixture before keeping it.

### Not recommended

- **A general entity/relationship graph with LLM entity extraction** (Hindsight, OpenViking entity cards). Its benefit is multi-hop questions about people and things in conversation. For project knowledge the entities that matter are files and symbols, which the code and 10.8 already give us; the extraction adds an LLM cost to every write and a resolution problem.
- **Per-turn recall injected into the prompt** (Hindsight and OpenViking Claude Code plugins). It changes content on every turn and cannot be cached; our auto-search hint gets the recall benefit without the bust.
- **LLM query rewriting or planning on every search** (OpenViking `search`, Honcho dialectic). It adds latency and cost to the read path, and our study found phrasing mismatch, not the lack of a planner, to be the paraphrase failure (`mc:docs/reports/ctx-search-empirical-study.md:20`); a cross-encoder handles much of that more cheaply.
- **Postgres, a hosted vector database or a separate service.** Every one of our hosts shares one SQLite file; nothing proposed here needs more.
- **Time-based forgetting of project facts.** Engram's review dates and OpenViking's hotness are reasonable for personal memory, but a project rule is not less true because nobody retrieved it. Staleness should come from verification against code, which we already do; the TTL belongs on candidates (10.1), not on promoted memories.
