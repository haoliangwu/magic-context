# Going back inside compartment-covered history (real-host probe)

2026-09-29. **The two OpenCode TypeScript hosts silently lose new-branch turns.** In both, `NEW-01` and `NEW-02` were present on the first branch wires, then absent on all later wires and from every compartment's text. The old `OLD-02`/`OLD-03` compartments survived a revert to the start of the second compartment. This is a model-visible history integrity defect, not merely stale metadata. Pi `/fork` made a new session with only the reachable prefix's compartment and did not lose any new-branch marker in eight follow-up turns. Pi tree navigation retained old-branch compartments and raw history. The Rust-mode OpenCode run did **not** exercise the expected coverage-gap refusal: the old raw branch remained visible after the revert, so no refusal code can be established by this probe.

## Reproduction and isolation

Harness: `packages/e2e-tests/scripts/revert-covered-host-probe.ts` and `pi-covered-tree-extension.mjs`. From this checkout, build the two plugins (`bun run build` in `packages/plugin` and `packages/pi-plugin`), then install OpenCode 1.18.30 **into the throwaway root** and run (substitute the existing 2.0.18 binary path as needed):

```sh
BASE="${TMPDIR:-/tmp/}magic-context/revert-covered"
mkdir -p "$BASE/opencode1-bin"
(cd "$BASE/opencode1-bin" && bun add --exact opencode-ai@1.18.30)
for HOST in opencode opencode-rust opencode2 pi-tree pi-fork pi-edit; do
  TMPDIR="$BASE" MC_REVERT_PROBE_ROOT="$BASE" MC_E2E_PI_VERSION=0.87.1 \
    MC_E2E_OPENCODE2_CLI="$HOME/.local/share/cortexkit/e2e-bin/opencode-cli/2.0.18/node_modules/@opencode/cli/bin/opencode.exe" \
    PATH="$BASE/opencode1-bin/node_modules/.bin:$PATH" \
    bun packages/e2e-tests/scripts/revert-covered-host-probe.ts "$HOST"
done
```

The harnesses set private `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_RUNTIME_DIR`, `OPENCODE_DB`, `MAGIC_CONTEXT_STORAGE_DIR`, and for Pi also `HOME`/`PI_CODING_AGENT_DIR`. The **final runs** exported `TMPDIR=$BASE`, placing every host's store under `$BASE`; the provider was the local mock only. Before the first prompt the probe captured `lsof -Fn -p <host pid>` and rejected any open path beneath the enumerated live-store roots. All six final runs recorded `forbidden: []`: OpenCode 1's `lsof` listed its private `opencode.db` and `context.db`, OpenCode 2 listed its private `opencode2.db`; Pi had no database fd open at sampling time (Pi's private root and configured env are still recorded). This is a sampled host-PID open-file check, **not** a continuous audit of every descendant. No live DB or config was opened by the probe. Full captured JSON requests and compartment rows are written to `$BASE/{opencode,opencode-rust,opencode2,pi-tree,pi-fork,pi-edit}.json`; they are deliberately not committed (large transient wire dumps). Harness disposal may remove each private host root, but these wire dumps remain in `$BASE`.

The mock historian reads **only** `<new_messages>` in its request, echoes distinct `OLD-nn`/`NEW-nn` markers from that chunk into a valid tiered compartment, and covers exactly the requested ordinal range. Thus a marker's absence from compartment text is independent of any expected value calculated from the persisted compartment coordinates. A prompt is ~2,400 tokens of narratable ballast plus one marker; mock usage is high enough to trigger repeated historian runs. OpenCode 1 uses the real `POST /session/:id/revert`; OpenCode 2 uses its real `session.revert.stage` then `.commit`. The Pi RPC `/fork` operation uses the second compartment's start entry. Pi RPC has no interactive `/tree` command: a throwaway extension invokes the same `ctx.navigateTree(entryId, { summarize: false })` path through `/e2e-covered-tree`; `pi-edit` follows this with a changed, `EDITED-OLD-02 NEW-01` user submission. That last leg proves the navigated-and-resubmitted edit path, **not** the interactive editor widget or an in-place mutation of the old JSONL entry.

**Key comparison:** OpenCode 1 TS NEW-04 wire has `NEW-01,02,03,04`; NEW-05 wire has `NEW-03,04,05`, while rows at NEW-05 add **only** `NEW-03`. OpenCode 2 shows the same transition one turn earlier: NEW-03 wire has `NEW-01,02,03`; NEW-04 wire has `NEW-03,04`, with the first new row containing **only** `NEW-03`. At NEW-08 both `NEW-01` and `NEW-02` remain absent from both the wire and all compartment contents. This is stronger than a row-count-only observation. Obsolete summaries and sometimes raw rows are simultaneously visible (Pi tree / Rust); old summaries and new raw rows can cover the same ordinal positions even where their *message IDs* differ.

The Pi tree/edit extension exercises the host's actual `navigateTree` API, not keyboard/TUI rendering; it cannot prove whether `/tree`'s editor UI would produce another event order. The Rust coverage check can only be adjudicated after an independent probe that proves the host supplies a genuinely shortened raw array on the next transform; this run did not do so, and no error code should be invented.

## Smallest fix to test

On removal **or branch/leaf change inside covered history**, identify the earliest off-branch message by *stable message ID and reachable lineage*, not merely ordinal. Atomically truncate compartments from the first affected compartment onward (including the one containing the branch point if it is only partially reachable), reset the historian next-start/boundary and any compaction marker that refers to it, then let the historian rebuild those ranges from reachable raw messages. For Pi fork this is naturally a new session with only reachable prefix compartments; for Pi tree/edit it must happen on same-session leaf navigation despite append-only JSONL. For Rust, apply the same check in the authoritative module store and require stable-ID ancestry before trusting coverage. If branch ancestry cannot be established, refuse the transform with a **named** error rather than trimming based only on reused ordinals.

**Cache bust location:** the first outgoing request after branch change/removal, **before** rendering or trimming any compartments: invalidate m[0] baseline, m[1] delta, prefix-trim boundary, and native/projection cached bytes together with the compartment truncation. Reusing a pre-revert m[0]/m[1] would continue to inject phantoms even after SQL deletion; trying to keep the old cached prefix here is invalid because the host conversation itself already diverged at the revert point. Add a regression oracle asserting every new-branch marker is either present on-wire or covered by the *reachable* compartment's text after each historian publish; checking row ordinals alone would pass while NEW-01/02 disappear.
