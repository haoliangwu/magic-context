## Is the guard justified?

Yes for this shape. `@ai-sdk/anthropic`'s locally installed 3.0.82 converter calls `groupIntoBlocks(prompt)` and appends each assistant `reasoning` part with Anthropic signature as a separate `thinking` block (`dist/index.mjs`, `convertToAnthropicMessagesPrompt`, lines 2268 and 2547–2604). It does not combine or discard these two signed parts. OpenCode 1.18.30 was the installed binary during this inspection; its on-disk executable did not expose a separately readable TypeScript adapter source here, so the wire-conversion comparison is against the installed Anthropic SDK and the project's adapter-facing strip rules rather than a direct trace of a live provider request. OpenCode's completed non-provider-executed tool result becomes user-side tool content, dividing assistant runs; `step-start`/`step-finish` are not provider content. The project's Anthropic workaround in `strip-content.ts` (the `stripReasoningFromMergedAssistants` rationale and merged-run planning) documents the same SDK behavior and the HTTP 400 risk for interleaved/multiple signed blocks. The failure here is **two thinking blocks before a completed tool in one assistant message**, not an image, pending tool, provider-executed tool or a thinking-after-text case. CEREB's long computer/browser tool loop generates interleaved thinking segments within tool-call assistant messages. Successful transform passes can proactively strip later segments; LKG restores a previously served prefix and appends the new pristine tail without running that strip, exposing the double-signed shape again.

A possible recovery is to strip only the later reasoning parts of an invalid assistant run **in the replayed tail**, using the existing merged-assistant strip planner's rules, while keeping captured prefix bytes fixed. This is not automatically safe: reasoning signatures can bind tool calls and later content, the newest assistant may be mutation-exempt, and stripping a signed part could change provider-visible history or cache binding. A safe design needs to prove the tail parts are mutable, persist/freeze strip selections before serving (or make the replay strictly one-shot), preserve the first leading signed block and fail closed when bound/exempt parts cannot be removed. This report proposes that investigation, not a replay rewrite; approval and a separate red-first binding/adapter test should precede implementation.

## Decline metric

The transform-latency sentinel now counts standalone LKG validation declines by session and UTC hour, persists a rolling 24-hour count alongside its existing cursor state, and attaches the current hour's reason counts to refused-turn alerts. `--summary --since <UTC> --until <UTC>` scans the requested log window read-only, includes the default OpenCode `.log.1` rotation, emits JSON `lkg_decline_summary` rows (`sessionId`, `hour`, `reasons`), does not send alerts or advance persisted watermarks. Only validation decline names are counted; hydration/capture and secondary `reason=lkg_*` release diagnostics are not duplicate declines. The fixture checks hour/session isolation, per-reason counts, refusal formatting and no-state-write CLI behavior.
