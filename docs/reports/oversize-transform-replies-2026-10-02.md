# Oversize transform replies and control-plane starvation

## Incident evidence

Read-only evidence from the October 2 daemon and plugin logs:

- At 14:08:13.084Z connection 6413, client channel 1, had **5,163,757 queued bytes in one frame**. A following 42-byte frame (correlation 21) exhausted the 4,194,304-byte egress budget. The writer still had not drained two seconds after close.
- At 14:09:18.145Z connection 6462, client channel 1, had **11,142,208 queued bytes in one frame**. A following 51,265-byte frame (correlation 5) caused the same close, followed by the same two-second writer-drain failure.
- CEREB session `ses_0758f6ce7ffeJ0A9sV8Qvema7d` issued a two-message tail delta at 14:08:08.654Z. At 14:08:27.636Z it logged a 18,978 ms transport attempt, `page=1/1`, and `projection_cache_missing_or_reverted`, then built a full request from 1,298 messages. At 14:09:13.647Z it retried the identical final page, and at 14:09:29.871Z served last-good replay after `timed out waiting for 351 bytes` (83,902 ms total pass).
- The first failed health probe was logged at 14:10:44.828Z. Its late answer arrived at 14:11:08.113Z with 28,289 ms latency. ALF's pass logged 17,838 ms of module handler time at 14:10:53.122Z. Route binds also timed out. A health-triggered drain/restart began at 14:13:04.253Z; the subsequent SUBC restart failure is outside this change.

**Attribution limit:** the daemon log identifies the module, connection, channel and correlation, not the request method or session, and does not retain the giant frame bodies. The timing strongly associates these closes with CEREB's tail/full transform attempts, but it does not establish that either queued frame belonged to that session or that the following frames were transform replies. No frame contents or exact session attribution should be inferred from the byte counts alone.

## Transport and scheduling findings

- `McHandler::handle_transform_unpaged_value` eventually returns one `HandlerOutcome::Response` containing the complete transform response. Native output can carry base64 screenshot data. `passthrough_transform_response` also attaches native messages and uses the same unary response writer.
- `buildPagedModuleTransformPayloads` and `handle_transform_page_value` page **requests**, not responses. A tail request can therefore log `page=1/1` while its reply contains many MB of retained history. `callModule` retried the identical final request after a timeout; the transport also reconnected and retried disconnected requests, while generation-sensitive callers could rebuild/re-upload a series.
- SUBC's `CONNECTION_EGRESS_BYTE_BUDGET` is 4 MiB per connection. Its queue admits one giant frame into an empty queue. It refuses the *following* frame until that giant drains. Module-to-client delivery is non-waiting and closes the client on refusal; client-to-module delivery waits for space instead. Thus a giant response is not intrinsically undeliverable, but it prevents safe multiplexing.
- `subc_protocol::MAX_FRAME_BODY_LEN` is 64 MiB. MC's facade/request cap reserves 16 MiB of headroom, leaving 48 MiB. Normal transform request pages are capped at 512 KiB. These body limits are not the daemon's queue budget.
- Production `ck-mc` uses a **current-thread Tokio runtime** in `main.rs`. The SDK spawns request and health tasks, but synchronous projection, SQLite access, native encoding and response serialization still occupy that same runtime thread. This is a concrete mechanism by which a long transform delays health, route binding and reads across all sessions; a separate async task is not a separate execution thread.
- A closed consumer does not directly make MC's handler await that consumer's socket: the SDK has a module writer, and daemon module-to-client enqueue is non-waiting. Large inbound resyncs can occupy the daemon-to-module queue and delay health enqueue/read, and retries can amplify work. The production logs do not expose queue occupancy or lock ownership sufficient to distinguish those contributions from the current-thread runtime starvation. They do not prove an unbounded retry storm or a particular store lock was responsible.

### SDK follow-up for SUBC

In the inspected sibling source, `subc-client-rs/src/lib.rs:280-299` defines `RequestDispatcher.permits`. Data request dispatch acquires this semaphore in `spawn_data_request`, and health acquires the **same** semaphore at `spawn_health_request` around line 1835 before invoking `handler.health()`. Saturating all handler slots can therefore delay health even after synchronous MC work is offloaded. This SDK change belongs to SUBC, not MC; the adapter does not claim to solve exhausted SDK admission capacity.

## Chosen fix

Reply paging was approved for this change; attachment references are deferred to a separate change.

- The production SDK adapter runs data dispatch on `spawn_blocking`, driving any asynchronous follow-up through the existing runtime handle. Control-plane health remains on the runtime. Route lifecycle reply-cache cleanup also runs off that thread so it cannot wait on a large response's cache preparation there.
- Paging is opt-in on each request: callers declare top-level `"accept_reply_pages": true` alongside `method` and other request fields. Missing, false or non-boolean values preserve the original unary response bytes and size, including responses above 512 KiB or the daemon budget. This deliberately retains the old callers' transport risk rather than changing their response schema. THALAMUS, BROCA and other independently deployed callers can adopt the field once they implement page assembly. The plugin adds it to structured transport requests; pre-encoded request bytes remain caller-owned and must include the field to opt in.
- For opted-in requests, responses up to 512 KiB remain unchanged. Larger JSON responses are retained as their **original serialized UTF-8 bytes**, split at character boundaries into 64 KiB chunks. Each JSON page is checked against the 512 KiB target. A byte can expand to six ASCII bytes when JSON escapes it as `\u00XX`; even that worst case expands a 64 KiB chunk to only 384 KiB, leaving room for page metadata. Screenshot pages are approximately 64 KiB, leaving substantial room for other sessions' frames.
- Each subsequent page requires a consumer `reply.page` request, so the entire response is never pushed into the egress queue at once. Page ids are SHA-256 digests of the original response. Ownership includes route channel **and epoch**. Retention is capped at 128 MiB / 64 replies and expires after 120 seconds; missing, expired or evicted pages fail the pass rather than repeating the transform.
- The plugin validates page order, id, total, byte length, page size and final digest before parsing or returning any response. A missing, late, corrupt or reordered page never produces partial messages.
- On a transform connection failure the plugin invalidates its route/connection, then throws `transform_transport_interrupted` instead of reconnecting and resending, or returning a generation-change token that would cause a series restart. The error's message is deliberately not a timeout message, so the transform's identical-final-page timeout retry does not reinterpret a socket failure as a retryable execute deadline. Ordinary non-transform reconnect behavior remains covered.

No pinned cache epochs, durable schemas, render identities or provider-wire content were changed. Older hosts that omit the capability continue receiving unary replies. An opted-in caller must understand `{"reply_page":{"id": "<sha256>", "index": 0, "total": N, "bytes": B, "data": "<serialized reply chunk>"}}`. Fetch indices 1 through N-1 on the same route with `{"method":"reply.page","reply_page_id":"<sha256>","reply_page_index":1}`. Concatenate UTF-8 chunk bytes, verify total bytes B and SHA-256 id, then parse the original JSON. Request paging and reply paging are independent; include the capability on the final transform request page that receives the response.

### Interrupted-transform completion

`module-transport.ts:695-712` produces `transform_transport_interrupted` without a timeout-shaped message or an automatic resend. In `rust-mode-transform.ts:1698-1738`, that error bypasses the identical-final-page timeout retry and reaches the main catch at `3915-4024`. The catch calls `replayLastGood` at `3992-4013`; its implementation at `1878-1995` checks model/context compatibility before replacing `output.messages` with the managed last-known-good (LKG) output bytes from the previous successful pass. If replay is unavailable, `serveRawFallback` at `2238-2245` immediately throws a reconnect refusal for `transform_transport_interrupted`, even when compaction is disabled; no unmanaged history or raw-fit estimation is allowed on this error path. Emergency pressure also refuses directly at `3957-3989`. Both successful replay and refusal finish the pass at `4018-4022`; the transport's deadline bounds an unresponsive request.

The explicit tests `replays byte-identical LKG after transform_transport_interrupted without retrying` and `refuses transform_transport_interrupted without LKG instead of serving unmanaged history` in `rust-mode-transform.test.ts` inject this exact typed error, await pass completion, assert managed output/refusal, and check that no additional transform request was issued. A third test, `refuses transform_transport_interrupted with compaction disabled instead of serving unmanaged history`, supplies a known fitting context and trusted estimator, ensuring refusal is not an accidental context-limit rejection. Removing the interruption guard makes only that third test fail while both other interruption tests pass. Existing transport tests additionally cover socket closure, partial reply interruption and a hung request's finite deadline.

## Verification

`packages/e2e-tests/mode-manifest.json`, which selects files for the automated TS and Rust test lanes, registers `tests/rust-oversize-reply.test.ts` as `rust-only`, with `invocation: {"ts": false, "rust": true}`, host `opencode` and contract `RUST-E2E`. Its validator now checks 155 declared test files (up from 154), including 55 selected Rust test files (up from 54); the 47 selected TS files are unchanged. Both the six validator tests and the standalone manifest validator passed. The unit compatibility test preserves an old-shape reply above 4 MiB byte-for-byte, and the real-daemon regression also checks an old-shape unary reply above 512 KiB before testing opted-in pages.

The regression suite exercises a real daemon and real MC native screenshot passthrough to isolate reply transport from historian/store decisions. It compares reconstructed **raw JSON bytes** against the unpaged small-response template with independently expanded screenshot bytes, observes actual received frame sizes, issues an immediate following response on the same client, probes real channel-0 health, and checks repeated output identity. A separate example wraps real MC dispatch with a two-second synchronous delay and uses the same production adapter on a current-thread runtime, proving health while that pass remains incomplete. The example is not part of the shipped module.

The legacy control was compiled with the production adapter removed from `main.rs`, leaving the original `McHandler` SDK wiring. The real-daemon reproduction closed the client with `subc closed the connection`, and its dated daemon log contained `egress byte budget exhausted`. Running the normal regression against that legacy control also delayed a real health probe by 3,772.9 ms; the independent slow-pass test using the new adapter passed. The fixed production binary passed both real-daemon regressions, including every health probe's one-second bound and repeated native/CK output identity.

`cargo clippy -p mc-module --all-targets -- -D warnings`, `cargo test -p mc-module --lib` (1,495 passed, 17 ignored), and `cargo fmt --check` passed. The plugin typecheck and full plugin suite passed (6,363 passed, four skipped). The new e2e file has a passing narrow TypeScript check. The broader e2e TypeScript project still has pre-existing errors in unrelated SQLite/SDK tests and scripts; no errors remain in the changed e2e files. Full plugin lint and `bun run build` passed.

Non-vacuity controls separately disabled final reply-digest validation and raised unary reply admission to 64 MiB. Only the named digest-corruption test and the named response-frame fence, respectively, failed. The frame fence uses a literal 512 KiB ceiling, independent of the implementation's size constant. Each mutation was staged from the live implementation, showed a non-empty working diff while applied, and was restored to an empty working diff before final verification. The failing controls were `module reply paging > verifies the digest even when a same-length corruption preserves page metadata` (the other three reply-page tests passed) and `tests::oversized_reply_frames_are_bounded_and_byte_identical` (`reply frame exceeded 512 KiB`). The former ran with `bun test packages/plugin/src/hooks/magic-context/reply-pages.test.ts`; the latter directly compiled the actual `reply_pages.rs` source with `rustc --test` and the worktree's built dependency libraries, then ran that test binary. Both controls showed one source file changed with two insertions and one deletion while applied, and no working diff after restoration.

Two additional controls verified the review follow-up: forcing capability acceptance for every request failed only `tests::old_shape_requests_keep_oversized_unary_replies_byte_identical`, while the opted-in frame test passed. Its working diff showed three insertions and four deletions in `reply_pages.rs`. Removing the interruption-specific raw-fallback refusal failed only `refuses transform_transport_interrupted with compaction disabled instead of serving unmanaged history`; the other two typed-interruption tests passed. Its working diff showed two insertions and three deletions in `rust-mode-transform.ts`. Both mutations were restored to an empty working diff before final verification.

The focused hermetic command is `bun run test:rust-e2e --test-name-pattern 'bounded replies'`. This run used locally built debug MC/probe binaries and a copied daemon debug executable through the harness's paired prebuilt-binary overrides; every process used throwaway connection/config/store roots. Without overrides the harness builds its own release binaries.
