# `context.db` migration compatibility audit (v80–v93)

**Scope and interpretation.** v80–v91 are from `master`; v92–v93 are from `window/b0-v92-v93` (branch citations below mean that branch's file and line numbers). This is a source audit, not a mixed-host experiment. “Additive” means **all** of S (permitted schema/data shape), D (optional, recoverable derived state under old writes), and R (old readers keep their meaning). A no-op passes S vacuously. The classification is about safely *allowing old binaries to continue writing*, not merely whether a fresh empty database opens. Current behavior compares the highest upstream `schema_migrations.version` against `LATEST_SUPPORTED_VERSION=91` and refuses newer databases [storage-db.ts:107,306-365](../../packages/plugin/src/features/magic-context/storage-db.ts); the runner records every migration in that same table [migrations.ts:3166-3187,3233-3302](../../packages/plugin/src/features/magic-context/migrations.ts).

### v91 mixed-version trace (0.43.2 / fence 90)

1. Under today's implementation the 0.43.2 plugin **cannot** perform the hypothetical write: opening a v91 database returns null because `91 > 90` [storage-db.ts:350-365,844-853](../../packages/plugin/src/features/magic-context/storage-db.ts). The trace below assumes a future separate additive ledger lets that exact older binary open it; it does **not** assert a live mixed-host run occurred.
2. The old host's ordinary `memories` insert/update does not set `memory_embedding_watermarks.written_memory_id`; the v91 table has no `memories` trigger [migrations.ts:3131-3150](../../packages/plugin/src/features/magic-context/migrations.ts). If a Rust module already marked a project, the newer drain queries *all* missing active embeddings and can sweep the old-host row while a mark is pending; it advances the embedded mark only after `done` [single-store-embedding-drain.ts:38-105](../../packages/plugin/src/features/magic-context/memory/single-store-embedding-drain.ts). If the old write happens **after** `written_memory_id == embedded_memory_id`, or no module writer ever made a mark, `getPendingEmbeddingWatermarks` returns nothing: the **watermark-driven drain alone cannot see that write**.
3. Crucially the new host also invokes `embedUnembeddedMemoriesForProject` on startup/interval maintenance for registered projects with embedding enabled [dream-timer.ts:446-471](../../packages/plugin/src/plugin/dream-timer.ts). That query scans active unembedded rows by project/model and hash-guards vector saves, independently of the watermark [project-embedding-registry.ts:2550-2555,2586-2645](../../packages/plugin/src/features/magic-context/project-embedding-registry.ts). Demand-driven search can also fill missing embeddings [embedding-backfill.ts:10-26,37-65](../../packages/plugin/src/features/magic-context/memory/embedding-backfill.ts). **Thus not permanently stale when the project is registered, embedding is enabled and the maintenance/provider eventually succeeds**, though a row may be missing from vector recall until then. When disabled, unregistered or provider-unavailable, there is no guarantee of eventual embedding; enabling/reopening/registration or a later module watermark permits catch-up. The v91 migration test only covers existing-row preservation, not this old-host sequence [migrations-v91.test.ts:64-106](../../packages/plugin/src/features/magic-context/migrations-v91.test.ts).

## Version/fence consumers and separate-ledger changes

* **TypeScript plugin:** `getPersistedSchemaVersion` reads `MAX(version < 10000)` from `schema_migrations`; `schemaVersionIsSupported`/`enforceSchemaFence` compare it to `LATEST_SUPPORTED_VERSION`, and `finishDatabaseOpen` refuses before using the DB and logs the pair [storage-db.ts:306-365,844-853,915-917](../../packages/plugin/src/features/magic-context/storage-db.ts). Open paths must keep rejecting a newer **breaking** lane, ignoring the additive ledger for old builds; new builds must discover additive migrations without reclassifying unknown legacy rows as harmless. Keep fail-closed for unknown future breaking versions, and use distinct names/log messages for additive progress versus compatibility ceiling. The OpenCode warning consuming rejection state must similarly describe only breaking incompatibility [conflict-warning-hook.ts:339-376](../../packages/plugin/src/plugin/conflict-warning-hook.ts).
* **Migration runner:** `getCurrentVersion`, `isMigrationApplied`, pending selection under `BEGIN IMMEDIATE`, per-migration insert and sibling-PK-conflict recovery all assume a single monotonically increasing `schema_migrations` sequence [migrations.ts:3166-3187,3200-3221,3233-3302,3317-3326](../../packages/plugin/src/features/magic-context/migrations.ts). Give each migration an immutable lane and ledger, select/check it by **its own** row rather than `candidate.version > MAX(breaking)` alone (otherwise an older missing additive migration is skipped), preserve transaction + row atomicity and concurrent-startup retry, and translate already-installed single-ledger rows without replay. Fence comparisons must see only breaking rows. Do not relabel previously recorded version 85's historical rewrite as never having happened on deployed databases [migrations.ts:2975-2989](../../packages/plugin/src/features/magic-context/migrations.ts).
* **Pi:** Pi imports the plugin's `openDatabaseAsync`, not an independent migration implementation [packages/pi-plugin/src/index.ts:67,1008-1043](../../packages/pi-plugin/src/index.ts); its unavailable handling and stale-host warning must continue to distinguish a *breaking* fence from harmless additive drift. Shared plugin open/runner fixes cover both hosts, including Pi's node:sqlite adapter [migrations.ts:3200-3209](../../packages/plugin/src/features/magic-context/migrations.ts).
* **CLI:** `openExistingContextDatabase` refuses newer versions for both reads and writes, and `CLI_SCHEMA_FLOOR_VERSION` rejects older DBs for writes [packages/cli/src/lib/database-access.ts:50-55,91-135](../../packages/cli/src/lib/database-access.ts). Use the breaking ceiling/floor for compatibility and independently check that each **required additive object** exists before a CLI mutation uses it (a single floor alone will no longer prove that). Doctor's `readStorageVersions` / `checkStorageVersionFence` currently report/compare max schema and compiled max; keep an explicit breaking lane and report additive ledger separately, preserving the pending-migration/live-process alarm [packages/cli/src/lib/storage-versions.ts:22-95](../../packages/cli/src/lib/storage-versions.ts); OpenCode and Pi doctors consume this alarm [packages/cli/src/commands/doctor-opencode.ts:1745](../../packages/cli/src/commands/doctor-opencode.ts), [packages/cli/src/commands/doctor-pi.ts:741](../../packages/cli/src/commands/doctor-pi.ts).
* **Cached/pinned plugin checks:** doctor opens the DB read-only without its own fence, scans OpenCode 1/2 dist-tag caches and compares each copy's compiled fence to DB max [packages/cli/src/commands/doctor-cached-plugin-fence.ts:56-104,113-128,141-175](../../packages/cli/src/commands/doctor-cached-plugin-fence.ts). Pinned checks extract `LATEST_SUPPORTED_VERSION` from installed dist or npm tarball and compare it likewise [packages/cli/src/lib/opencode-plugin-schema-fence.ts:15,69-106,154-182,254-294](../../packages/cli/src/lib/opencode-plugin-schema-fence.ts). Compare only the breaking ledger to each artifact's breaking ceiling; old artifacts already containing the current literal remain readable. Unknown/missing artifact fence stays “unknown,” not “safe.” Show additive lag as informational, not a cache-delete/restart instruction; bundled dist fence guards/tests must reflect the new meaning.
* **Dashboard:** Rust workspace readiness requires a `schema_migrations` row with max upstream version ≥35 *as well as* tables/column checks; caches only `true` [packages/dashboard/src-tauri/src/workspaces.rs:13-17,41-93](../../packages/dashboard/src-tauri/src/workspaces.rs). Keep the old v35 breaking proof or explicitly verify that v35's objects exist; do not replace the check with additive max or read an absent ledger as not-ready. The dashboard is a read-only schema consumer, not a ceiling that refuses higher versions [workspaces.rs:60-93](../../packages/dashboard/src-tauri/src/workspaces.rs).
* **Rust module:** `BUILT_CONTEXT_FENCE_VERSION=91` is **reported**, not a global write refusal; `FenceState` reads the same max and stores built/persisted versions, `lane_ahead` is informational [crates/mc-module/src/host_store.rs:61-67,474-526](../../crates/mc-module/src/host_store.rs). Separate breaking/additive reporting in status if desired. Actual writes check bracket and per-table SHA256 `sqlite_master` fingerprints (table + indexes + triggers), so even an additive index/column on a fingerprinted table may be refused until the Rust binary's expected hash is updated [host_store.rs:83-106,372-413,430-471,503-551](../../crates/mc-module/src/host_store.rs). A ledger split alone does **not** make these Rust writes compatible: retain strict checks for real authority changes, or design a compatibility-aware projection with tests; the v91 table is itself in `DOMAIN_TABLES` and fingerprinted [host_store.rs:83-96,386-392](../../crates/mc-module/src/host_store.rs). On the v93 branch, `MARKER_LANE_VERSION=93` determines whether the marker is consulted and its fingerprint is checked even though the module never writes that table (`window/b0-v92-v93:crates/mc-module/src/host_store.rs:67-79,113-122,431-449,535-560`); change that threshold to marker-object/ledger presence without treating an absent/altered marker at the required level as “unmarked.”

## Mechanical gates and compatibility experiment

**S is substantially checkable.** Parse the executed SQL plus helper calls such as `ensureColumn`, allowlist `CREATE TABLE`, `CREATE INDEX` and nullable/defaulted `ADD COLUMN`, and reject `CREATE TRIGGER` on a pre-existing table, `DROP`, `RENAME`, `UPDATE`/`DELETE`/data-copy and unsafe defaults. Static SQL alone misses dynamic helpers, conditional branches and trigger bodies; for each v(n−1) fixture also snapshot `sqlite_master` (type/name/tbl_name/SQL), `PRAGMA table_info` and representative pre-existing data before/after `migration.up` in one throwaway SQLite DB. The diff can catch added/modified triggers/indexes and incompatible columns; data hashes or row-level comparisons catch v87-like rewrites that a schema-only diff misses. Verify generated fresh-schema parity too (`initializeDatabase` already creates/ensures objects independently [storage-db.ts:921-935,1823-1827,1915-1924](../../packages/plugin/src/features/magic-context/storage-db.ts)). Neither static nor schema diff proves D/R; v83, v89 and v93 pass S but fail overall.

**D/R need behavioral compatibility tests, not just schema tests.** In a throwaway root under `$TMPDIR/magic-context/migration-compat/`, set `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`, `OPENCODE_DB` and `MAGIC_CONTEXT_STORAGE_DIR` there. Use an immutable **previous released npm artifact** with its actual compiled old fence, migrate the isolated DB with the new build, start the old OpenCode/Pi plugin and exercise representative inserts/updates/deletes, then restart new code and check both old query results and new invariants. A legacy artifact will fail at today's fence before the compatibility behavior runs: for the experiment use a test-only fence-bypass/shadow additive-ledger adapter in the *throwaway* environment, never change a release artifact or live DB. Include completed-backfill-before-old-write cases (v83/89), `mapping_origin` fallback (v82), changed-coordinate and floor epochs (v84/88), post-watermark v91 old inserts with no subsequent Rust write, and marker-present v93 mirror/drain refusal. Assert independently against base data rather than computing expected output via the same cache or watermark logic under test. Probe old writes and old reads before new catch-up, eventual new convergence, and provider-off/on and restart recovery. A green finite test bounds its tested paths/schedules, not all user stores, SQLite adapters or future writers; require review for D/R and unknown migrations.

## Decision and user impact

**5 of 14 additive** on the present bodies: 80, 81, inert 85, 91 and 92; **9 breaking**: 82–84, 86–90 and 93. If each version were rolled out separately with an older host still running, the split would avoid **five per-transition forced coordinated restarts per lagging host**, not five measured historical fleet restarts: deployments may batch versions, v85 used to be harmful before being made inert, v92/93 are on a branch, and v91's benefit depends on eventual embedding maintenance. There is no defensible count of actual machines or restart events from source alone. The module's fingerprint fence can still force its own write refusal at a supposedly additive version until independently addressed.

False **additive** is worse than an extra restart: old writes may leave FTS/date results silently missing after a completed backfill, preserve wrong memory-mapping provenance, use an obsolete protected floor or wrong conversation ordinals (bad compaction/protected-tail decisions), make a live historian lease appear owned by a dead PID (two concurrent holders), or mirror/drain a single-store project's authoritative data into a stale store and lose/duplicate notes or memories. Trigger changes can also make old writes fail unexpectedly. False **breaking** only retains the present availability cost (lagging OpenCode/Pi host fails closed until restart/update), but is the safe default for uncertain migrations. In particular, v91's mark is not a complete change feed: its classification depends on verifying the independent full unembedded-memory scan before relaxing the fence.
