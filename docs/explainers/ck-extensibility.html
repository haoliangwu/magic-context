CK session extensibility: providers, preflight and a runner that freezes

An explainer of design draft r4.1, for the operator's review. It describes a design, not built behaviour; where the design says a piece is already live, this page says so. Each section cites the design section it summarises; where this page simplifies, the cited section has the full rule. illustrative marks a sketch made for this page (screen wording, example layouts) that the design doesn't specify. design is silent marks a point the design doesn't settle.

The question it answers: how modules contribute to a model session that a CortexKit runner executes. Broca is the first runner; Thalamus uses the same interface. Two constraints hold throughout [§1]:

  • the runner knows nothing about personas, session kinds or any module's internals;
  • the prompt cache is never broken by accident.

2. What changed since r3.1

The design changes between r3.1 and r4.1, grouped by area. Section numbers are r4.1's.

Launch and preflight

  • Trust is no longer an input to preflight. There is no trust fact on the route, no trust claim on the call and no admission_facts_targets list. A trusted and an untrusted run with the same params get byte-identical manifests [§4.2].
  • Preflight no longer runs on a dedicated internal_service route per (provider, trust value). It must have no side effects; how a provider achieves that is its own business. Prefrontal opens preflight-only routes against the CK data home, never a project [§4.2, §11.1].
  • A narrower toolset for unapproved projects is now an explicit param choice by Prefrontal, never a side effect of trust [§4.2].
  • The manifest cache key grew: machine id, consumer profile, a digest of the provider's prefix-affecting config keys, host capability inputs, and (for system-prompt providers) the resolved tool names. Trust and a self-declared module_version are never part of it [§4.2].
  • Cached manifests are dropped on every new spawn of the module, learned from supervisor.spawn_subscribe; a cursor gap drops the whole cache [§4.2].
  • Determinism is scoped per (host, provider version, consumer) [§4.2].
  • Capability names changed from dotted to dashed: ck-provider-tool/v1 and so on. A dotted name now fails manifest deserialization, so the module is never registered [§4.2].
  • System-prompt providers are preflighted after tool providers and receive the resolved model-facing tool names as an input [§4.5].
  • The freeze covers the whole session, not one run. tools and system are sent only on the first send; a later send that changes them is refused with a named error [§4.5].
  • Project docs: ruled for now. Magic Context's m0 keeps carrying them until Prefrontal ships its own carrier, and no second carrier runs meanwhile [§4.3, §16.1].

Trust and identity (new sections)

  • Project trust has an owner: entorhinal, as a journaled field of the project record, asked with project.trust(path) when a call executes. It has its own walk that handles clones and worktrees [§4.6].
  • Caller identity is a separate question from project trust. The daemon-stamped route principal is the only caller fact a provider trusts [§4.7].
  • Routes the runner opens carry a Prefrontal-signed agent credential (v2) that names the agent, the machine and the carrier. It has no expiry and isn't a security boundary; authority stays with each provider's per-call grant check [§4.7].
  • A call with a credential needs both the carrier module's grant and the agent's own grant [§4.7].

Compaction

  • REFUSE no longer ends the run with a new CompactionRefused reason. It ends as Error, with the provider's code as provider_code [§5.5, §13].
  • WAIT past the cap now ends as Error with compaction_wait_exceeded. Broca also won't send when it can't tell whether the request fits [§5.4].
  • The status carries window limits and usage only when they are known, and the previous run's provider_code when it ended as Error [§5.2].
  • An overflow ends the run as Error with the provider's code, which the next status carries [§5.3].
  • New CompactionMessages, call timeouts, and entry into and exit from compaction_wait are written and synced before the request goes out [§5.2].
  • Each CompactionMessage carries a monotonic version; a late answer never replaces a newer one [§5.3].
  • The "kept signed thinking is byte-identical" check is gone. The runner's own validity rules for the family replace it [§5.3, §12].
  • soft and hard describe cache cost only. Mid-conversation appends are re-emitted after a soft replacement and folded into the new prefix on a hard one [§5.3].

Hooks

  • Hooks return operations (prepend, append, replace) instead of new values [§6.2].
  • Per-tool allowed operations replace result_integrity: append_only [§6.2].
  • Attribution is the list of operations with their module and note. The per-stage output digests are gone [§6.2].
  • The final value lives in the record's existing rendered field, so a rolled-back Broca still renders the right bytes. Originals and attribution are new fields [§6.3].
  • PreTool providers declare on_unavailable: pass | refuse, defaulting to refuse [§6.3].
  • The runner's own step edits are ordinary recorded operations [§6.3].

Changes while running

  • manifest_applied is replaced by two WAL records: manifest_pending (the full new manifest) and prefix_rebuilt at the fold. The drift guard compares against the latest fold [§4.5, §11.2].
  • The fold model: while the prefix survives, a change is an append (only on routes with the append capability); any full bust rebuilds the prefix from the latest manifest and absorbs the appends [§11.2].
  • Each route reports one append capability, yes or no, fixed at admission [§11.2].
  • The watch set is seeded from live_roots once, then tracked by the provider from its own binds and closes [§11.1].
  • The hint subject is ck.<account>.ext.changed.<module_id>. The module id is trustworthy because of per-module publish grants, which need a commons grant change and a ck-bus release [§11.1].

Runners, cache and records

  • §12 is now "Runners". It starts with the runner's obligation: every rendered request is valid for its family, and the rules live in the runner's own spec [§12].
  • Whatever the runner strips after a prefix change is recorded in the same WAL record as the change [§12].
  • The Thalamus section is now a detailed mapping: ccm-N ids, how each hook maps onto the harness's own hooks, 503 behaviour, WAIT bounds [§12.1].
  • The breakpoint planner is now two explicit steps, and a bridge takes the lowest-priority chosen slot. Broca's plan_markers changes to this order [§7].
  • provider_notice gained durability: acknowledged after fsync, resent until acknowledged, deduplicated by event id [§10].
  • The reader gate's mechanism is a new frame ver, with a NewerWriter{ver} step and a per-WAL rollback floor. It also covers new fields on known kinds [§13].
  • Build stages name their dependencies (the entorhinal write check, the Plexus work). The crash matrix is the exit test for stages 4 and 5 [§15].

Open items

  • Closed: project trust, including the trust fact's schema (now §4.6), and the project-docs carrier for now. The per-family append table moved to Broca's own research note [§11.2, §16].
  • New: whether a worker may act under its parent head's agent, Magic Context's [cleared]-thinking handling, and provider-restart reconciliation [§16].

3. Principles and provider kinds

  1. The caller decides, the runner executes, providers supply. Prefrontal, or whoever starts a run, decides what a session gets. Broca runs it and applies changes when told. Modules provide tools, system text, compaction and write-time transforms.
  2. Broca never sees a persona, a session class or a turn's origin. It gets a flat manifest of providers and their contributions.
  3. The prefix is frozen. System text and tools are resolved once and replayed byte for byte. They change only through an explicit change applied under a declared policy.
  4. Every module output that affects bytes is written when it's produced. Resume replays the record and never calls a module to produce it again. There is one exception, in section 12 of this page.
  5. Each provider keeps itself coherent. It returns a finished, self-consistent contribution for the params it was asked for. The engine doesn't compose, filter or repair it.

4.1 Params

The persona belongs to Prefrontal. It decides which tools the session needs, how strict it is about them, and which params to ask each provider for. CK defines a small shared vocabulary; a provider may add axes of its own. A value a provider doesn't know is refused at preflight, never guessed [§4.1].

4.2 Preflight

preflight(cwd, params) returns a manifest: the exact tool definitions and system text the provider would put on the wire, a digest for each item, and one digest over the whole manifest [§4.2].

What the provider guarantees

  • Own configuration. It resolves its user, project and harness tiers with its own merge rules. No second merger exists.
  • No trust input. Trusted and untrusted runs with the same params get byte-identical manifests. Trust is enforced only when a call executes.
  • Coherent. Everything the tools and text refer to is in the manifest. AFT returns a foreground-only bash when bash_status is absent (AFT's own work, in its spec). Each provider tests this itself.
  • Deterministic per (host, provider version, consumer): stable key order, no timestamps, counters or random ids. Manifests may differ between machines, versions or consumer profiles, never within one.
  • Bytes only. Settings that don't change bytes (watch timeouts, size caps) travel with each call instead.
  • No side effects. It writes nothing and starts nothing. How it achieves this is its own business.

What Prefrontal does

  • Runs it early. While planning, before a worktree exists or a model call is spent.
  • Bounds it. A short deadline per preflight. On a timeout it keeps the last good manifest and retries later. A turn is never delayed by preflight.
  • Caches it under the key below.
  • Invalidates it on every new spawn of the module, learned from supervisor.spawn_subscribe (cursor {daemon_incarnation, seq}). A cursor gap drops the whole cache.
  • Discovers providers from the catalog's capabilities.provides, with no calls. Names allow only [a-z0-9-] before /vN; a dotted name fails deserialization, so the module's HELLO is refused and it never registers.

4.3 System text is operator authority

A SystemPromptProvider is one the operator chose to install. Its text may vary with params and user-level configuration. It never includes content supplied by a project: a cloned repository must not be able to inject text into the system prompt. A project-level setting may only choose among texts the provider ships. Per-project and per-session content (project docs, memories, counts) goes into user-role content [§4.3].

Project docs today: Magic Context's m0 carries ARCHITECTURE.md and STRUCTURE.md. It keeps them until Prefrontal ships a carrier of its own. Until then no second carrier runs for Magic Context sessions. What replaces it later is open (§16.1).

4.4 The persona check

Runs in Prefrontal. Each role declares its params per provider, its required tools (by model-facing name) and whether it's strict or lenient. A strict role missing a required tool fails with a typed launch refusal naming the tool, raised before any worktree exists. A lenient one runs without the tool [§4.4].

4.5 The session manifest and the freeze

Prefrontal sends Broca [§4.5]:

  • the tool providers, each with its params and manifest;
  • the system-prompt providers, in order; the order is the precedence. Prefrontal is itself first: its persona and role text is preflighted and digested like any other. A persona catalog update is a change like any other (section 14 of this page);
  • the compaction provider, or none;
  • the step-transform providers, in order.

Preflight order is not manifest order. System-prompt providers are preflighted after tool providers because they take the resolved tool names as input; Prefrontal's role and head templates branch on tools.<name>. Their digest covers that input, so a tool-set change re-preflights them. The order in the manifest stays the precedence order.

The freeze covers the whole session

  • tools and system are sent only on the first send. The resend after an auth pause repeats that first send byte for byte.
  • Broca freezes the manifest on the first RunStarted.
  • A later send whose tools or system differ is refused with a named error code, never applied.
  • Tool-set changes go only through the change path: appends where the route allows them, or a fold.
  • Resume takes tools and system from the frozen manifest or the latest fold, never from the latest RunStarted.

A pending manifest is a WAL record

A changed manifest from Prefrontal is written as manifest_pending{manifest, digest, policy}, holding the full bytes, behind the reader gate. The step that applies it (a tool step included) rebuilds the prefix from that record and writes prefix_rebuilt{manifest_digest, step}. No new RunStarted is needed. The drift guard compares the latest fold's prefix with the manifest_pending record its digest names; both come from the WAL.

5. Project trust (owned by entorhinal)

The question: has the user approved this repository, so its own configuration may act (enable shell auto-approval, write tools, endpoints that could leak data)? [§4.6]

Trust never changes the prefix. Providers enforce it only when a call executes: they refuse, restrict paths or skip project filters. They never change tool definitions or system text. Approving or revoking a project mid-session changes no bytes and takes effect on the next call [§4.2].

Owner and values

  • entorhinal holds the approval as a journaled field of the project record and declares project-trust/v1.
  • Two values: approved and unapproved. Finer limits are each provider's own policy for an unapproved project.

Writers

  • Only the ck CLI and Reserved{prefrontal-core} may write; mutations come only from Direct or Reserved{prefrontal-core}.
  • This check is hygiene against buggy writes, not a security boundary. The real protection: a repository's own content has no path to any writer.
  • Status: in entorhinal cc6eedd (0.1.6), pushed but not yet placed. Placing it is the precondition for project.trust writes.

AFT never refuses for trust

For AFT an unapproved project is never a refusal. The command runs; only the project's own output filters are skipped. AFT never returns project_approval_required.

5.1 The walk

entorhinal answers project.trust with its own walk, separate from resolve. It canonicalises the path with ProjectRootId, then checks each level from the path upward. Check (a) comes first at every level, so the .git-directory boundary never applies to a registered root itself.

Provider cache

  • Never cache "unapproved".
  • Cache "approved" with a short TTL (about 60 s) plus the change hint.
  • When the TTL expires, ask again. No generation-only probe: project.trust costs the same (one local route call, one indexed read), and the journal generation also moves on unrelated registry edits.
  • Drop the whole cache on any bus disconnect or cursor gap.

Failure answers

  • entorhinal unreachable on a cold cache → approval_unverifiable{root}, never an approval prompt.
  • entorhinal not installed → one fast unknown_module refusal, cached until the catalog changes; the provider then uses its own record.

Without entorhinal

For example a standalone AFT inside OpenCode. The provider keeps its own record, as AFT's per-project trust list and Magic Context's project-config boundary do today. Records are keyed on a canonical path or an id the provider resolves itself, never on the bind's caller-supplied project_id.

6. Caller identity and agent credentials

The question: who is making this call? Two callers in the same project can differ, so this can't come from a project record. For example, AFT gives an MCP facade or an unverified principal text-only replies, forced root-path restriction and permission-gated bash, while the same project is fully trusted when Prefrontal or AFT's own plugin calls [§4.7].

  • The route principal is stamped by the daemon on every bind. It is the only caller fact a provider trusts. The bind's session is never trusted.
  • Runner-opened routes. Broca opens the routes for its tool calls itself, as reserved:broca. That principal names the runner, not the agent. So authority for an agent on such a route has two layers, and neither substitutes for the other:
    • the carrying module's own grant: may reserved:broca carry agents at all;
    • a Prefrontal-signed agent credential naming the agent.
    This is the same shape as the live GitHub bot path through reserved:aft.

What the credential is for

It identifies the agent and keeps a carrier's bookkeeping honest: a provider doesn't have to trust which agent a carrier says a call belongs to. It is not a security boundary. Every call reaches a provider through this machine's daemon, which stamps who opened the route. A call relayed from another machine arrives under the relaying module's principal (for example reserved:callosum), which the carrier binding refuses. Using a credential needs a carrier holding a module grant, and grants are the operator's act. Anything on the machine can read Prefrontal's key anyway.

No expiry

v2 claims carry no exp, and a verifier reads a missing exp as non-expiring on v2 only. No far-future exp is used, so nobody mistakes a number for a policy. Plexus's verifier requires exp today, so this is a verifier change. Authority stays with the provider's per-call grant check: revoking an agent's grant takes effect on its next call.

Machine-bound

  • The signing key is created in this machine's vault. Nothing replicates it, though a vault backup carries it. Plexus verifies against its own machine's Prefrontal key.
  • Both sides take the machine id from the daemon, never the OS: ModuleHelloAckBody.machine_id, served from subc-protocol 0.25.0, read through subc-client-rs 0.18.0+. Prefrontal already reads it.
  • Absent is not a match. Prefrontal never issues a credential while its own HelloAck had no machine id.
  • A match only ever narrows. The id survives a full restore (ck machine adopt), so binding catches a vault copied to a second machine without its id, not a restore that adopts it.

Carrier-bound

The credential names the carrier it was issued to (for example reserved:broca). Federation can deliver a call from a paired device with the tool arguments byte for byte, but under reserved:callosum. A replayed credential therefore fails on principal alone, whatever the relay's exposure config says.

Resume and storage

  • A resume with the sidecar missing refuses dependent tool calls by name (agent credential missing for this session). Calls that need no agent identity are unaffected.
  • After a Broca restart, Prefrontal re-issues only if the sidecar is missing and the run is still one it launched. Otherwise a missing sidecar is a permanent refusal for that run.
  • The runner never requests a credential. There are no Broca heads yet.

Relays and exposure

  • A relaying module (for example callosum federation) gets no carrier grant for agent credentials without an explicit operator decision. Today no relaying principal holds any Plexus grant, and nothing on Plexus, AFT or Broca is exposed to federation peers.
  • An exposed Prefrontal operation that enqueues a prompt lets a paired peer make a local agent act under its own credential. Owner-paired devices act as the operator. Any wider audience needs its own exposure decision, outside this design.

7. Compaction: setup and one model step

7.1 Setup

Called once when the session starts. It returns [§5.1]:

  • The initial CompactionMessage. This is how a session starts with its head already in place. For Magic Context it inserts m0 and m1 before the first user message, as an empty range replaced by [m0, m1]. A provider with no head returns an empty one.
  • Message stability. A rank for each of the provider's own messages; higher means it changes less often. Magic Context's main sessions declare {m[0]: 2, m[1]: 1}. A subagent session declares nothing, because it has no m0 or m1. Indexes refer to the provider's output, not wire positions.

Broca records the initial CompactionMessage before the first model call. If Setup fails or times out, no model call is made and the run ends as Error with a provider_code.

7.2 The per-step call

On every model step, Broca sends a status and waits for one of four answers [§5.2].

The status

Only what Broca already has in its WAL or model catalog. The status itself isn't written to the WAL.

  • the step id; new user turn or tool step;
  • the model and variant;
  • the context window and output limit when the catalog resolves them, otherwise absent;
  • the previous step's usage (input, cache read, cache write, output) with completion time and finish reason, when recorded;
  • when the previous run ended as Error, its provider_code. An overflow ends a run this way with no usage;
  • Broca's estimate of the request, labelled as one (no tokenizer for most families), plus the previous step's measured input;
  • prefix_rebuilding with its reason (flush, manifest change, model switch, expired cache);
  • the newest message id and the last applied CompactionMessage id;
  • the current time.

Written before the model call

Broca writes and syncs, before sending: a new CompactionMessage it will apply, with whatever the runner strips in response; a record of a call timeout; entry into and exit from compaction_wait. NOOP writes nothing. The request goes out only after these are durable.

Timeout

About 2 s for NOOP and CompactionMessage. On a timeout Broca records it and proceeds with the last recorded CompactionMessage. One always exists, because Setup's is recorded before the first model call.

8. The CompactionMessage

  • The range. from is the marker; messages before it aren't sent. to is exclusive: the start of the provider's protected tail, which goes out raw. Both ends are Broca's durable message ids, never array indexes. to may not separate a tool call from its result.
  • The replacement stands in for the range. For Magic Context: [m0, m1, reshaped messages from the range]. It's the provider's finished output, so the hooks don't run over it.
  • The whole working range, never a delta. The runner uses the latest one until another replaces it.
  • Monotonic version, increased per session by the provider. The runner applies one only if its version is higher than the last applied. A late answer (a retry after a timeout, or overlapping requests on one key, which Thalamus sees) never replaces a newer one.
  • Drops. ctx_reduce only queues. Queued drops land on the provider's next pass as a new replacement, with the marker unchanged.

[§5.3]

Checks before sending

  • roles follow the family's rules;
  • every tool call is paired with its result, over the replacement and the raw tail together;
  • no tool-call id appears that isn't in the range;
  • the rendered request meets the runner's own validity rules for the family.

A view that fails is refused and recorded; Broca proceeds with the previous CompactionMessage.

What the label means

soft and hard describe cache cost, not request validity. soft promises only that the cached prefix up to from survives. The runner may still discard content after from (for example reasoning) to keep the request valid for its family, per its own spec. Broca verifies the claim, and every check, against the array it rendered last; it doesn't trust the label.

Appends and compaction

Appends exist only on routes with the append capability.

  • soft: each append the range covers is re-emitted byte for byte, in its original form and order, right after the replacement; never merged or rewritten. A soft replacement that would drop one is refused like a structural failure.
  • hard: the prefix is rebuilt anyway, so the appends fold into it and are dropped from what's sent.
  • Turn-scoped (clear_at) messages stay in history byte-identical after they clear, until a fold.

Recorded in the WAL

Every CompactionMessage is a record; resume replays the latest. If the provider is down, Broca keeps serving the last recorded compaction plus the raw tail. The only risk left is overflow, which ends the run as Error with the provider's code; the next status carries it.

[§5.3]

9. Cache breakpoints

Broca owns breakpoint placement, per model family. Its planner works in two steps [§7].

  1. Choose which markers get a slot. Candidates in priority order:
    1. the tail;
    2. the compaction provider's declared messages, highest stability rank first;
    3. the end of system: cheap to lose, because the most stable message's cache entry already includes system;
    4. the lookback bridge (for a step more than 20 blocks past the previous boundary) and the standby-model bridge.
    With N slots the first N candidates get one. A bridge, when needed, takes the slot of the lowest-priority candidate chosen. Under pressure the tail is kept and the least stable candidates drop first.
  2. Place each chosen marker. The tail marker goes on the last block. A declared-message marker goes where that message is rendered after the replacement; Broca maps provider indexes to wire positions on every step, so positions are never fixed. The system marker goes on the last system block.
  • Broca's plan_markers resolves slot pressure in the opposite order today. It changes to this order in build stage 4.
  • A caller's cache.tail: volatile removes the tail candidate. It is refused on runs with tools.

10. WAIT and REFUSE

WAIT

  1. Broca holds the step and sends nothing. The run enters compaction_wait, written and synced before the wait begins.
  2. Within the running daemon, Broca calls again with a fresh status on whichever comes first: compaction.ready(session) from the provider (the normal path), or bound_ms running out.
  3. The provider may answer WAIT again, but an engine-wide cap limits the total wait per step.
  4. At the cap Broca decides from its own numbers. If the window is resolved and the request is estimated to fit with the last recorded compaction, it sends. Otherwise the step ends as Error with provider_code compaction_wait_exceeded. It never sends a request it knows, or can't tell, will overflow.
  5. Broca publishes "waiting on compaction: <reason>". The user can cancel the step; new user messages queue as usual.
  6. Interruption. A daemon stop seals the run Interrupted. After a crash, resume finds a wait entry with no exit, seals the run Interrupted and sends nothing. Either way, only a caller's resend continues it, with a fresh provider call.

[§5.4]

REFUSE

  1. Broca doesn't send. It ends the run as Error, written to the WAL. The provider's code becomes provider_code; the record also carries the provider id and reason. No new terminal reason or enum value exists for this. Nothing is added to the model's history.
  2. Retryability maps onto the existing transient or permanent classes, never a new one.
  3. Prefrontal gets it as the run's terminal result, like any other, and shows reason as user-facing text. This doesn't depend on the deferred user-notice channel.
  4. The session stays usable; the next send calls the provider again. Transient: automatic retry makes sense (the historian was only busy). Permanent: the user has to act (switch to a larger model, fix the configuration).
  5. A refusal on a tool step keeps the tool results already written.

[§5.5]

11. Step-transform hooks

Step-transform providers change messages when they are written, not every time history is sent. Within a turn: the assistant message completes, PostAssistant runs and is written; then for each tool call PreTool, the tool, PostTool, written. When a user message or notice arrives, PreUser runs and is written [§6.1].

[§6.1, §6.3]

Operations, not values

PostAssistant, PostTool and PreUser return prepend(text), append(text) or replace(value); Broca applies them.

  • Allowed operations. Each tool declares which its results accept; default all three. AFT's read and bash accept prepend and append only: a later edit addresses read's hashline tags, and AFT's line tags must survive a renderer rolled back to a build without hooks. Broca sets the rule for PostAssistant and PreUser. A disallowed operation is refused before it's applied, and recorded.
  • Stacking in manifest order: prepends stack outward, appends in order, a replace sees the value as it stands then.
  • Attribution is the operations themselves, each with its module and an optional short note. A UI shows original, final and the list. No diffing.

[§6.2]

One frame, applied once

  • The final value lives in the record's existing rendered field, so a Broca rolled back to a build without hooks still renders the right bytes. Original and attribution are new fields.
  • PreTool needs no original field: the model's input stays in ModelStepFinished.assistant_message. ToolDispatchIntent holds the input that executes, which at-most-once execution depends on.
  • Every edit is applied before the message's first send and never changed after.
  • A crash before the frame syncs loses the hook output with its subject. Resume re-runs that step's hooks; it doesn't replay a guess or stop for review.

[§6.3]

Order, budget, failure

  • Several providers on one hook run in manifest order, each receiving the previous one's output.
  • Each declares a per-hook time budget in its manifest, capped engine-wide. A hook that fails or times out passes the message through unchanged, recorded.
  • PreTool is the exception. Each PreTool provider declares on_unavailable: pass | refuse, default refuse, applied on a timeout or any failure. pass runs the model's input; refuse returns a typed "pre-tool hook unavailable" refusal as the result. Only the provider knows if its hook is enforcing, and an executed call can't be undone.
  • PreTool changes only what executes; the recorded assistant message keeps what the model produced.

[§6.3]

Everything else

  • PostAssistant and reasoning. Text only. Whether a family accepts edited text next to reasoning is the runner's concern. The display lane already streamed the original; subscribers get the final on the control lane.
  • Reading history. session.read(from, to) returns any range with raw and final forms: after a restart, for the provider's own history work, to recover originals.
  • Wakes and nudges. The provider tells them apart itself, for example by their <system-reminder> wrapping. Broca doesn't classify turns.
  • The runner's own edits (Broca's repetition guidance, a PostTool append) are ordinary recorded operations. Resume never reconstructs them.

[§6.3]

13. Tool calls and notices

Tool calls

  • Params. Each call carries the params the provider was preflighted with, so behaviour matches the frozen description.
  • Pinned revision. Each call carries a digest of the input schema it was described with, plus a semantics version. Description text isn't pinned, so a description-only deploy keeps serving old pins. A provider refuses only when it can no longer honour the schema, with tool_revision_mismatch, which SDKs treat as terminal. Argument changes stay additive.
  • Settings flipped mid-session. A setting that changes description bytes (AFT's bash.background, github.write) stays frozen until a change is applied. Meanwhile the provider refuses by name any call the current config forbids.
  • Host-only arguments are rejected in calls from the model, and refused from any caller that hasn't declared it supplies them. The agent credential is one; the runner adds it at dispatch.

[§9]

provider_notice

  • Asynchronous events: AFT's finished background task, Magic Context's idle nudge. Sent with a per-event id.
  • Written as a user-role message tagged with its provenance, at the next legal position, never between a tool call and its result. It passes through PreUser and can later be compacted.
  • Durability. The provider holds a notice until Broca acknowledges it; Broca acks only after the frame is fsynced. The provider resends un-acked notices, and Broca dedups by event id, so a redelivery after a crash is written once.
  • One engine-wide size cap, published as a number. An oversized notice is refused back, never truncated.
  • Whether an idle session wakes for a notice is Prefrontal's decision, outside this design.

14.1 Detection

  • Watch set. The global configuration plus the configurations of roots the provider has a live session route for. supervisor.live_roots seeds it at start; after that the provider tracks its own binds and closes, and drops a root's watches when its last route closes. A missing file is watched through its nearest existing parent. Roots that were only preflighted aren't watched; turn-start re-preflight covers them.
  • Preflight routes are not session roots. subc has no rootless route and live_roots doesn't distinguish targets, so Prefrontal opens preflight-only routes against the CK data home, never a project, and providers leave them out of the watch set.
  • The hint is {scope, generation, boot_id}, with no content. scope is the entorhinal project id, never a path. The subject is named in the commons naming crate. NATS doesn't tell a subscriber who published, so the module id is trustworthy only because each module's grant lets it publish solely on its own subject. Today's participant grant publishes no workload subject at all, so this needs a commons grant change and a ck-bus release.
  • Correctness never depends on the bus. A public install may have none. A missed hint only delays detection.

[§11.1]

14.2 Policies

Prefrontal picks the policy per class: masons and readers default to next_prefix_rebuild (short-lived, never worth a bust); heads to next_soft_bust, with the pending change shown on the board and phone. Broca works out what changed from the per-item digests [§11.2].

14.3 The append capability and the fold model

Each route has one capability the caller sees: can it apply a mid-session tool or instruction change without rebuilding the prefix? Yes or no. The runner reports it once, at admission, derived from the frozen (provider family, model). It never changes mid-session, because a model switch is a fold anyway. How a runner decides it is in the runner's own spec; Broca's per-family table is in its research note append-capability-by-family.md [§11.2].

  • Why appends are dropped at a fold. Keeping one would, for example, add a tool that's already in the tool list, which a family may reject. The rebuild changes previously sent prefix bytes, which the runner handles (section 15).
  • Placement. Only right after a user turn (tool results count) and before an assistant turn, never between a tool call and its result; the renderer enforces this. Only operator text rides this carrier, never recall or tool output.
  • Presets declare tools up front, so most later changes narrow the toolset rather than add to it.
  • Recorded. An append is an ordinary transcript entry. A fold writes one WAL entry, prefix_rebuilt{manifest_digest, step}, behind the reader gate, with whatever the runner strips in the same record. Resume uses the latest fold as the frozen prefix and replays the appends after it.
  • A change that never finds its moment stays pending. Prefrontal can show it and flush.

14.4 Flush and disabled tools

session.flush_prefix drops the frozen prefix and applies any pending manifest on the next step, whatever the policy. It backs the Desktop flow: "toolset changed, applies on next bust", then Apply Now, then a warning that the cache will be rebuilt, then continue. Apply Now is a Prefrontal op that calls session.flush_prefix; Desktop and phone go through Prefrontal and never talk to Broca directly [§11.3].

15. Runners: Broca and Thalamus

The runner's obligation. The runner makes every rendered request valid for its model family, including reasoning-validity rules when the prefix changes. Those rules live in the runner's own spec, not in this protocol. Compaction and hook providers need not know them [§12].

Two parts are protocol-level:

  • Prefix changes are known. A CompactionMessage and a prefix_rebuilt change previously sent prefix bytes. The runner is told which positions changed: a CompactionMessage's range compared with the last one sent, or the fold's step.
  • Strips are recorded. Whatever the runner strips in response is written durably in the same WAL record as the event, so resume reproduces it.

15.1 Broca

Broca is the first runner. It owns its transcript, keeps everything in its WAL, and is the subject of most of this page. Its own spec holds the per-family validity rules and live tests, its per-family append table, and the prerequisites for appends, including its renderer split. Until those land every Broca route reports append capability "no" [§11.2, §15].

15.2 Thalamus

Thalamus uses the same interface and is the runner for Claude Code sessions. Claude Code owns its transcript and resends the whole array on every request. The design lists only what the protocol sees; the rest is in Thalamus's own spec. This is THALAMUS's first read, dated 2026-09-26 [§12.1].

  • Identity. Records are keyed by ccm-N: ordinals the gateway's message-id store mints, stable across resends and hook cuts. ccd/v1 is only the join key to Claude Code's JSONL rows.
  • Hooks. By the time a request shows a tool call, the tool has already run, so the gateway can't do PreTool itself. Claude Code's own hooks carry most hooks, and their outputs land in Claude Code's transcript, which serves as the WAL for them. Probed live on Claude Code 2.1.282:
Interface hookCarried byNotes
PreUserprompt.submitA text rewrite works, but the transcript keeps only the rewritten text. context blocks work too.
PreTooltool.callAn input rewrite works; the transcript keeps the model's input and the tool runs the rewritten one. A deny reaches the model as a <tool_use_error> result.
PostTool appendtool.call, nativelyStored as its own hook_additional_context record, rendered as a separate <system-reminder> after the result.
PostTool prependthe gateway, on each resendNative only per tool: works for Bash, lands inside line 1 for Read, untested for MCP tools. So the gateway applies it, keyed by ccm-N.
PostAssistantthe gateway, on each resendNot expressible natively (turn.complete's rewrite doesn't reach the stored message).
Attributionthe hook itself, or MC's storeClaude Code keeps neither the original of a PreUser rewrite nor the executed input of a PreTool rewrite, so these are recorded by ccm-N.
  • tool.call hooks run concurrently for parallel calls, so per-session hook state must tolerate concurrent writers.
  • Status also carries the new messages since the last step, by ccm-N, so the provider doesn't depend on JSONL, whose lead or lag against the wire is unmeasured.
  • The latest CompactionMessage persists in Thalamus's store per key, fenced by the monotonic version. On a timeout Thalamus serves it plus the raw tail. With nothing recorded and the provider unreachable, it returns 503, never raw. If a new one fails validation and the previous one no longer applies (the raw tail changed underneath it), it refuses with 503. "Proceed with the previous one" never means "forward raw".
  • Resend rules. A missing from is valid only when a hook cut removed everything before the kept head. A missing to is a 503, never a guess. Side requests (title, token counting, spinner subsets) never call the provider and never get the replacement. session.compact cuts at the latest from, snapped earlier to a clean point.
  • WAIT holds the HTTP request. bound_ms is capped at 120 s here, the longest hold calibrated so far. The user sees only the spinner. Claude Code resends after a 503, so a resend whose newest ccm-N matches the waiting step is the same step: the cap covers the step, not each request.
  • REFUSE is a 503 today, which Claude Code retries about 12 times over roughly 180 s. What Claude Code shows for a permanent refusal is unmeasured, so user-facing refusal text here waits on that measurement.
  • Provider errors across retries are kept per key, so the next step's status carries them.
  • Reasoning validity. Thalamus asks the provider to drop failing blocks on every qualifying turn. It strips nothing itself, so there is no strip record, and every resend carries the same control.

16. The reader gate and other carried-over rules

Carried over from r2 unchanged: operator text is static and never interpolated per session; recalled content, tool output and notices are user-role, never operator authority; host-only arguments are rejected in model calls; nothing activates implicitly on the next send [§13].

Why today's WAL decode can't carry new records

  • WalRecord::Unknown drops the payload;
  • a new value in a closed enum fails serde and makes the whole WAL Corrupt;
  • new fields on known kinds are silently ignored;
  • RECORD_SCHEMA_VERSION is inert.

The mechanism: a new frame ver

Every deployed build already refuses an unknown ver before digest and decode, with a named error ("unsupported WAL framing version 3"). The digest covers ver. From the gate build on, readers return a distinct NewerWriter{ver} step that no tooling repairs. Older builds report the named Corrupt, which is safe because nothing auto-repairs corruption.

Coverage and floor

  • Covers new kinds, new values in known records and new fields on known kinds: CompactionMessage, manifest_pending, prefix_rebuilt, strip records, appends, compaction_wait, notices, hook fields. ModelAttemptFinished stays skippable; TransformUnavailable stays decodable.
  • Refusals are Error + provider_code, never a new enum value.
  • "Ships" means confirmed on the running Broca image, not a merged commit or a lock.
  • Each WAL carries a writer and high-water stamp. Rolling Broca back below the floor it names is blocked, and the rollback card names that floor. This holds for every Broca that might resume a WAL: one per machine today, to be restated before WALs travel with federation.
