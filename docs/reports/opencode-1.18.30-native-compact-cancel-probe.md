# OpenCode 1.18.30: can a plugin cleanly cancel native compaction?

**No.** Throwing in `experimental.session.compacting` prevents the summary model call and leaves the effective history un-compacted, but the native summarize endpoint reports **HTTP 200 `true`**, persists a compaction request **and an errored summary assistant**, and emits `session.error`. It is an error-producing veto, not a clean cancellation. Do not ship it as a quiet `/compact` redirect.

### Manual `/compact` equivalent

Created two ordinary user turns with `POST /session/{id}/message` and received two normal mock assistant replies (`finish:"stop"`). Then called `POST /session/{id}/summarize` with `{"providerID":"mock","modelID":"tiny"}` (the route used by TUI `/compact`). In session `ses_f22f5c990ffeRJk4xY65Yhf4L8` it returned **200 `true`**, not an HTTP failure or a hang. The hook marker recorded this session. Immediate `GET /session/{id}/message` returned exactly six rows: two user text rows, two finished assistant rows, one user row containing `{"type":"compaction","auto":false}` with no `tail_start_id`, and a summary assistant row (`summary:true`, `finish:"error"`, `error:{"name":"UnknownError","data":{"message":"PROBE_COMPACTION_CANCEL"}}`, no parts). There was no summary text and no summary-provider request. The same row state was observed in the first manual session `ses_f22f76711ffeybD8PtaV3oVMQW`. **Important discrepancy:** tagged `compaction.ts:372-419` calls the hook before its explicit assistant creation, yet the running host records an errored assistant; do not assume a hook-time deletion can safely eliminate every row on this binary.

A subsequent real prompt in the first manual session returned HTTP 200 and an ordinary build assistant (`finish:"stop"`, `"Mock response."`); mock requests numbered three for the two pre-compact and one post-compact turns, and the hook fired only once. The dangling request was **not** retried on each later loop. A separate SSE `GET /event` observation during auto compaction captured `session.error` with the same `UnknownError`. The TUI `/compact` action discards the summarize promise (`void`) and clears the dialog, without a `.catch` toast (`packages/tui/src/routes/session/index.tsx:561-585`); the global `session.error` listener *does* show an error toast for non-abort errors (`packages/tui/src/app.tsx:1018-1029`), and the errored assistant renders an error box (`packages/tui/src/routes/session/index.tsx:1533-1546`). Thus SDK/HTTP sees a **misleading success**, while the TUI should show an error toast/message rather than the proposed friendly guidance (toast inferred from listener, not visually verified in interactive TUI).

The loaded window retains the old turns, not a compaction boundary: no successful, finished summary exists and the compaction part has no `tail_start_id`. `filterCompacted` only registers a summary assistant when `summary && finish && !error`, and only stops at a *completed* compaction user row (`packages/opencode/src/session/message-v2.ts:521-575`). The hook never reached prompt conversion or a successful boundary (`packages/opencode/src/session/compaction.ts:372-419,461-465,552-556`). This is established from the stored rows plus the source filter; the model window was not separately instrumented byte-for-byte.

### Auto-compaction

Restarted the same scratch mock to report 15,510 tokens per normal answer against a 16,000-context/1,000-output mock model, `compaction.auto:true`. Session `ses_f22f52826ffevIftorNbYG2GM2` first user prompt returned HTTP 200 with an **errored compaction assistant**; store contained its ordinary completed user/assistant turn, followed by `compaction` user part `auto:true` and summary assistant `finish:"error"` / `UnknownError(PROBE_COMPACTION_CANCEL)` / no parts. The next real prompt generated another ordinary mock reply and **another new auto compaction request/error pair**; it did not retry the old row. The repeated attempts here are expected because the mock **always reports over-limit usage**, not because the dangling first request is picked up. The auto-continue probe marker was never created: `experimental.compaction.autocontinue` runs only *after successful processing*, not before it (`packages/opencode/src/session/compaction.ts:468-554`). SSE `session.error` was observed during the auto run; no hang or HTTP error occurred.

Source explains both paths: `prompt.ts:1092-1096` loads filtered history and identifies pending tasks via `MessageV2.latest`; `prompt.ts:1141-1159` processes a compaction task and `:1161-1168` creates auto compaction after over-limit prior usage. `message-v2.ts:582-597` ignores task parts at or before the last **finished** assistant, including the errored summary row, so the old marker does not replay. The streaming processor sets `needsCompaction` on overflow, with an `auto:false` guard for non-summary assistant overflow (`processor.ts:613-630`), returns `"compact"` at `:641-695`; `prompt.ts:1319-1329` creates a fresh auto row. `overflow.ts:22-34` checks the resolved `compaction.auto` and token threshold. If native auto is inadvertently left enabled, a veto can keep producing visible errors and extra rows as usage remains high.

## Cleanup / alternatives

- `experimental.session.compacting` has only `context` and replacement `prompt`, no cancel output (`packages/plugin/src/index.ts:298-308`). Throwing is not a supported cancellation signal. The summarize handler creates the compaction user row, calls `promptSvc.loop`, and returns `true` (`packages/opencode/src/server/routes/instance/httpapi/handlers/session.ts:273-293`).
- `experimental.compaction.autocontinue` toggling `enabled:false` cannot prevent the compaction; it runs only after a successful summary, immediately before a synthetic *auto-continue* turn (`compaction.ts:468-554`), and does nothing for manual `/compact`.
- The scratch plugin's `command.execute.before` marker was not created on direct summarize. TUI `/compact` calls `sdk.client.session.summarize` directly (`packages/tui/src/routes/session/index.tsx:561-585`); the hook belongs to the separate prompt command path (`packages/opencode/src/session/prompt.ts:1356-1368,1461`). It cannot intercept this built-in action.
- `session.compacted` is published only after a successful summary (`compaction.ts:552-556`), hence cannot clean up this failed attempt. `message.updated` fires at message creation, **before** its compaction part is appended (`compaction.ts:566-581`); relying on it to delete the request races both part creation and the running loop. `message` deletion requires the session not be busy (`handlers/session.ts:380-387`). After failure/idle, the *supported* `DELETE /session/{id}/message/{messageID}` returned 200 `true` for both the compaction user and its error assistant in scratch session `ses_f22f5c990ffeRJk4xY65Yhf4L8`, leaving the original four turns. That is possible **postfactum cleanup**, not an atomic clean cancel: the user has already seen an error, the summarize caller has seen success, and asynchronous event cleanup would require safely pairing IDs and waiting for idle. Direct DB edits are not advisable.

**Recommendation:** retain `compaction.auto:false` as the primary prevention and explain that native manual `/compact` cannot be cleanly overridden by the server plugin in 1.18.30. A proper friendly redirect (e.g. “Magic Context manages this session's history; use /ctx-wrapup instead”) needs host/TUI support to intercept the built-in action *before* the summarize endpoint creates rows, or a native cancellable pre-compaction hook with explicit successful cancellation semantics. No plugin-source change was made.
