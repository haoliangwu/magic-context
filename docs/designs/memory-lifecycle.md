# Project memory lifecycle — r2

**Status: proposed; no runtime or schema change is made by this document.**
Original code citations refer to `6b1b55cd8052d90d847bcda564edf0fc7e6f36e2`. Review-response source checks were made at `99ae86b1eb7a30cd119d1ddae7ef0e92a0115d99`; new source citations below use that snapshot. Trial results are observations on copied stores, not a census of every installation or permission to mutate a live project. Proposed contracts below are requirements, not claims that the runtime already implements them.

## Decision in brief

Keep compartments as the dated episodic record and source of evidence. Make project memories independently useful claims with citations and non-destructive revision history. Do not mistake a syntactically valid rewrite, a high similarity score, an old date or a search count for proof.

**Decided first-release scope:** verification results reach the memory row; anchored candidates survive in a durable pending queue; every writer uses one revision/evidence applier; historian turn one omits the memory block, followed by a **shadow** `new / covered / abstain` reconcile turn; and a usable fleet approval inbox. Keep the revision journal and the cache projection. Completing these foundations is not permission to activate the whole lifecycle.

**Decided authority:** rewrites, merges, replacements, retirements, restore conflicts and promotion to standing rule require approval of the exact revisions. An agent save is not permission to mint an immortal instruction. Semantic coverage and new admissions stay shadow by default; they need their own quality gate and explicit opt-in. Existing auto-promotion opt-outs remain effective.

**Decided clock and surface:** freshness uses project activity, specifically distinct compartment publications since reinforcement, not calendar time. Three idle weeks lose nothing. Keep the heuristic in shadow until replay beats importance-only selection. Keep last-used, last-observed and last-verified separate. Approvals live in one dashboard inbox across projects, grouped by topic with scheduled digests—not slash commands or interruptions on every turn.

**Deferred:** automated transitions, usage-driven freshness, periodic rescoring, weighted mural policy and broad event re-anchoring, each behind its own measurement. Bulk backfill is also deferred unless its complete projection barrier is specified and tested. The later attention experiment is **weight = importance × activity freshness**, adopted only at an independently required rebuild; background work must never create that opportunity. Replaced knowledge leaves ordinary search but remains available through deliberate history/restore.

**Vocabulary:** a compartment is a saved episode summary; P1 is its fullest narrative, with P2–P4 progressively shorter versions. `m[0]` is the frozen prompt baseline and `m[1]` its saved additions/corrections. A HARD fold rebuilds that baseline; a SOFT refresh updates only the delta on an already-authorized rendering opportunity; a defer replays both unchanged. “Shadow” means recording proposed decisions without applying them. The cache analysis below spells out which opportunities are legitimate.

## 1. Setting and current state

### The setting we are designing for

The operating assumption is **one long-lived conversation per project/scope**, with its complete dated compartment history. This is not a plan to aggregate fragments from unrelated short sessions. A scope still needs a canonical project identity, an owning conversation and a harness: the existing visibility policy already separates owned project rows from shared workspace rows (`packages/plugin/src/features/magic-context/memory/memory-visibility.ts:57–108`). This assumption is not a database constraint enforcing one session per project; backfill must enumerate the actual registered histories and report departures from it.

Compartments are the episodic layer; memories are claims extracted from that layer, not another event log. Today the historian prompt already distinguishes event narratives from durable world knowledge (`packages/plugin/src/hooks/magic-context/historian-prompt.source.md:23–46`). Evidence references should carry a compartment identity **and** a session/harness-qualified ordinal range. At this base `ctx_expand` accepts message ordinals/ranges, not a compartment-id argument (`packages/plugin/src/tools/ctx-expand/tools.ts:26–40,73–139`). A displayed compartment citation must therefore resolve to `ctx_expand(start=…, end=…)`; opening evidence from another scope needs an authorized scope switch or an explicit evidence-reader API, not an invented tool argument.

The operator recalls studying Hindsight in May. The checked-in comparison is dated September, not May (`docs/reports/memory-solutions-comparison.md:3–13`); it corroborates observations with proof counts, source IDs and change histories (`:66–80`). Borrow that **content shape**: evidence-backed claims, freshness trends and recorded transitions. Do not borrow its bank/service topology, per-prompt recall, global graph or cross-session consolidation assumptions. Freshness trends in this design are derived from reinforcement records, not claimed as an already implemented Magic Context feature.

## 2. Goals and non-goals

**Goals**

- Admit independently useful claims; reconcile paraphrases and changed values without erasing still-valid constraints.
- Make the evidence, origin, current truth, revision history and degree of re-observation inspectable.
- Keep standing instructions until explicit revocation; measure activity freshness in shadow without changing attention in the first release.
- Make later legacy repair possible with consent, resumability and undo; do not launch bulk repair in the first release.
- Preserve frozen provider-visible bytes on defer paths in TS OpenCode, Pi and Rust, including mixed memory authority.

**Non-goals**

- Recompacting or rewriting compartment narratives, raw coordinates or original messages as part of memory repair.
- Cross-project learning, a global knowledge graph, per-turn model retrieval or short-session aggregation.
- Treating importance as truth confidence, enforcing a score histogram, or retiring something merely because it is old or unused.
- Using search counts as a popularity-based permanent promotion system.
- Repairing every unsupported host's inference/tool capabilities in this feature. Refuse unavailable operations clearly and retain pending work.

## 3. The model: claims, evidence, classes, weight and tiers

### Memory and evidence records

A live memory has current text, category, ownership/visibility, importance and review provenance. Add a monotonic content revision for compare-and-swap (CAS): a decision applies only to the exact revision it read. The immutable revision journal is the **sole authority for history**; any UI history array is derived, not a second editable truth. Evidence applicability and unique observation keys determine proof totals, maintained transactionally and checked by audit. Reuse `first_seen_at`; do not invent another first-seen field. Nullable class/rubric metadata can support shadow evaluation, not an active decay policy.

Store individual evidence records as well as their summaries. A reference contains canonical project identity, scope/session, harness, source compartment ID if valid, ordinal endpoints, native endpoint/block identities where available, evidence hash, source kind, observation time and certainty. Keep event IDs as optional provenance, not as the only citation. Imported creation dates are not necessarily event dates: the rescore report documents import timestamps (`docs/reports/compartment-rescore-trial.md:84`). Unknown dates stay unknown; never infer a precise first occurrence from an import date.

Evidence uniqueness is by original observation lineage, not retry/apply timestamp. Preserve native message/block identity, original range and source hash through recomp, import and re-publication, plus publication/fact IDs for attempt deduplication. Those attempt IDs alone cannot distinguish a copied observation. Store `independent_observation`, `recitation`, or `unknown_lineage` with the reason and claim applicability. Copies of injected text, agent citations of that text, retries and duplicate citations add no proofs or evidentiary reinforcement. Uncertain lineage stays pending/inspectable, not optimistically independent. Repeated real work can count as an observation without being statistically independent; `proof_count` is an auditable count, **not a posterior probability**.

### Four classes

Classes are orthogonal to the existing five content categories (`packages/plugin/src/features/magic-context/memory/constants.ts:9–29`). The second turn proposes a class; classify reviews it against origin evidence.

| Class | Eligibility and examples | Decay and exit |
| --- | --- | --- |
| **Standing rule** | An explicit user instruction or saved operating rule, with original evidence **and revision-bound promotion approval**. An agent save only proposes this status. | Constant shadow freshness. Leaves only through explicit evidenced replacement/revocation with approval; code change or silence cannot revoke it. |
| **Structural fact** | Architecture, configuration semantics, external limits, naming decisions or mechanisms with continuing consequence. Include harness/version/environment applicability. | Candidate for a longer **publication-count** half-life in shadow; no active decay in the first release. |
| **Situational fact** | Changeable state that affects continued work: temporary constraints or provisional configuration. | Candidate for a shorter **publication-count** half-life in shadow. Preserve actual validity/expiry evidence; a plan is not an accomplished fact. |
| **Episode** | Something done, investigated, released or measured without an independently reusable claim. | Not a live memory. Retain it in the compartment evidence layer; archive legacy episode-memories after reviewed backfill. |

These are provisional vocabulary, not a validated decay model: episode is an admission disposition, standing rule an authority/revocation policy, structural/situational volatility assumptions. One enum cannot determine truth, visibility and attention. Half-lives and review cutoffs await replay calibration. Splitting mixed rule/state text changes claims and requires approval; never assign an average class to avoid that review. Unknown-origin legacy rules remain unchanged pending origin review.

Existing category TTLs are a separate legacy policy: the promoter sets `expires_at` for some old categories (`packages/plugin/src/features/magic-context/memory/constants.ts:65–70`; `promotion.ts:36–39`), and loaders hide expired rows using a live or frozen cutoff (`storage-memory.ts:693–711`). New lifecycle admissions must not translate a class half-life into `expires_at`. Review legacy automatic expirations during backfill; preserve an explicitly evidenced validity deadline as claim metadata, and require stale review rather than quietly expiring a standing rule. Do not blindly clear operator-authored deadlines or count expiry as proof of contradiction.

### Reinforcement

Keep three signals separate, with occurrence dates **and** project activity ordinals:

1. **Last-observed:** grounded work evidence for named claims. `covered by #N` means N entails the candidate; it does **not** mean that observation confirms every clause of N. A repeat of “uses SQLite” cannot refresh “uses SQLite and must preserve protected region X.” Partial coverage attaches evidence only to the matched claims. Row-wide reinforcement is allowed only for reviewed atomic/equivalent claims or evidence covering every current clause. In the first release semantic coverage is shadow, not an automatic freshness write or a terminal discard of the candidate.
2. **Last-verified:** a genuine check of specified current claims, backing files and commit. Mapping, skipping, an unsafe-update refusal or `still_true` fallback is not confirmation. Unchanged confirmations may apply automatically through the shared applier; changes require approval.
3. **Last-used:** scoped citation/consumption telemetry. A returned hit is not use; an agent reciting its injected prompt is not new truth evidence. Usage-driven freshness is deferred, so this signal does not advance the evidentiary clock.

For a shadow row-wide weight, the reinforcement ordinal is the latest accepted observation/verification that supports **all** current claims. Otherwise retain claim-level ordinals and leave the row-wide value unchanged/unknown. Keep evidence occurrence time separate from apply time; backfilled old evidence does not become fresh today. Classify and cue compression never reinforce. Corrected revisions inherit only proofs explicitly applicable to their surviving claims, not proofs of the false value.

Search counts alone are specifically excluded: today explicit search increments telemetry, automatic hints do not, and the bump is skipped under module authority (`packages/plugin/src/features/magic-context/search.ts:2258–2281`). Memories already injected may never be searched. Detect structured scoped citations outside quoted/tool data, deduplicate use records, and do not let a generated transcript repeat reinforce itself.

### Importance and freshness

**Importance = consequence of not knowing × breadth of applicability**, assessed by a calibrated review rubric. Store an integer on the existing importance scale; the rubric maps severity and breadth judgments to that scale rather than multiplying two arbitrary model-emitted numbers. Missing a safety constraint is consequential even if it is short; large implementation effort does not imply high importance. Truth uncertainty belongs in evidence/verification state, not a disguised importance discount.

Importance is stable between explicit reviews. Repetition and age do not change it. Periodic rescoring is deferred pending a blind fixed-text memory trial. The later shadow attention heuristic is:

```text
age = max(0, captured_project_publication_ordinal - full_claim_reinforcement_ordinal)
freshness = 1                                      for a standing rule
freshness = 2 ** (-age / class_half_life)           otherwise
weight = reviewed_importance * freshness
```

**Clock chosen: distinct compartments published for the canonical project**, across its registered histories, not raw message ordinals. Message counts vary with harness/tool chatter; compartments are the common durable unit of processed project work. This is still an approximation: publication granularity varies, so replay must test that bias. Increment a project-owned monotonic counter once per genuinely new work compartment publication, with an idempotent publication key; recomp, retry, historical import, restore and repair do not increment it. It is not a session-local sequence that can reset. Evidence records capture the project's ordinal at observation/check; original lineage keeps its original ordinal. No publications during a three-week hiatus means age is unchanged.

Capture one ordinal and policy version per shadow replay/natural fold, not a live timer. Unknown legacy reinforcement remains unknown and uses importance-only selection; neither migration nor repair makes it newly fresh. Half-lives are in publication units, with no chosen numeric values yet. Compare importance-only, publication-clock freshness and explicit validity/change signals on dormant projects, never-reencountered negative constraints, scoped facts and standing-rule saturation. Activate only if held-out replay improves useful-claim retention/retrieval without losing safety constraints; publish the metric and chosen parameters before activation.

Compartment decay is a useful cache pattern, but a different clock: current compartment decay uses distance from the newest compartment and importance-dependent half-life, not elapsed wall time (`packages/plugin/src/hooks/magic-context/decay-curve.ts:27–64`). Do not describe it as the same time-based algorithm.

### Attention tiers

**Later measured policy, shadow only in r2:** at a natural HARD, project eligible revisions and make one deterministic selection shared by text and mural. First release keeps the existing selection policy, but fixes its captured revision manifest (§7); it does not activate weighted mural selection.

| Tier | Selection policy | What remains available |
| --- | --- | --- |
| Full text | Highest-weight eligible claims that fit the text budget; admit whole facts, not truncated rules. Protected standing rules are considered first. | `#id` and actionable current prose in `<project-memory>`, with compact evidence links where useful. |
| Mural cue | Remaining claims above a calibrated cue-worthiness floor that fit the image/cue budget and have current cues, on a vision-capable model. | Short cue plus ID; ordinary search/expansion supplies the full claim. |
| Search-only | Low-weight claims, missing/stale cues, image overflow or a non-vision model's unselected claims. | Full current text in search; no deletion and no superseded “cold copy.” |

No fixed tier cutoff or new budget is justified by the listed trials. Retain the configured text budget during shadow replay. The promotion report calls **8,000 tokens** the default (`docs/reports/historian-memory-promotion.md:104`); that is the renderer's fallback (`packages/plugin/src/hooks/magic-context/inject-compartments.ts:1131`), **not the schema's configured default of 4,000** (`packages/plugin/src/config/schema/magic-context.ts:1477–1483,1559`). The hook threads the configured value (`hook.ts:1085–1086`). Additive m[1] admission uses **25%** (`inject-compartments.ts:2955–2964`). Calibrate cue floors from served prompts, not counts. The later total selection order is approved standing priority, weight descending, full-claim reinforcement ordinal descending (unknown last), then numeric ID ascending; category only orders presentation. Equal-ordinal fixtures must match TS/Rust. Current TS returns equality for equal non-null reinforcement timestamps (`memory-selection.ts:36–43`), so ID ties need an explicit contract rather than input-order dependence.

Never-decaying does not mean unlimited prompt capacity. If protected standing rules exceed the budget, report an explicit capacity problem and require review/budget choice; do not silently replace full instructions with ambiguous cues. Decay does not archive. Long-unreinforced, low-weight rows only enter the stale-review backlog.

## 4. The historian write path

### Turn one: episodic extraction without project memory

Remove `<project-memory>` from the first-turn input and remove instructions to deduplicate against that absent block. Keep the transcript guard, examples, continuity references, tiered compartments, boundary validation and fact-extraction rubric. Ask for candidate facts with source-compartment/range anchors and observed origin, including an explicit “no memory; episode” disposition. The TS parser currently emits only category/content fact pairs (`packages/plugin/src/hooks/magic-context/compartment-parser.ts:390–406`), while Rust accepts optional compartment anchors (`crates/mc-module/src/historian_validate.rs:360–409`). Extend both contracts; never guess source attribution when a tail was discarded.

Do not change chunk sizes or force a compartment count. The independent prompt-fit and boundary rules remain authoritative. The fresh paired control is now complete (§1); it fixes the earlier historical-answer confound but shows changed selection, not proved durable recall. Switch extraction only with durable candidate capture and an omissions review using the full-memory-only families as controls. Do not describe removal as a token-only optimization.

### Turn two: same-session reconcile

Append the reconciliation request to the **same hidden session/lineage**, retaining the first prompt and reply as preceding roles. Reuse the model/system/profile for the attempt and measure actual cache hits rather than assuming them. Skip inference when no candidate facts exist; still record successful empty extraction. A resumed pending fact can use a later run's second turn, but must be labelled with its own original evidence, not attributed to the later transcript.

Retrieve candidates from the full current eligible **owned project** memory pool, not only injected text. Shared foreign memories may be read for context under visibility policy but cannot be mutated or used as a sole owner-local coverage target. Use compatible compartment/memory embedding identities and a lexical lane; absent/incompatible embeddings fall back visibly to lexical retrieval, not silent no-match. Similarity is a retrieval aid, never a verdict.

Use the v2 readable ranked layout: a heading per fact; complete candidate text; IDs, category, origin, age and lane/rank metadata; no implicit correctness claim from a score. Reserve a **dedicated distinct lexical candidate slot** before filling ranked slots. Do not truncate a long memory to fit; reduce batch/candidate count with an explicit coverage warning. The trial's top-eight reduction is not the recommended production shortlist (`docs/reports/historian-merge-turn-trial-v2.md:15–22,64–66`). Exact shortlist capacity/lexical allocation remains a new trial, not a measured optimal number.

**First-release wire:** `new`, `covered` with target revision and claim mapping, or `abstain` with reason. All are shadow decisions; pending candidates are not consumed merely because the model says covered. Conditions, negations, fallbacks, bounds, keys and exceptions are claims too. Transition proposals authored by other writers/inbox review use the wider applier vocabulary below, but the historian does not acquire rewrite authority. Later transition inference must inventory exact target clauses, mark kept/removed claims, and evidence each removal. A compatible observation or workaround is not contradiction.

| Decision | Durable effect |
| --- | --- |
| `new` | Shadow candidate for an independently useful claim, with origin/citations. Only approval (or separately measured opt-in admission) creates the row. Exact-hash checks remain a concurrency defense, not semantic approval. |
| `covered by #N` | Shadow claim mapping: N alone entails the fact. Approved evidence attaches only to applicable clauses; partial coverage does not refresh all of N. Joint coverage stays pending unless explicitly mapped/reviewed. |
| `abstain` | Retain the candidate and reason in pending review; never convert uncertainty or malformed output into an automatic new row. |
| `merge` | With approval, refine a coherent facet preserving all still-valid claims. Retain the nominated survivor ID; archive other sources with successor pointers and journal links, not copied editable histories. |
| `update` | Keep the target ID and revise the same property's state; preserve its unrelated claims and append a state-update history entry. |
| `replaces` | Create a **new successor row/ID**, archive the old row(s), and link immutable revisions. Same-property `update` keeps its ID; replacement is not an ambiguous choice between revision and row. Revocation with no surviving claim is an audited archive, not an empty live memory. |

The wire may use a structured `covered` action and integer target ID; `covered by #N` is its human-readable form. Keep decisions separate from prose and correlation IDs. Validate each fact independently: unknown/duplicate fact IDs invalidate that fact; a valid sibling shadow decision can be recorded. An unparseable envelope leaves all unresolved facts pending. Never infer integer indices from text, silently repair IDs, or convert every valid sibling to `new` because one entry is malformed.

### Agent-written memories are classified by the next historian run

A memory an agent saves with `ctx_memory` keeps its text and is never rewritten by this step. It does not get a source-based starting importance. Instead, every agent-written memory created since the session's previous historian run is listed in the next run's second turn, as a classification-only item: the historian assigns importance with the same rubric and proposes the decay class, judging from the transcript around the save (which turn one already reads, including the `ctx_memory` call through `historian.expand_tools`). This replaces the source-ranking idea in issue 579 (decided by the operator, 2026-10-06): who wrote a memory is provenance, not a priority.

- **Text is untouched.** The item carries the saved text and its save context; the only outputs are importance and a proposed class, plus `covered by #N` if an older memory already states it (a reinforcement of #N and a duplicate proposal for the inbox, never an automatic archive).
- **Standing rule still needs its evidence.** The historian may propose `standing rule` only when the transcript shows a user statement or an explicit instruction to save one. An agent save alone is not that evidence (see the authority section).
- **Until classified,** the memory keeps today's default importance and has no decay class, so freshness selection treats it as importance-only. A memory saved after the last run of a session that never runs the historian again stays unclassified; the later backfill covers those.
- **Cache:** importance and class are attention metadata. They reach the prompt only through the projection rules in section 7 (adopted on an independently required rebuild), like any other score.

### Gates and publication

Port the v2 deterministic token/evidence gate from investigative code into a shared contract: preserve backticked identifiers, paths, refusal codes, quantities/units and named keys unless the exact containing claim is explicitly replaced with verbatim evidence **from the actual source transcript**, not examples/candidate memories (`docs/reports/historian-merge-turn-trial-v2.md:17–20`). Treat stored/model text as untrusted data, not instructions.

This gate is necessary, not sufficient. A valid quotation does not prove contradiction, and a surviving numeric token in historical prose may still lose its operative meaning. Keep transitions approval-gated; later automation would require independent held-out preservation/contradiction review, including detach-guarantee and workaround-versus-API-gap failures (`historian-merge-turn-trial-v2.md:68–99`). A rejected rewrite leaves the old row untouched and fact pending, not automatically inserted as a duplicate. A genuinely new fact may be admitted only with review or the separately measured opt-in admission gate.

Publish validated compartments and **all unresolved fact records** atomically with the boundary, so first-turn success is durable even if turn two times out or memory authority is elsewhere. Revision-approved decisions may apply in that transaction if already available, or later in a short lease/CAS transaction; shadow decisions only record proposals. No SQL transaction spans inference. Use the actual authority, not a TS fallback writer when Rust owns the domain; current “skip facts on authority refusal” is a loss path to replace (`compartment-runner-incremental.ts:1087–1103`).

The queue is **durable, not promised small**: bounded processing does not bound arrivals. Persist project, source session/harness, publication/fact identity, original text/category/origin, immutable evidence lineage, both stage/run IDs, attempt state and last error. Fair oldest-first retries use per-project and fleet token/spend/attempt caps with backoff; one poison item must not monopolize a drain. Above a backlog threshold, pause paid proposal/retry work and notify the inbox, but keep episodic publication and anchored fact persistence running. Never drop facts or block publication on review throughput. Memory-disabled/auto-promotion-disabled policy pauses admission, not secretly enables it. Deliberate deletion explicitly cancels session-owned continuations while retaining project-owned provenance as evidence-unavailable.

Use per-project leases plus content-revision CAS and idempotent observation/decision keys. A target changed during inference is re-retrieved and reconciled, not overwritten. Hash collisions with archived rows require an explicit restore/new-revision decision: TS's current bump-on-archived-match must not count as live coverage. Embeddings and cues are regenerated after commit with content-hash checks (the embedding writer already guards stale results, `packages/plugin/src/features/magic-context/memory/promotion.ts:119–139`).

### One shared revision/evidence applier (approval boundary)

Historian, verify, curate, tools, dashboard and later backfill all submit the same operation envelope: project/owner, actor, operation/decision key, expected source/target revisions, complete proposed after-state, evidence applicability, dependency revisions and adoption class (`live` or `deferred`). They do not update memory SQL directly. Under the actual memory authority and project lease, one transaction validates ownership and revision CAS for **every** source in a merge, checks hash collisions/cycles/evidence, appends the journal, writes canonical rows/mappings/proofs, records prompt operations and resolves the pending item. A crash rolls back all or replays the same idempotent receipt. A stale source applies nothing and returns to review.

Rewrites, merges, replacements, retirements, restore conflicts and standing-rule promotion require an approval token binding actor/decision, all source and target revisions, after-text/metadata hash, evidence-set hash and dependencies. A token for old prose cannot authorize edited prose. A tool `save`, verify `update`, curate `archive` or backfill job cannot bypass this requirement by using a different endpoint. Unchanged revision-matching code confirmations and retry-safe no-text-change accounting may automate; semantic coverage/new admissions remain shadow by default. Missing authority retains pending work; there is no host SQL fallback under module ownership.

The applier, not the caller, assigns adoption class: approved live new/textual update/merge/replacement/retirement may ride an independent SOFT if dependencies fit; class/importance/proof/standing-priority changes wait for HARD; restore/undo and any future bulk operation are deferred until HARD. Mixed operations take the stricter class, and live successors depending on deferred revisions are withheld. Approval changes canonical state, not render permission. Existing direct promotion must route through this boundary when the replacement path activates; preserve opt-outs and do not silently treat the shadow decision as its approval.

**Regression tests:** `all_writers_require_revision_bound_approval` exercises historian, verify, curate, tool, dashboard and backfill adapters; `approval_rejects_changed_source_or_after_hash` applies no partial write; `merge_cas_all_sources_is_atomic` races each source independently; `agent_save_cannot_promote_standing_rule` preserves the opt-out; `unchanged_confirmation_is_idempotent` advances only verified applicable claims. These are required future product tests, not results claimed by this document.

### Non-destructive transitions and repair

Every merge/update/replacement appends to the surviving memory:

```text
history entry = {
  previous_text,
  changed_at,
  reason: refine | state_update | correction | merge,
  evidence: compartment reference(s),
  source_ids: predecessor/merged memory IDs
}
```

Record complete before/after category/class/importance/status, content hashes, actor/rubric/model, observation keys and successor relationships in the journal so undo proposes **metadata as well as prose**. `changed_at` is apply time; evidence carries occurrence time. Append in the same transaction as canonical changes. A merge nominates one existing survivor ID; other source rows become tombstones pointing to it. Each row has at most one active successor, no self-edge, and the transaction rejects cycles across the entire chain. Retain source journals; the survivor links them instead of copying independently editable histories or summing proof counts.

Current prose says “was X, now Y” only if the transition itself helps future work. Archived predecessors leave semantic, FTS, vector candidate and explicit-ID **current-memory** search. An ID lookup can return a tombstone with successor/history links, not obsolete prose as knowledge. Dated raw/compartment history stays searchable as dated evidence, not a covert active memory copy. Canonical retirement and removal of already-frozen prompt text/image are separate states.

**Restore is a new audited revision on the original ID**, referencing the selected historical revision without erasing intervening edits. Recheck current row, successor chain and same-project/category/hash collisions. If an active successor exists, review must explicitly choose to keep it and cancel restore, or retire/update the successor and restore the predecessor in one all-source CAS transaction. Clear the restored row's current outgoing successor edge in that new revision; historical edges remain in the journal, and any new active links must remain acyclic. A same-hash live row requires a reviewed consolidation/no-op decision, never a hidden seen-count bump; an archived collision remains history until its own reviewed restore. No automatic conflict winner or new identity to evade uniqueness. Restored text defaults private: revalidate current ownership/share policy and obtain separate explicit sharing permission; do not resurrect old permissions. Restore/undo use deferred prompt adoption at natural HARD, never the eager unarchive epoch path. Tests: `restore_conflict_requires_all_revision_approvals`, `restore_does_not_resurrect_sharing`, `restore_keeps_intervening_journal`, `successor_cycle_and_archived_hash_are_not_live_coverage`.

### Fleet approval inbox (decided product surface)

One dashboard queue across projects, filterable by project/topic/risk/age, groups related proposals without authorizing an entire model batch. Scheduled digests link to that inbox. An Ask-style phone notification is **a digest pointer**, never one notification per proposal and never a blocked agent turn. Slash commands may inspect status later; they are not the approval product.

Every card shows full before/after text, explicitly removed and retained claims, all source/target revisions, dated evidence and its authority/lineage, source/caller links, dependent operations, and canonical versus prompt-adoption state. Approve binds the exact envelope above; grouped review still records an individual revision-bound decision per proposal. A stale card returns to review without applying. Actions: **approve**, **keep** current knowledge (close this attempt), **reject** the unsupported proposal, or **snooze** until a chosen digest. Keep/reject do not silently delete the underlying durable fact.

Persist both the exact rejected envelope and a **rejection-family key**: canonical project, operation and sorted source/target IDs (for targetless new proposals, original candidate lineage). Record the evidence-lineage set accepted at rejection. Before emitting a proposal in that family, require a new claim-applicable independent observation or actual current-code verification record outside that set, or an explicit operator reopen. Topic labels, revision numbers, cosmetic after-text changes and retry/send IDs cannot bypass suppression; they are envelope details, not new evidence. A changed revision invalidates an approval and requires re-review, but does not automatically clear rejection. Tests must reword the after-text and advance a revision without new evidence, not merely retry identical JSON.

Expose backlog count/oldest age/age bands, arrivals versus decisions, attempts/token/spend per stage/project, stale-card rate, snoozed/rejected counts, and measured review minutes/throughput. Set digest frequency and paid-work backpressure from operator capacity, not a reassuring batch-size limit. Before fleet-wide proposals, run a representative 25-project inbox pilot and publish latency/throughput/spend. Tests: `digest_is_one_pointer_not_per_proposal`, `rejected_proposal_needs_new_evidence`, `stale_inbox_approval_returns_to_review`, `backpressure_preserves_publication_and_pending_facts`.

## 5. Cleanup sweeps

### Verify: connect the result to the row

The TS `verified` branch writes `memory_verifications` and optional commit metadata, **not** `memories.verification_status` or `memories.verified_at` (`packages/plugin/src/features/magic-context/dreamer/verify.ts:729–773`). `recordMemoryVerifications` only replaces side-table rows (`memory/storage-memory-verifications.ts:60–81`). Thus a successfully checked row can remain `unverified`, and selection misses verification reinforcement because it reads the row timestamp. TS's update branch also clears mappings without applying its reported file set (`dreamer/verify.ts:737–746,794–809`).

This is not universal across runtimes: the module verification writer sets row status/timestamp and updates mapping timestamps; its update branch marks the row verified but deletes mappings (`crates/mc-store/src/lib.rs:17077–17160`). The TS module request sends verdict/content/hash, not the freshly normalized complete file set or checked commit (`dreamer/verify.ts:667–705`). Align these contracts; do not announce that all verify paths currently fail in the same way.

Proposed apply transaction:

- Recheck project ownership, active status, revision and checked source commit; distinguish real confirmation, unmapped, skipped, refused and failed.
- For a confirmed unchanged claim, write row verification fields, normalized backing-file set, checked commit, evidence record and reinforcement together.
- For a proposed correction, retain the check/evidence and seek revision-bound approval. Only then append history, rewrite current content, replace mappings and verification provenance, invalidate old derived data, and queue a correction eligible on an independent render. Verify itself has no semantic mutation authority.
- Preserve standing directives: code can verify an implementation fact, not revoke a user's operating instruction. The existing directive/content-loss refusals remain defenses (`dreamer/verify.ts:612–660`), but reviewed history is still required for every accepted rewrite.

Before repairing legacy flags, audit a copied store by project, writer/authority, mapping origin and verification timestamp. A mapping sentinel or `verified_at=0` is not a check (`memory/storage-memory-verifications.ts:3–20,36–58`). Only genuine content-verified results matching the current revision may be carried into the row; reverify uncertain legacy matches. Do not stamp repair time as reinforcement. The exact supplied checked-row count remains a report gap.

### Stale check and curate

A later bounded stale-proposal sweep may run under the project memory lease; it is not part of the narrowed first release. Low shadow weight/non-reinforcement selects candidates, not a verdict. Retrieve newer same-facet evidence and code with caller context. Require exact old claims and a preservation inventory. Keep uncertain/partly true entries; retirement requires approval.

Current curate assumes accuracy, merges same-category duplicates and refuses standalone stale/low-value deletion; it protects rules, rationale and external limits (`packages/plugin/src/features/magic-context/dreamer/task-prompts.ts:110–122`). Do not simply remove those protections. Port curate/tool/verify changes to the same non-destructive applier, and add a stale-proposal result distinct from redundant archive. The completed retirement trial demonstrates that plausible citations can still be wrong.

**Reconcile-check is complete**, not a placeholder: primary reviewed known action precision was 60%, with four wrong accepted changes in each pass (§1). A quoted source can be an incorrect comment or justify changing only one clause. Keep this sweep proposal-only; any future automation trial needs independently graded preservation, caller context and repeat controls, not a more flattering label-detection precision.

### Classify: deferred calibration, not first-release periodic rescoring

Today classify shows each candidate's current importance (`packages/plugin/src/features/magic-context/dreamer/classify-prompt.ts:80–98`) and samples sorted quantiles of already classified rows (`dreamer/classify.ts:191–217,237–253`). A flat pool cannot supply calibrated diverse anchors. Its guidance conflates durability with impact (`classify-prompt.ts:41–52`). Its introductory comment says small pools are rescored wholesale, but the implementation selects unclassified IDs in both larger stages (`classify.ts:60–69,237–265`); periodic review is not implemented by that comment.

Replace it with a versioned consequence/breadth rubric and **fixed, human-scored anchors across several bands**, including safety rules, structural facts and ordinary situational facts. Do not show the candidate's current score; supply provenance needed for class eligibility, while keeping scope/shareability separate and privacy fail-closed. Review class as well as importance. The compartment anchor trials motivate hiding current/recent numbers, but do not establish memory-scoring accuracy; run a fixed-text, blinded memory trial with repeat controls before enabling periodic re-review.

After calibration, a later release may rotate a bounded overdue cohort by rubric/review age; not every run and not to force a histogram. Audit score/class changes and never reinforce on classify. Explicit privacy/ownership revocation retains its safety path; ordinary classifier/lifecycle metadata must not gain eager-HARD permission merely because it shares a visibility API (§7).

### Preserve admission opt-outs; defer configuration retirement

Keep `memory.auto_promote` during the first release: it has actual TS/Pi/Rust readers (`packages/plugin/src/config/schema/magic-context.ts:1485–1496,1560–1561`; `hook.ts:325,750–752`; `packages/pi-plugin/src/index.ts:1123,2060–2142`; `crates/mc-module/src/config.rs:744–747,796–799`; `historian.rs:3115`). Do not promise search-to-permanent promotion. Preserve `memory.enabled`; explicit prior opt-outs need a configuration decision before automatic admissions, not a silently ignored safety choice.

### Events as evidence, not authority

`compartment_events` is kind-agnostic JSON with a publish-local anchor; it has no compartment foreign key, and recomp can leave dangling IDs (`packages/plugin/src/features/magic-context/compartment-events.ts:7–26,52–104`; schema `migrations.ts:1100–1120`). Its “not consumed yet” comment is outdated: retrospective loads recognized causal/correction kinds and renders them as corroboration (`dreamer/task-executor.ts:1231–1255`; `dreamer/task-prompts.ts:206–248`). It is not a general memory provenance consumer today.

Use `causal_incident` to explain the cost/discovery behind a constraint or correction. Its current prompt is about an external-system surprise, not every internal bug (`historian-prompt.source.md:587–618`). Retain it as an optional evidence supplement anchored to a recoverable range.

**Do not map every `trajectory_correction` to a standing rule.** The current definition is discarded investment/direction change, and its source may be user, test, tool or self-review (`historian-prompt.source.md:620–645`). A proved explicit directive/save can propose a standing rule, but promotion still needs revision-bound approval. Other events belong in history/compartments. Direct instructions need not have caused a pivot; event extraction is not the authority gate.

Retain existing events. Repair only references actually needed by accepted evidence, copying essential provenance into its journal so recomp cannot erase it. Broad event re-anchoring is deferred until a sample measures added evidence value versus cost; it is not a first-release cleanup campaign. Unknown kinds/dangling anchors remain inspectable but cannot authorize changes. Any later production/removal change needs separate review; “not a primary reader” is not “unused.”

### B1: counterfactual render permission, including probe and commit

Ask **“would this pass already lose its provider cache or change its served prefix if all pending lifecycle effects were absent?”** before reading them for rendering. The Rust normal branch probes `compose_hard_fold_m0` before pricing mutations (`transform.rs:4638–4674`); that helper currently supplies `ctx.now_ms` and the store source (`:8831–8871`), whose memory snapshot read is live (`m0_compose.rs:445–462`). This is an extension hazard when lifecycle/score inputs are added, not proof that unimplemented lifecycle decay already leaks today.

For the probe, supply an **applied-state source**: exact applied memory revisions/metadata, score overlay revisions, captured activity/expiry clocks, policy/budget identity and frozen mural payload/hash. Combine those pinned inputs only with genuinely independent changed content/coverage. Do not regenerate an image from current cues. If this counterfactual produces no served change and no independent cache loss, commit only markers and replay **the complete existing text/delta/image pair**; do not compose latest state again in the commit branch. If independent loss/change is proven, a new captured canonical snapshot may be adopted. The same decision/source contract covers normal, compaction-off/no-live-head, recovery and contention branches. Marker-only HARD is not a lifecycle adoption boundary merely because its enum says HARD.

Lifecycle jobs, approval, verification, classification, restore, cue compression and later backfill **never** set project/workspace epochs, soft-refresh/force/emergency flags, render-config identity, compartment versions/boundary identities or structural m0 mutation markers. A selection-policy upgrade is pending metadata, not automatic invalidation. The dashboard approval endpoint sends the revision envelope to its owner, not generic `update_memory_status`/`update_memory_category`. Explicit privacy/ownership revocations are a separate authenticated operation and retain their stronger invalidation; an ordinary classifier verdict cannot borrow that exception.

**Refuted review claim:** background cues do not change `persisted_mural_hash` on the next pass. Both Rust branches use `frozen_mural_hash(&loaded.core)` (`transform.rs:3029,3902`); the helper reads the frozen mural unit's `reset_rule` (`:7286–7291`), not the live cue table. Keep that behavior. This does not remove the distinct speculative-composition hazard above.

### B2: SOFT projection and admission algorithm

Today TS rereads eligible canonical rows, trims all IDs above the baseline watermark each SOFT, and forces successor/visibility IDs; Rust does likewise, including IDs below its watermark (`inject-compartments.ts:2794–2975`; `m1_compose.rs:394–468`). A numeric ID watermark alone cannot freeze prior delta choices. The r2 loader must implement this order:

1. Load the session's applied manifest and **persisted delta admission ledger**. Each entry binds project/ID, admitted revision/hash, representation, immutable creation-time priority, rendered cost and any live correction receipts. Keep waiting/unadmitted operations separate; restart reloads the same membership, not a new trim of canonical rows.
2. Build the render-only revision pool **before** eligibility, successor resolution, forced-ID selection, mutation coalescing or budget accounting. For adopted rows use applied revisions plus already-rendered live corrections. Ordinary metadata/status/deadline edits stay pinned; deferred additions are absent and deferred archives expose the old applied active row. Explicit privacy revocation overrides this projection via its separate safety path. Canonical state remains available to search/reconcile, not automatically to the head.
3. Select eligible live operations whose dependency revisions are present in this session's projection. **A1 → deferred A2 → live A3 based on A2: withhold A3 until an independent HARD adopts A2/A3.** Do not rebase semantically in the first release. This also covers dependent new rows, successor edges, archive, restore and undo. Withheld operations remain pending, not rendered/acknowledged.
4. Reuse every admitted delta revision and priority unchanged. A genuine new admission **cannot displace a prior admission** in the first release. Order new candidates by frozen creation-time priority (existing permanent flag, creation-time importance descending, created-at ascending, ID ascending), never current reinforcement/score. Append whole entries only within the quarter budget; those that do not fit stay waiting until a later safe opportunity/HARD. Later semantic admissions need their own opt-in gate (§4).
5. Coalesce eligible live textual corrections against the union of text-visible, cue-visible and already admitted IDs, with terminal remove/successor precedence and cycle checks. First-release **correction allowance is another 25% of the configured memory text budget**, capped at **40 rendered mutation records** including removals/successor markers; this is a conservative design bound, not a fitted quality result. Capture it with the session policy; charge XML/header and any forced successor text to it. It is separate from additive admission space, cannot evict admissions, and cannot force unbudgeted replacement targets. If a correction plus required successor does not fit, withhold the atomic operation group and expose pending adoption. Pending/deferred counts do not enter the pressure backstop; rendered correction count alone cannot exceed its current >40 threshold. Oversized-claim fixtures must prove withholding, not truncation; replay must measure whether this allowance causes unacceptable adoption delay before release.
6. Commit refreshed m[1] bytes, admission/visibility manifest, correction receipts and cursors together under snapshot CAS. Maintain **per-operation rendered receipts plus a scan position**: a scan may pass a withheld item only if that item remains explicitly pending. A scalar “last rendered mutation ID” cannot acknowledge holes. HARD adopts one approved snapshot, folds pending eligible operations and resets the delta ledger atomically.

Determine independent pressure before step 3 using the pinned applied pair and newly eligible **non-lifecycle** compartment/profile work. On a SOFT that has no counterfactual HARD reason, proposed lifecycle groups must also fit remaining pressure headroom: total m[1] stays at or below its absolute cap (currently 20% of history budget) and, when m[0] is at least 500 tokens, its 15% m[0] ratio cap. Charge all serialized bytes through the same token estimator. Withhold the first atomic group that would cross a bound; do not turn that crossing into HARD permission. If the counterfactual already exceeds pressure bounds, the independent HARD may adopt latest approved state. Tests must exceed **count, ratio and absolute** thresholds with pending repair while an unrelated SOFT remains eligible, and assert no manufactured HARD.

This pins metadata edits even if no mutation-log entry exists. It is intentionally conservative: not every canonical correction is immediately automatic context. No automatic change occurs on defer. An independent SOFT can carry live changes whose dependencies and budgets are satisfied; deferred changes wait for HARD.

### B3: one revision-qualified text/mural/correction manifest

Capture one immutable pool of memory revisions, visibility/expiry state, cues with source hashes, selector policy/budgets and clock in a read snapshot. Pass the resulting tier decision directly to text **and** image renderers; neither rereads rows or recomputes the complement. Save entries `{project, id, revision, content_hash, representation: text | cue | search_only}`, cue hash/image identity, and correction overlays with the served snapshot. At SOFT the cue manifest/image remains frozen; correction coverage uses the union of text and cue entries plus delta admissions. Search-only IDs are not automatically visible.

The shown TS path captures text before COMMIT then separately calls `resolveMuralForM0` (`inject-compartments.ts:2513,2538–2555`); `resolveMural` can load rows/cues and recompute overflow (`mural/resolve-mural.ts:99–122`). Its correction renderer skips ordinary mutations outside baseline IDs (`inject-compartments.ts:2843–2847`), and those IDs come from the text trim (`:2601`). **Required cue-only case:** memory N@r1 is only in the frozen image; an approved live correction/archive N@r2 gets an explicit “trust this over cue N@r1” correction/removal at the next independent SOFT. Keep the image bytes unchanged, record the effective overlay, and fold/remove the obsolete cue at natural HARD. A deferred correction or one depending on deferred A2 still waits (§B2); the cue does not secretly authorize it.

### B4: current search in the tail, frozen automatic head

The guarantee is **no automatic lifecycle change to frozen m[0]/m[1]/image**, not “no current repair text can enter agent context.” Explicitly requested search may return approved current canonical prose in the tool-result tail immediately, with revision and pending-head-adoption status. It does not fold the head or create a new rendering opportunity. Unapproved proposals remain inbox/history data, not current search knowledge.

Replace ID-only “already visible” exclusions with `{project, id, rendered revision/hash, representation, effective correction}`. Suppress a hit only when its **current revision's complete text** is already visible (baseline/delta/full-text correction). N@r2 remains discoverable when only N@r1 is injected. A mural cue never suppresses full-claim retrieval, even at the same revision; a removal overlay is not full prose. Apply this predicate in semantic/FTS/explicit-ID lanes and Rust/TS/Pi adapters. Current tools pass a Set of IDs (`packages/plugin/src/tools/ctx-search/tools.ts:131–134`; ID predicate `search.ts:1994–2000`). Prune retired rows before retrieval budgets; the existing semantic selector already intersects its vector IDs with the eligible memory pool (`search.ts:805–833,925–958`), so the review's claim of a current dead-vector-slot defect is not established by the constant `50` alone.

### Later backfill needs a stronger barrier than ordinary live writes

Merely writing backfill content to `memories` and adding ordinary mutation-log entries is **not** enough: a priced SOFT rereads live eligible memories and mutations, before the next HARD (`inject-compartments.ts:2900–2925,2944–2975`). Suppressing the mutation log alone is also insufficient for already-added m[1] rows whose content is reread.

Keep the versioned **prompt projection**, not searchable cold copies. Deferred operation-set membership and per-ID revisions, not just a bulk watermark, pin backfill additions/archives/restores/undo until independent HARD. Later live observations reconcile canonical state but use the A1/A2/A3 withholding rule. Staging tables may hold proposals, but once approved canonical rows change the same barrier is mandatory. Bulk backfill remains deferred until this entire algorithm, cost allowances and recovery contract have passed the spec-exit gate.

This is render-only version selection, **not searchable cold copies**. History is private audit; ordinary search uses only canonical active claims. Weight/tier adoption uses the same applied projection. A SOFT may incorporate independent live corrections while keeping bulk repair revisions frozen; a HARD atomically adopts the latest approved bulk set, reselects tiers, folds corrections and updates visible IDs/cursors. Undo follows the same barrier. This extra loader/journal work is a prerequisite for the promise “nothing from repair until next natural rebuild,” not a claim that the base already provides it.
