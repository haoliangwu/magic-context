# Emergency transforms and retry joining (source audit and bounded probe)

**Status: design, not an implemented join. Measurement is inconclusive for large real sessions.** This report distinguishes a finished response from a historian run: joining the latter alone does not replay the former. Source references below are relative to the repository root at `5cbcbb7f3230442dc912af6b01450a4674e5cebc`.

## Executive finding

The claimed 1,500–1,650 s inline budget is not the present handler's wait. `MAX_EMERGENCY_REQUEST_BUDGET = 1500 s` remains the advertised consumer deadline (`crates/mc-module/src/historian.rs:1589-1602`), but `TRANSFORM_HISTORIAN_FOLLOWUP_BUDGET = 20 s` is the actual current emergency follow-up deadline (`crates/mc-module/src/lib.rs:246,7158-7168,10860-10866`). On expiry the historian task **continues**, while this request serves its emergency reduction (`lib.rs:7170-7225`). OpenCode's Host runner already serves before its long-running historian finishes, without even waiting 20 s for a newly fired run (`lib.rs:10868-10902,11007-11029`; `crates/mc-module/src/historian_runner.rs:61-77`). The 1,500 s constant is therefore an overconservative *consumer* timeout, not evidence of a 1,500 s inline fold today. A slow synchronous transform, store wait, rendering, or response transfer is outside that 20 s follow-up limit.

**Recommendation: both a bounded inline path and an exact-request join, but do not blindly introduce a new 200 s cap.** Keep the existing 20 s historian follow-up cap (already much less than 200 s), explicitly cap or monitor the *entire* gateway-to-first-byte path below Claude Code's 360 s silence limit with margin, and add the join to prevent duplicate effects if retries nevertheless arrive. Do not claim 200 s suffices for large real requests until representative end-to-end measurements succeed. For Host, the background fold and immediate emergency-reduction response are preferable to extending inline work to 200 s. Coordinate any change to the advertised 1,500 s budget with consumers after verifying the other stages.

## Current duplicate behavior and hazards

`handle_transform_dispatch` creates a health ticket and calls the page or ordinary handler, without a same-session request lock or result table (`lib.rs:10359-10375`). The ordinary handler parses each request, records its own attempt, begins a new snapshot generation and executes `run_transform` independently (`lib.rs:10399-10433,10493-10516,10582-10590,10717-10845`). Rust execution is synchronous between awaits; this can incidentally serialize CPU work on a single-thread executor, but does **not** provide an across-route or across-worker deduplication contract. At an await (particularly emergency historian completion), a second request can run. There is no equality comparison between bodies. Identical and near-identical requests take the same independent path; different channel bindings are checked, not coalesced (`lib.rs:10493-10512`). Paged final transforms *do* have a separate content-addressed completion replay (`lib.rs:1681-1732`), which must not be mistaken for an ordinary transform join.

The snapshot cache's `InFlight` is a marker **for wrapup snapshot validity**, not a request future: `begin` overwrites the entry and increments generation; `finish_ready` of the older pass refuses to publish if the generation changed (`lib.rs:2664-2674,2699-2720,2749-2815,10582-10590,11140-11160`). Its 4,096 in-flight entries are count-bounded, and ready requests are limited to 64 MiB (`lib.rs:1315-1327`). This avoids stale snapshot resurrection but an older completed pass can lose its wrapup snapshot even if its transformed bytes were valid. It does not return the first pass's response to the second.

`transform_with_projection_cached` independently loads/classifies/commits; it retries a row-version CAS conflict on a fresh state, not by replaying the other response (`crates/mc-module/src/transform.rs:2187-2205,2402-2475`). A second pass can consume newly visible frozen decisions, observe a new publication floor, or reject after changing the snapshot generation. Frozen marker/drop rules and durable CAS constrain many duplicate moves, but they do not guarantee two overlapping requests produce identical bytes or no duplicate work. The historian has an independent per-session live-run claim: a busy second emergency pass awaits the current run, may retransform and even prepare a subsequent firing if still eligible; below emergency it simply reports busy (`lib.rs:10901-11051`; tests `lib.rs:37764-37801,37928-37957`). One live claim prevents *simultaneous firing in that process*, not every subsequent run or repeated trigger evaluation/decision trace. Producer work after the first caller disconnects can still finish; the first transform's response is not saved for that caller's retry. Store row CAS and historian publication fences reduce conflicting persisted decisions; there is no proof of exactly-once transform across disconnect/restart. An older pass may return bytes made before a newer publication; the final publication-floor check catches one emergency interleaving (`lib.rs:11031-11050`). Native/LKG and host state are likewise subject to the independently completed pass; the join should avoid feeding an older pass's response into a newer cache state. The single-writer **store-open lease** arbitrates *process ownership*, not transforms within the same module: one store is held by the handler (`lib.rs:3808-3834`), and a competing process waits up to 60 s at open (`lib.rs:252-254,4521-4663`). It cannot serialize requests sharing that store. No claim that duplicate marker moves or LKG overwrite actually occurred is made here.

## Measurement and limits

A read-only SQLite `backup()` of the module store was made in `$TMPDIR/magic-context/ckmc-emergency-fold-and-join/` (1,067,446,272 bytes in 2.8 s). `lsof -n -p <backup PID>` showed the host source descriptor **read-only** and the destination in the temporary directory writable during the attempted host backup; the profiling Rust process received only the scrubbed temporary module-store path. The host `opencode.db` backup (33 GB source) failed the 180 s command ceiling, so its incomplete unsanitized copy was deleted immediately. No host shape or credentials were read from that partial backup. On the module-store copy, all data tables except three sessions' tag rows were emptied; retained `source_bytes` were replaced by equal-length zero blobs, and block identities were exported with only `kind_tag`. Triggers were removed on that disposable copy to permit scrubbing. Three original session identity sizes were 8,341 / 7,941 / 7,120 messages, with inferred—not observed—host role/time scaffolds. **These are real block/tag geometries, not faithful real-session requests or a valid production emergency replay.** The disposable copy and all exported scaffolds were removed after probing; `lsof -n -p $$` at cleanup showed no live-store handles and the temporary specimen directory was absent. No file in the excluded live configuration directories was read.

The existing ignored profiler `transform::tests::real_session_stage_profile` (`crates/mc-module/src/transform.rs:16209-16496`) replays a rebuilt array on a copied store and reports `planning`, `state_evolution`, `tag_overlay`, `build_output`, etc., but **does not drive a historian or force an Emergency95 handler pass**. The 8,341-message probe with scrubbed store, synthetic roles/time and 4,314 tags emitted only the setup census and timed out at the 600 s command limit (including 139 s compilation); a 500-message prefix with those same 4,314 tags also emitted only setup and timed out at 180 s (including 52 s compilation). Neither emitted a `real-profile pass=` line. These are timeout/censored observations of an **invalid reconstructed fixture**, not 461 s and 128 s measurements of emergency planning, and cannot be used to say real emergency transforms approach 200 or 360 s. No repeat distribution, p50 or worst case across completed large sessions is available. The attempted host backup and profiling timeouts make the requested real-session measurement **unmet**, rather than providing reassuring numbers.

A narrower control with an isolated in-memory scripted producer passed `handler_emergency_inline_drive_folds_in_the_same_response` (`lib.rs:37788-37801`) three times: wall clock including cargo test startup was 1.234 / 1.250 / 1.181 s (median 1.234 s, worst 1.250 s). The scripted response is not the configured real historian model and is not representative of provider latency, large payloads, or the host runner; no numeric planning/historian/fold/render split is inferable from this control. No real model credential or external model service was used in this probe; a representative historian run on a scrubbed specimen remains outstanding. The useful source-side split is `TransformTimings.planning`, `.state_evolution`, `.build_output`, handler `.transform_execute`, `.handler_followup`, `.native_attach`, response encoding (`transform.rs:1253-1333`; `lib.rs:11167-11199,16330-16445`) versus historian busy/inline wait logs (`lib.rs:7199-7212,7229-7245`). A future credible measurement should obtain consent for a real model, backup and immediately scrub *both* databases via read-only backup into the designated tmp directory, validate host role/ordinal mapping and a true >=95% request, record per-stage timestamps plus the actual model run(s), collect at least several completed distinct sessions including cold and warm requests, then report p50/max separately for Host and Broca. A fast credential-free mock cannot establish provider wait time.

## Proposed join contract

* Admission occurs **after route/session/lineage authentication** and page-vs-unpaged selection, but **before** snapshot `begin`, traces and all side effects. Use a key `(session_id, canonical route lineage root, effective config/render epoch, SHA-256(canonical semantic transform request))`. Canonicalize JSON object keys; include full/delta request semantics, fingerprints, message bytes, model, usage/geometry, tool controls, and all values that can affect the result, including the effective historian timeout if different. Exclude only transport channel, request `attempt_id`, `request_observed_at_ms` and other independently demonstrated per-attempt telemetry. Freeze or hash resolved config/runner at admission; a changed effective policy must miss. A near-identical body with changed semantic fields is a **different** request and must run independently (or be explicitly serialized if that is required for safety). Compare length and canonical bytes as well as digest if collision defense is desired. The digest must be computed from actual expanded delta content or include its acknowledged base identity to avoid reusing a result across a changed snapshot (`lib.rs:10564-10575`).
* Atomically register one owned computation and let all matching callers await its completion; publish the **same serialized response bytes and error** to waiters (not merely the same historian run or mutable response object). Keep the completed result joinable for **10 minutes from completion**, spanning at least one 360 s timeout/backoff retry; expire by monotonic time and LRU. After expiry a retry is an ordinary new pass. Do not replay a failure with transient store/route refusal for ten minutes: either use a short bounded failure TTL or remove it on completion and let only already attached waiters receive it.
* Bound retention explicitly: e.g. at most **8 active flights and 64 MiB of completed response bytes**, plus a per-result limit (e.g. 32 MiB). Account actual encoded bytes, metadata, and active Arc holders, not just map keys. At capacity, do not silently execute an identical duplicate: attach to its already-admitted flight if possible; refuse excess *new* flights with a typed retryable capacity error, or make a separately justified nonjoinable oversize policy. A 32 MiB limit alone cannot guarantee same-result joining for a larger accepted response; either reserve its full worst-case frame size, reject it before side effects, or provide a secure bounded spill strategy. Never retain indefinitely after a waiter disappears.
* Do not tie the computation's lifetime to the first route's future. Put it in a module-owned task, fan out a cloned immutable result, and continue through commit/fold/final response construction if the first channel closes. Route closure should detach only its waiter, not cancel the work. Keep the in-flight entry until completion, then its bounded TTL. Health tickets need distinct completed/cancelled-waiter accounting (`lib.rs:1095-1163`). A module restart drops all in-memory flights and completed bytes; a resend after restart re-executes against the durable store (or follows existing paged-final replay), with CAS/lineage fences and possible changed output. Do not claim cross-restart exactly-once or revive a phantom result. The process store lease prevents two owners opening the same store concurrently but cannot replay the lost response (`lib.rs:4555-4663`).
* Keep `TransformSnapshotCache` separate. Only the owner calls `begin/finish_ready` once; joiners do neither. Publish the snapshot *before* the completed response becomes joinable. A joined result must not regenerate native attach or update an LKG twice. The cache's ready LRU is a request for wrapup, not an output cache (`lib.rs:2749-2815,11140-11160`). Keep separately scoped result metrics (hits, misses, expiry, bytes, active flights, owner-aborted route, restart miss). Test concurrent identical bodies, attempt-field differences, semantic differences, route close, snapshot generation, first failure, late completed join, expiry, oversized response and restart.

The TypeScript OpenCode Rust path **can** encounter analogous lost-result retries, but it currently suppresses a duplicate during a healthy stalled ordinary transform (`packages/plugin/src/hooks/magic-context/rust-mode-transform.ts:2064-2122`). For a content-addressed *paged final* request it explicitly retries only the identical final page and uses the module's existing page completion replay (`rust-mode-transform.ts:2018-2055`, `lib.rs:1681-1732`). A later pass after a timed-out or closed call can still arrive for the same session; do not conflate the paged mechanism with a generic unpaged join. The proposed key and response-byte contract would apply to both hosts, while preserving the existing paged protocol.
