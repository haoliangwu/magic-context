# CortexKit authority operations and writable inputs

Source inventory, 2026-09-29. **No live command, vault, state store, or authentication prompt was exercised.** Citations are repository-relative under `~/Work/Projects/CortexKit/` (prefix each cited path with the named repository). `direct` means possession of the local subc connection, **not** proof that a person typed the request. This is an inventory of verified surfaces and explicit gaps, not a claim that a CLI prompt protects a hostile same-user process.

## 1. Operations

### Entry points and caller boundary

The built-in `ck` parser handles `setup`, `upgrade`, `module`, `routes`, `catalog`, `provenance`, `health`, `quota`, `daemon`, `machine` and `help`; unknown domains dispatch to `ck-<domain>` on PATH after a `--ck-domain` probe. Thus the recursively extensible command tree depends on installed executables, not just the core parser (`subconscious/crates/subc-core/src/bin/ck.rs:150-323,7319-7917`). Module management catalogs are independent of this CLI. A local client uses a connection file/key and subc authenticates before routing, but the supervisor control dispatcher has no human-presence gate (`subconscious/crates/subc-core/src/bin/ck.rs:500-558`; `subconscious/crates/subc-daemon/src/server.rs:287-347`; `subconscious/crates/subc-daemon/src/control.rs:2098-2187`). A same-user model shell can call the binary by absolute path or speak subc itself. A module `reserved:<id>` identity is distinct from a client `direct` bind: the supervisor checks reserved HELLO/launch nonces (`subconscious/crates/subc-daemon/src/control.rs:1785-1835`; `subconscious/crates/subc-daemon/src/daemon_config.rs:227-245`). None of these checks proves physical operator consent.

## 2. Human confirmation independent of Prefrontal

| Method | Shell-attacker resistance, UX and platforms |
|---|---|
| Phone or Desktop **tap through elicitation** | Strong *only if* approval travels over a channel the local shell cannot forge/read and is cryptographically bound to exact operation, scope, target, expiry and nonce; phone/Desktop relay credentials and notification routing must not be writable by the attacker. Current elicitation provider is Prefrontal; extracting it to an independent module is a later architectural option. Best remote UX; requires paired device/provider/connectivity; fallback must fail closed rather than silently switch to a shell question. |
| macOS `LAContext` / Touch ID | Local biometric/user-presence prompt from a trusted process can stop a model that only drives shell input; a subc module or `ck` can *invoke* LocalAuthentication, but put the decision and protected state in the owning module, not in CLI. Distinguish `deviceOwnerAuthenticationWithBiometrics` from passcode fallback. Merely receiving a Boolean from a replaceable same-user helper is not enough. A signed app/entitlements are **not generally required just to evaluate an LA policy**; keychain/Secure Enclave access-control bindings, hardened runtime distribution and UI session/headless behavior have additional requirements to validate on target OS. macOS only; no prompt in headless daemon session may mean no usable fallback. |
| System auth dialog | `osascript ... with administrator privileges` / Authorization Services proves an admin credential for privileged acts, **not an independent confirmation when same-user authorization is cached or the shell can drive the dialog**. macOS dialogs differ from LA biometric; `sudo` and auth services may cache. Linux polkit can authenticate a privileged service, but agent/policy/active session and cached authorization matter. Windows UAC consent for an admin user is not a password boundary; Windows Hello bound to a key/use with OS-mediated user verification is stronger. Cross-platform UX/packaging cost. |
| `sudo` | A fresh password entry can block a shell that does not know it, but sudo's timestamp cache makes subsequent calls silent; a model shell can inherit a ticket-bearing TTY and can type in a PTY. Elevating every change to root also expands blast radius. Check/cache invalidation alone cannot establish consent for each operation. |
| User-only PIN | Only useful if secret is not in user-readable files/env/process memory and is entered into a **separate trusted UI** not under model control; then it approximates out-of-band consent, subject to brute-force lockout and binding. Plain TTY PIN is a password the shell can type/replay; a PIN stored in a same-user file is no defense. |
| Terminal `y/N`, `--confirm`, `--apply`, `--yes` | Stops accidents only. The model can answer prompts, pass flags or run a PTY. Never use as authority boundary. |

**Recommended layered rule.** Require a one-shot human-presence authorization for *widening* project trust/roots, credential creation/replacement/handle/grant and secret export/sign/decryption outside already scoped grants, connector ceilings/bindings/policies, pairing/exposure, agent identity/delegation/wake/change policy, durable browser/app grants, installation/release/rescan that changes authority, and any config promotion that widens these. Destructive removal of trust, credentials, grants, modules and persistent stores merits confirmation for irreversible loss even if it narrows rights. Read-only public metadata need not prompt; secret reads require pre-existing scoped grant or a new confirmation (avoid prompting for every already authorized bounded read). The **owning module** checks a purpose-bound, short-lived proof before commit/secret release, including when invoked by `direct`, a reserved module, or a model-facing tool. Do not trust CLI-only prompts, PATH interception, manifest-only roles or request-declared origin.

Default: mobile/Desktop out-of-band tap when an independent elicitation provider exists; macOS use LAContext-backed module-side authorization as local fallback without Prefrontal; Windows use Hello key/user verification; Linux use polkit backed by a privileged broker with no cached consent for protected changes. Where no trustworthy provider/UI exists, refuse widening and offer a separately initiated setup ceremony; a shell prompt is informational only. Allow an operator to pre-authorize a signed, stored capability such as `approve projects under ~/Work/* for one hour`, specifying verb, canonicalized path subtree, target identity, caller, maximum count/rate, expiry and revocation; narrower existing grants still apply. On each request atomically consume/check it in the owner; no generic global `approved=true`. AFT should put session/project scope in bash child environment so operations can label a request `agent session X` versus an unlabelled direct caller. **This is self-asserted attribution**, because a same-user shell can edit the environment, not a security credential; bind real grants to independently authenticated identity/proof.

### Defending against same-user file edits

Mode 0600 / filesystem ACLs distinguish *other users*, not a model process running as this user. Merely migrating grants into a same-user SQLite database is insufficient: direct writes, replacement executables, relocated env/data roots and backup/restore still bypass an operation-level check. A signed config can detect unauthorized edits **only if** signing key and verification executable/accepted public key are outside model-write reach, with rollback protection; signatures made with a user-readable key or a model-callable signer do not help. Root-owned or separate-user config and service/broker identity can be a real boundary, at the cost of privilege broker, install/update friction, cross-platform packaging and harder backups; owner still must verify requested change and protect service launch path.

**One consistent rule:** files and environment may provide ordinary preferences and *tightening* deltas only. Authority-widening values are effective only when promoted by an owning-module confirmed operation into a tamper-resistant authorization store, or when that module notices a file edit and obtains out-of-band confirmation bound to the *canonical diff/hash*, exact target and expiry before applying it. Unconfirmed edits remain pending; malformed/deleted baseline must not restore permissive defaults. Prefer moving mutable authority to operations (trust approvals; Claustrum grants/handle issuance and raw reads; Plexus ceiling/grant/`allow`/bind/repin; Callosum peers/expose/roster; Cerebellum durable grants; Prefrontal `autonomy`, `sessions.change_policy` if implemented, agent wake/delegation/permission/model/substrate/extension routing; AFT enabled tools, sandbox/network/filesystem and executable selectors; subc module program/identity/reserved gates/fed exposure). Confirm executable/plugin/service or manifest replacements before load as well. Project files should *never* widen user policy, generalizing AFT's partial only-tighten rule; apply the same rule to host OpenCode/Pi extension lists and user-tier files, not just `.cortexkit`. Audit raw-state tampering and binary replacement with an OS-protected broker; absent such isolation, describe this as an accident-resistant consent system **not a security boundary against arbitrary same-user shell code**.
