# issue 554: shared-store contention and OpenCode 2 health

## Result and limits

**A synchronous SQLite writer wait in Magic Context can make a live OpenCode 2 server miss `/health`.** This is reproduced with a deliberately held writer lock, not inferred from the reporter's log. In the current build, the traced call is the pre-provider `withPrivilegedWriter(..., () => undefined)` admission in `packages/plugin/src/v2/hooks/context.ts:1122-1127`, through `shared/sqlite.ts:539-562,582-591`, to `bun:sqlite` `exec("BEGIN IMMEDIATE")`. Two instrumented hosts spent 5,001 ms each in the first call and about 4,465–4,470 ms each in the second before the external ten-second lock was released. Their in-host 20 ms heartbeat gaps were about ten seconds; external 900 ms `/health` deadlines expired. The bounded 15-second **boot** storage open does not bound subsequent hook calls (`v2/hooks/storage-gate.ts:55-64` resets the successfully opened handle to a 5,000 ms busy timeout). Three foreground acquisition attempts plus synchronous `Atomics.wait` backoffs can total 16.5 seconds for *one* acquisition (`shared/sqlite.ts:547-562`). Background paths avoid those **extra retries**, not the native 5-second wait.

For archived 0.43.2, the corresponding locked runs had five-second heartbeat gaps, `/health` failures, and `SQLITE_BUSY` stacks with `ensureSessionMetaRow -> updateSessionMeta -> bun:sqlite #run`; `storage-meta-session.ts:113-157` updates metadata inside an immediate transaction. This is a direct demonstration that the released plugin can block the host loop under a lock. It does **not** prove that the reporter's minutes-long storms were caused by this mechanism, identify the owner of their lock, or demonstrate a self-sustaining stall without a held lock. An alive process and a failing `/health` are consistent with blocked synchronous work but not specific to Magic Context. The reporter states 0.44.0 was never installed: do not attribute these incidents to its schema-91 regression. Its once-per-open `SQLite boot busy timeout … timeout=5000ms` diagnostic reports configuration, not a five-second wait (`storage-db.ts:203-213`).

## Isolated real-host experiment

`packages/e2e-tests/scripts/issue-554-contention.ts` starts 11 real `opencode serve` processes (seven mock-provider sessions driven, four idle) per run, each with its own OpenCode DB/XDG roots and the **same** throwaway `context.db`. Every run has an external one-second `/health` poll with a 900 ms deadline and an in-host 20 ms heartbeat, then ten seconds of ordinary load, 30 seconds with all hosts `SIGSTOP`, ten seconds after simultaneous `SIGCONT`, a ten-second external `BEGIN IMMEDIATE` writer hold, and seven seconds after release. The stop interval is a control: health failures *during* intentional suspension are not counted as a plugin failure. Prompts complete against the mock provider; a fast `session.prompt` response during the locked interval does not imply that all later asynchronous hook work completed. These are macOS timings, **not Windows timings**. No real provider or operator config was used.

All final runs had some transient steady-load failures, but the data do not attribute these to SQLite; startup, host differences, machine load and plugin contention remain possible. An earlier master/2.0.15 run had 56/110 steady failures and ~11-second prompt durations, whereas its private-TMPDIR repeat had 6/110 failures; those numbers must not be presented as a stable release comparison. Only the *injected-lock* failures have the explicit lock-owner and call-stack evidence above. Simultaneous wake alone produced no persistent post-resume failure in the final runs (an earlier master/2.0.15 run had four transient timeouts). A 30-second `SIGSTOP` is an approximation: macOS does not reproduce Windows network suspension, OpenChamber's health supervisor, or its timer scheduling. Neither result validates or rules out the reported sleep/wake trigger. No multi-minute self-sustaining loop was reproduced.

## Probe and writer audit

* In **0.43.2**, RPC startup's `warnIfOtherLiveInstance` scans discovery records synchronously and invokes `isPidAlive` for each foreign PID (`v0.43.2:packages/plugin/src/shared/rpc-server.ts:254-267`). On Windows that invokes synchronous `tasklist` with a one-second timeout per PID (`v0.43.2:packages/plugin/src/shared/rpc-utils.ts`, `readWindowsProcess`). Ten foreign files per host can make this an O(host²) collection of synchronous process probes at boot; migration's process-discovery guard can also invoke synchronous CIM/PowerShell (up to five seconds) and tasklist. The old warning uses `!isPidAlive(pid)` although liveness is a **string** (`alive`, `dead`, `inconclusive`); that expression is false for all three, so *any parsed foreign record* can trigger the warning, even if its PID is dead. Accordingly the reporter's warning alone does not fingerprint the old code or establish a verified competing PID. This audit does not count actual Windows subprocess executions: no Windows host was available. These probes run on startup/open or discovery, not once per `/health` request. An OpenCode 2 startup comparison with an injected slow process transport was previously documented in `docs/reports/windows-opencode2-storage-boot.md:40-55`; it demonstrated a five-second stall, not the present storm.
* Current RPC startup fires `warnIfOtherLiveInstance` without blocking listener startup and awaits a cached/coalesced asynchronous process snapshot (`shared/rpc-server.ts:179,266-280`, `shared/rpc-utils.ts:876-986`). Current async storage opening likewise probes asynchronously and uses a zero-timeout boot lane; the boot grace is 15 seconds (`v2/hooks/storage-gate.ts:55-64`, `storage-db.ts:2480-2538`). Legacy sync helpers remain available for other callers (`shared/rpc-utils.ts:106-115,293-315,786-815`, `shared/rpc-client.ts:154-163`), so "all process discovery is async" would be inaccurate. Eleven hosts do not create an RPC singleton: each listener advertises a per-process port record.
* **Turn-critical:** storage availability/schema safety, foreground transform and metadata necessary to serve a turn, writer admission, and atomic pending-operation application. Deferring these without preserving turn refusal/consistency changes correctness. Current `withSqliteTransformPass` limits *additional* acquisition retries to an active awaited pass (`shared/sqlite.ts:490-562`); the explicit admission transaction in `v2/hooks/context.ts:1122-1127` precedes transform callbacks but still waits synchronously. Foreground locks should have a documented upper responsiveness budget distinct from the user's turn budget.
* **Deferrable or coalescible:** message indexing/reconcile/orphan sweep (`features/magic-context/message-index.ts:666-1016`), embedding registry and stale GC (`project-embedding-registry.ts:946,1197`), dreamer leases/scheduling (`dreamer/lease.ts:102-118`), historian publish (`hooks/magic-context/compartment-runner-incremental.ts:1122`, `compartment-runner-recomp.ts:137`), note nudges (`hooks/magic-context/note-nudger.ts:57`), cleanup and backfill. Some eventual results (e.g. historian publication) must be committed atomically once produced, but need not monopolize the host loop while another process holds the SQLite writer lock. The one-second slow-transaction logger measures **hold time after commit**, not waiting before acquisition (`shared/write-transaction-timing.ts:3-22`); it cannot identify a lock owner from an external process. No Magic Context internal transaction was shown to hold the lock for seconds in this experiment. **The longest known holder was the harness's external `BEGIN IMMEDIATE` connection (10 s)**, deliberately held to establish causality.

## Smallest next fix to test, not implemented

First give *non-critical host-thread writes* a short busy budget (e.g. 0–50 ms) and defer/retry them on an asynchronous timer with a bound, deduplication and lifecycle cancellation. Do not merely lower the timeout for a critical foreground admission write and then silently proceed: a busy admission must remain an explicit turn refusal, or be awaited through a genuinely nonblocking handoff. A connection-wide PRAGMA change without isolating foreground and background handles would inadvertently shorten foreground tolerance and does not solve a sync `Atomics.wait` retry. Add attribution around **acquisition** (site, SQL, elapsed, foreground/background) as well as committed hold time and compare failures/latency on both host versions; the current 1-second hold-only logger cannot diagnose these waits. Next, move genuinely high-volume background writers to a worker/process or an async queue with separate connections; this is more invasive and requires snapshot/ordering and shutdown semantics. Finally shorten transaction holds by moving parsing/model/network work before `BEGIN IMMEDIATE` and batching small commits; this helps contention but cannot prevent a different process from holding the lock for ten seconds. No product-code change is justified solely by the present artificial holder; measure real lock owners and Windows probe duration in the reporter's environment before choosing an implementation.
