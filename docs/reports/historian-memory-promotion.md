# Historian fact promotion: volume, fate, and a gate

2026-09-29 · Investigation/proposal only; no product changes.

## Conclusion

The historian is a *direct writer* of cross-session memory, not a candidate producer. Its prompt asks for sparse, stable world knowledge, but a valid category bullet is promoted at the same transaction boundary as its compartment. There is no evidence threshold, semantic similarity check, numerical quota, or cooling period. In this snapshot, 736 successful historian runs emitted 3,097 fact bullets in 14 days (2.46 per compartment); 2,955 new historian memory rows appeared in the same window, about 211/day across projects. Exact-text/hash dedup and downstream curation do not prevent a first, slightly reworded or short-lived fact from entering the live pool. The two counts are **not** a reconciled ledger: run telemetry and memory rows differ in timing, gating, legacy identity, and dedup.

## Method and boundaries

The only live-store access was a backup attempt with `sqlite3 ~/.local/share/cortexkit/magic-context/context.db ".backup <task-root>/context-copy.db"`. That CLI backup timed out at 30 minutes while the busy source kept changing. I completed the *same destination copy* with Python's SQLite backup API from a `mode=ro` connection, using `pages=-1`; `PRAGMA integrity_check` on the finished 6.9-GiB copy returned `ok`. All subsequent SQL and vector calculations used `file:context-copy.db?mode=ro` (no `opencode.db`). The analysis cutoff was `max(memories.created_at) - 14*86400000` in this copy; its most recent historian row was 2026-09-29 10:56:24 UTC. Counts are a point-in-time observational cohort, not a controlled model comparison. `project_path` below is a git identity prefix, not a repository pathname; legacy pathname identities and missing run telemetry are kept distinct, not silently merged.

An operator's read-only live-store count on 2026-09-29 reported 94 new memories for one project in 24 hours, 92 from one historian session. The backup independently contains **92** historian insertions for that project in its last-24h window. Other copied projects have 89, 80, 44, 37, 33, 32, 18 historian insertions in that window; these are not their total memory gains. The supplied 14-day comparison was 2,955 historian, 444 agent, 163 dreamer; this slightly later copy contains 2,955, **445**, 163 respectively.

## Promotion path and actual gates

1. The TS source prompt defines facts as cross-compartment durable world knowledge, not events (`packages/plugin/src/hooks/magic-context/historian-prompt.source.md:23-46,391-410`). It says to skip semantically overlapping visible `<project_memory>` and emit a changed value instead (`:58-60,399-410`). Its five category tests explicitly reject feature/pipeline descriptions, snapshots, inventories, and transient measurements (`:412-416,438-461,488-528,530-575`). It specifies no per-run fact count. The Rust **system** prompt is the vendored TS prompt, not an independently tuned gate (`crates/mc-module/src/historian_prompt.rs:91-96`); Rust's prompt input includes the same project-memory category priority (`:20-36`). Visible project memory is a budgeted subset, so prompt-only dedup cannot see the whole store.
2. TS parses `*` bullets only under recognized category tags in `<facts>` (with a legacy fallback outside compartments/events), drops unknown categories, and carries `{category, content}` without a source-compartment anchor (`packages/plugin/src/hooks/magic-context/compartment-parser.ts:91-113,227-260`). Rust also parses known categories and optional `[at_compartment=N]` anchors (`crates/mc-module/src/historian_validate.rs:360-409`). On discarded lookahead or forced weak final boundary Rust discards promotion side channels (`:603-619`); TS skips unanchored facts for those boundaries (`packages/plugin/src/hooks/magic-context/compartment-runner-incremental.ts:874-888`). These are boundary-validity gates, **not** quality gates.
3. TS requires a project directory, `memory.enabled`, and `memory.auto_promote` (both default-on absent explicit false) before in-transaction promotion (`packages/plugin/src/hooks/magic-context/compartment-runner-incremental.ts:890-907,1023-1039`); Pi calls the same promoter (`packages/pi-plugin/src/pi-historian-runner.ts:1409`). `promoteSessionFactsDurable` rejects empty/invalid facts and non-promotable categories, looks up `(project_path, category, normalized_hash)`, bumps `seen_count` on an existing row, or inserts a `source_type='historian'` row (`packages/plugin/src/features/magic-context/memory/promotion.ts:49-93`; `storage-memory.ts:628-653,681-692,971-975`). Embeddings are best-effort **after commit**, not a pre-insert filter (`promotion.ts:96-143`). New TS writes accept the five v2 categories; the promotion helper also accepts legacy categories (`memory/constants.ts:4-29`). The uniqueness constraint covers `(project_path,category,normalized_hash)` regardless of status (`storage-db.ts:1177-1208`): same-hash restatement cannot create another row, but other wording/category can, and an archived row can receive another seen increment rather than be revived. There is no publish-time supersession.
4. Rust sets `promote_facts = memory_enabled && auto_promote`, projects validated facts into the publish request, and publishes them with compartments (`crates/mc-module/src/historian.rs:316-327,931-940,986-1005,3157`; `crates/mc-store/src/lib.rs:14002-14010`). **Do not equate Rust's internal dedup with TS's hash behavior:** `promote_facts_tx` loads active/permanent content in the project, skips *byte-identical* content (even across categories), then inserts with a synthetic `historian-exact:<content-hash>:<nonce>` hash; repeated historian content does **not** bump `seen_count` there (`crates/mc-store/src/lib.rs:18683-18747`). The host single-store writer, where active, checks live exact `content`, increments `seen_count` on repeats, and computes the normalized hash for inserts (`crates/mc-module/src/host_store.rs:1094-1165`). This is a parity distinction to resolve before implementing a shared gate, not evidence of semantic dedup. Neither writer compares embeddings, ages, or a per-day/per-compartment counter at historian publish. Current Rust/TS gates therefore differ in exact-repeat accounting; neither enforces the durable-fact contract.
5. Supersession is later maintenance, not historian admission. Verify can update/archive based on current source; its changes queue m[1] mutations (`packages/plugin/src/features/magic-context/dreamer/verify.ts:60-70,480-485,678-698`). Curate merges near-identical same-category entries and archives redundant ones **only** with a surviving same-category `superseded_by` (`packages/plugin/src/features/magic-context/dreamer/task-prompts.ts:94-121`). Its prohibition on deleting standalone low-value facts means curating cannot reliably remove all low-value first promotions.

There are 25 distinct project identity keys in the row cohort, including the legacy pathname key (24 git keys). The remaining 17 keys contribute 881 rows. A 0 in run telemetry must not be read as zero underlying compartments. Facts have no reliable foreign key to a specific compartment in the TS publication; **facts-per-compartment here is a ratio of aggregate run totals**, not a distribution of fact counts attached to individual compartments. In the leading matched project (`93ee…`), 675 emitted facts / 232 compartments = 2.91; `47b…` = 301/107 = 2.81; `f78…` = 241/189 = 1.28. The 92-per-day session may have many chunks and compartments, not one 92-fact output.

**Near duplicates:** Of 2,955 newly created historian rows, 2,949 have an embedding in the copy. For each, I compared its float32 vector against *earlier-created, currently active/permanent* memories in the same project and **same embedding model ID**, cosine >= 0.90; ties at equal millisecond are ordered by row ID. All 2,949 had a comparable prior active vector. **52/2,949 = 1.76%** match at least one older active row, **33/2,949 = 1.12%** in the same category. Examples: #19135 -> #19131 (.966), #20130 -> #18992 (.983), #20359 -> #20103 (.902). This is a conservative *present-active retrospective proxy*: a row archived since the newcomer was created is absent, different embedding models are incomparable, and 0.90 misses conceptual duplicates with changed terms. It is **not** an at-publication historical-active snapshot. The unique hash constraint makes an exact `(project,category,hash)` collision among *two inserted rows* impossible: 0/2,955 such earlier-row collisions by construction. Only 1/2,955 recent historian rows currently has `seen_count>1`; exact repeat events not represented by new rows cannot be inferred from these insertions.

**Later fate:** 153/2,955 (5.18%) are archived at snapshot; 76/2,955 (2.57%) have `superseded_by_memory_id` (a subset of archived), leaving 77 archived without a named successor. `memory_mutation_log` contains a `superseded` entry for all 76 and an `archive` entry for 66 of the other 77; 11 have neither. Matching mutation time/project to a dream run interval +/-30s attributes 69 supersessions to `curate`, 21 plain archives to `verify`, 1 to `verify-broad` (the broader-scope verification task), and 3 plain archives to intervals with overlapping verify/curate or verify/verify-broad tasks. Seven supersessions and 41 plain archives have no matching verify/curate interval; do not ascribe those to either task (other operations, expiry, absent telemetry, or clock/identity mismatch). Using row `updated_at-created_at` as an **upper-bound proxy**, archived rows have median 58.1h, 56/153 within 24h and 136/153 within 7d; superseded rows median 24.3h, 38/76 within 24h and 68/76 within 7d. `updated_at` can be changed after archive; the first archive mutation timestamp gives a closer lag for the 142 rows with such a log. Recent rows are right-censored, so these are observed fates, not eventual failure rates.

**Retrieval and surfacing:** In the same 14-day *creation* cohort, historian 33/2,955 (1.12%) have `retrieval_count>0`, 41 total counted hits, 33 non-null `last_retrieved_at` (range Sep 16–29 UTC). Agent 29/445 (6.52%), 56 hits, 29 non-null dates; dreamer 66/163, 1,124 hits, but only 3 non-null dates (legacy/other-writer telemetry discrepancy). Historian 2,658/2,955 have a `memory_verifications` mapping row and 341 are marked `verified`; agent 413/445 mapped, 26 verified. A zero retrieval count **does not mean never surfaced**: the counter is incremented for explicit agent searches, not automatic hints/injection (`packages/plugin/src/features/magic-context/search.ts:2180-2203`), and under module authority the TS counter write is intentionally skipped. Exposure through m[0] (the rebuilt base prompt's project memory), m[1] (the in-session prompt delta), and the mural (a visual rendering of memories that do not fit the text budget) is not measured by this field. It cannot establish whether an agent read or used the memory.

## Manual quality sample

Seeded uniform sample of **150 IDs** without replacement from all 2,955 last-14-day historian insertions (`random.Random(20260929).sample(sorted_rows,150)`). One mutually exclusive label per row, with precedence: semantic same-project duplicate of an earlier active memory; clearly provisional/superseded design; volatile status/number; event/change restatement; otherwise standalone durable reusable rule/constraint. I read full sampled text only locally from the backup; quotations below are deliberately short. This is subjective single-reviewer coding, **not** a statistically validated precision estimate or a representative sample of the single 92-memory project.

| Label | n/150 | share | short illustrative quotes (memory IDs) |
|---|---:|---:|---|
| Durable reusable fact | 61 | 40.7% | #19518 “omits the Debug trait … password”; #20114 “streaming responses at 15 minutes” |
| Volatile number/status | 16 | 10.7% | #18668 “Active Claustrum custody accounts”; #19775 “abandonment threshold: 2 hours”; #18939 “plan path … #3155” |
| In-progress or version-specific design detail | 13 | 8.7% | #20484 “extensibility r5”; #20305 “extensibility architecture”; #20925 “priority service tier … default” |
| Restatement of implementation/change/event without independent long-lived rule | 58 | 38.7% | #18233 “release.sh automatically commits”; #17520 “connection discovery is hybrid”; #20522 “refuses replies” |
| Duplicate of existing same-project memory | 2 | 1.3% | #20359 overlaps #20103 on mid-session prefix mutations (cos .902); #19304 overlaps #17357 on issue-link wording (cos .902) |

This rubric deliberately treats a narrowly descriptive implementation behavior as a restatement even when worded in present tense: the current code or its compartment already supplies the answer. Some borderline items could be defensibly durable (e.g. a security invariant); a second blind reviewer and adjudication are needed before using the proportions as a shipping threshold. The two duplicate examples are not proof that a 0.90 similarity threshold should auto-delete them: #20359 also adds provider comparisons and #19304 gives acceptable positive formats.

## Gate alternatives and costs

| Option | Benefit | Failure mode / fit |
|---|---|---|
| (a) Stricter historian prompt | Cheapest parity-friendly first defense; explicitly make **zero facts normal**, demand cross-session need and stable/settled evidence, route implementation steps and changed numbers to compartment narrative, check current project memory. | Existing prompt already says most of this (`historian-prompt.source.md:391-410,438-575`); model variance and budgeted `<project_memory>` mean prompt-only filtering will leak. Avoid a hard numeric instruction that trades away one-off security constraints. Rust vendored prompt must be regenerated together. |
| (b) Stage candidates for dreamer batch review | Best admission architecture: preserve all historian proposals without immediately spending prompt budget; review against full current active pool and source compartment(s), merge paraphrases, revise/supersede stale entries, decay undecided candidates. | Adds schema, scheduled model work, leases, provenance, retries/idempotence, parity and privacy review; promotion latency could hide a critical new rule unless a narrowly defined urgent path exists. Existing `user_memory_candidates` + `review-user-memories` reviews observations against stable user memories, requires recurring variants and consumes reviewed candidates (`user-memory/review-user-memories.ts:103-178`). Primer candidates instead embed/cluster/decay before promotion (`dreamer/promote-primers.ts:93-119,143-175`); neither may be blindly reused as a project-fact reviewer. |
| (c) Per-compartment/day cap | Predictable ceiling on downstream work and visual overflow-memory volume. | Arbitrary truncation preferentially loses later or lower-scored-but-critical facts; can shift bursts across compartments/projects, and a day cap needs durable cross-process accounting. Use an alert/overflow-to-candidates, not silent discard, if volume protection is needed. |
| (d) Similarity gating at publish | Catches paraphrases before downstream work; hash only catches normalization-equivalent repeats. | At >=.90 the observed retrospective lower bound is just 52/2,949; a raw vector match can collapse distinct values, negations, or a changed configuration. Embeddings are currently produced after commit and may be absent/mismatched across models. Use similarity to **retrieve review candidates**, never as sole destructive verdict; check category, contradiction and provenance. |
| (e) Two-compartment corroboration | Filters one-off task details and revised drafts, enables a simple evidence count. | Compartments from one session are highly correlated and repeat stale design; truly important one-off external constraints/user rules would be lost. Distinct sessions/time and independent evidence are stronger signals, with a justified high-confidence exception. |

The preferred design is **candidate-first, review-then-promote** (b), supplemented by a stricter prompt (a), semantic *retrieval* (d), and corroboration as evidence rather than a hard rule (e). Stage category, text, project, session, source compartment IDs/ordinals, created-at, a normalized key and decision/decay state transactionally with historian publication. Preserve original candidate text and provenance. The dreamer reviews bounded batches against the complete active same-project pool (not merely rendered `<project-memory>`), relevant category and near neighbors, source context, and newer candidates for the same design key; verdicts: promote one canonical durable fact, update/merge an existing fact, explicitly supersede a contradicted earlier fact, defer until settled, or reject/expire. Make the apply idempotent under a per-project lease, recheck current memory state inside the transaction, and record source IDs/verdict reasons. Contradiction is not semantic similarity. A high-confidence urgent path may promote a clear security rule immediately with explicit evidence, not an arbitrary numeric score. Give staged rows their own retention and budget; do not enqueue them for mapping, verification or prompt rendering until promotion. Roll out shadow verdict telemetry and compare held-out samples/false negatives before switching writer behavior.

**Cache and cost constraints.** Today a newly promoted memory is eligible for `<new-memories>` in m[1] on a materializing opportunity (TS `inject-compartments.ts:2853-2877`; Rust `m1_compose.rs:310-327,372-439`), then joins the `<project-memory>` pool in m[0] on the next rebuild. The in-session revision is deferred until an independent render; a watermark move alone must not bust a cache (`crates/mc-module/src/m1_compose.rs:124-143`). Candidate writes must **not** change memory IDs, mutation cursors, project-memory epochs or render fingerprints: no new bust, no candidate text in m[0]/m[1]. Promotion should use the existing memory insert/mutation and watermark paths at normal opportunities, not an eager external epoch. New live rows later trigger mapping (`dreamer/task-gates.ts:74-89`) and verify/curate cycles; 2,658 recent historian rows already have mapping rows. Avoid paying these costs on rejected candidates. Text injection has an 8,000-token default budget and m[1] new-memory additions are trimmed to 25% of it (`inject-compartments.ts:1081-1084,2864-2874`); the mural is the deterministic complement of text-budget-selected rows, not an infinite free memory store (`mural/mural-selection.ts:4-30`). More memories push good ones out of `<project-memory>` and require cue compression/storage and image attention even when text cost is capped. Scheduled curate's prompt cites ~6,000 tokens (`dreamer/task-prompts.ts:100-118`); distinguish that planning statement from the current 8,000-token code default.

**Rust parity and migration.** Implement the same candidate schema, validation, scheduling and render-neutral apply in TS/host and Rust module authority; align exact-repeat semantics (including `seen_count`, category and normalized-hash treatment) before comparing metrics. No migration is needed for the **first prompt-only step**. Candidate-first production does require a forward schema migration (plus module-store/single-store mirror or equivalent authority support), not written here. Do not retroactively stage or rewrite the 10,861 already stored historian rows; existing memory IDs and mutation history must remain stable. Backfill would be a separately consented cleanup exercise.

**Smallest first step:** revise the shared historian `<facts>` instructions with a small contrastive set of *reject* examples taken from the observed classes (ephemeral threshold/status, unlanded revision, commit/change recap, duplicate visible memory), state that zero facts is a valid and often correct output, and regenerate the vendored Rust prompt. Add a cross-mode golden test for prompt parity and an observational counter of emitted/inserted facts by project/model; replay a fixed held-out historian corpus before/after to measure retained critical rules and false omissions. This costs no schema change and keeps cache behavior unchanged, while preparing the evidence needed to justify staged promotion.
