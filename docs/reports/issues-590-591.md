# Issues 590 and 591: a history boundary the OpenCode 2 store lost, and `/ctx-recomp` on OpenCode 2

2026-09-30. Both reproduced on a real OpenCode **2.0.20** host (`@opencode/cli@2.0.20`, pointed at with `MC_E2E_OPENCODE2_CLI`) with the lane's mock provider, and both fixed. New host tests: `packages/e2e-tests/tests/opencode2/missing-history-boundary.test.ts` (three shapes) and `recomp-hidden-executor.test.ts`. All four are red on the base build (`5b9d387cfe`) and green on the fix.

## Issue 591: `/ctx-recomp` fails with MC-R01

### Call chain

1. `/ctx-recomp` on OpenCode 2 is a server command (`v2/hooks/commands.ts`, `ctx-recomp`), or the TUI's recomp dialog. Both dispatch the `recomp` RPC.
2. `plugin/rpc-handlers.ts` `recomp` handler builds a `ManagedRecompContext` whose `client` is `args.client`. OpenCode 2 registers the handlers with `client: undefined` (`v2/hooks/context.ts`, `registerRpcHandlers(... client: undefined ...)`), because the host gives a plugin no SDK client.
3. `runManagedRecomp` (`recomp-orchestrator.ts`) → `executeContextRecomp` (`compartment-runner.ts`) → `executeContextRecompInternal` (`compartment-runner-recomp.ts`).
4. `executeContextRecompInternal` called `await client.session.get(...)` to find the session directory. With `client` undefined that throws `undefined is not an object (evaluating 'client.session')`; the function's catch logs `recomp failed code=MC-R01 reason="…"` and returns the MC-R01 text. This is the log line in the issue.

Two more gaps sat behind the missing-client failure:

- Every historian pass in full and partial recomp called `runValidatedHistorianPass` without `hiddenCompletionExecutor`, so with no client `resolveHiddenCompletionExecutor` would have thrown `historian: v2 hidden completion executor is missing`. The incremental historian and wrapup already passed it.
- The RPC delivered the outcome with `sendIgnoredMessage(args.client, …)`, which needs the OpenCode 1 client to write its chat row.

### Fix

- `compartment-runner-recomp.ts` and `compartment-runner-partial-recomp.ts`: the session lookup is `client?.session.get(...)` (falls back to the plugin directory, as the incremental runner does), and every historian pass gets `hiddenCompletionExecutor: deps.hiddenCompletionExecutor`, which OpenCode 2 supplies through `buildRecompDeps`.
- `rpc-handlers.ts`: with no client, the outcome goes to the result dialog on the notification channel (the same carrier wrapup uses). With neither a client nor an executor the handler answers with a specific error ("History rebuild is unavailable: this host gave Magic Context no way to run the historian.") instead of a generic MC-R01.

### Proof

`recomp-hidden-executor.test.ts` on 2.0.20: six turns, then `session.command({ name: "ctx-recomp" })`. The mock historian answers each `Messages a-b:` chunk; compartments are published, the log has `recomp finished (published=true)` and no `MC-R01` or `client.session`, and the next turn's provider request carries the rebuilt compartment's text. On the base build the same test fails (no compartment within 60 s). Unit tests: `recomp-orchestrator-v2.test.ts` runs a full and a partial recomp with `client: undefined` and a hidden executor.

## Issue 590: the boundary no longer exists in the host store

### Reproduction

`missing-history-boundary.test.ts` builds the reported shape on a real host whose mock provider enforces a 60,000-token window (an over-window request gets HTTP 400 `prompt is too long`; the historian runs on a second mock model so its own prompt is not subject to that window):

1. 24 turns of about 5,000 tokens each, with two `/ctx-wrapup` runs, so the session has 11 compartments; `/ctx-flush` and a turn so the cached baseline sits on the newest compartment end.
2. `session.compact`: the host writes its own compaction checkpoint. Two more turns, another flush, and the baseline is asserted to equal the newest compartment's `end_message_id`.
3. The host is stopped and that message row is deleted from `session_message` in the throwaway store, which is what the conversion and `/undo` did to the reported session. The drops the plugin had recorded for the history rows are reactivated, because in the reported session none of the 2,966 tags were dropped (`fetched=0`), so the restored rows are served at full size.
4. The host restarts and the next turn is sent.

Base build: the turn's request was **137,548 tokens** against the 60,000 window and the mock answered 400. The plugin log had exactly the report's signature:

```
compartment injection entering degraded mode: boundary msg_… not in visible messages (consecutive degraded passes: 1)
prefix trim: boundary msg_… absent from current messages; pass=defer; no in-pass trim applied (degraded pass 1; boundary does not sort before the first live message msg_…; whole window served until a cache-busting pass moves the boundary into the window)
```

Fixed build: **25,648 tokens**, one rebuild pass, then ordinary replay.

### Why Magic Context's request was larger than the host's own

Yes: the host's compaction trims history, and Magic Context puts it back and then cannot cut it.

With a completed host compaction, the OpenCode 2 host's own request is the checkpoint summary plus the retained tail. That is why the session fits with Magic Context off. With Magic Context on, the context hook (`v2/hooks/context.ts`, the block after `reader.latestCompaction`) replaces the checkpoint with Magic Context's own summary (m[0]/m[1]) and restores, from the store, the rows between Magic Context's cached baseline boundary (`cached_m0_last_baseline_end_message_id`) and the host cut, because those rows are not in its summary yet. The restore starts at `servedBoundaryRow(boundary)`, then `sequenceForId(boundary)`, and when neither finds the row it falls back to `earliestSequence - 1`, the first row of the session. So a boundary the store no longer has makes the restore bring back **every** row the host compacted away. The transform's prefix trim then looks for the same id to cut through, cannot find it, classifies it as absent, and serves the whole restored window. In the report that is 2,389 messages (conversation 1.86M + tool output 1.22M estimated tokens). With `compaction: { enabled: false }` none of this runs: the adapter passes the host's own compacted messages through, which is the 3-message pass in the report.

### Why degraded mode never ended

- The trim boundary is recomputed from the compartments on every priced pass: soft refresh stores `getLastCompartmentEndMessageId`, materialization stores the newest compartment's end id. Both are the deleted id, so "a cache-busting pass moves the boundary into the window" can never happen: every pass moves it to the same missing row.
- The degraded counters are in memory. The report ran `opencode run --standalone`, one process per turn, so every pass was "degraded pass 1". The existing layer-B re-anchor in `prepareCompartmentInjection` waits for two consecutive in-process degraded rebuilds on a cache-busting pass, and it only splices the visible array; it does not change the OpenCode 2 restore or the m[0]/m[1] prefix-trim boundary, which are the two places that decide the served size here.
- Nothing ever reclaims: the restored rows carry no dropped tags, and `channel2` sees only the small reclaimable tail.

### Fix

**Re-anchor on proof** (`hooks/magic-context/history-boundary-repair.ts`, called from `checkHistoryBoundary` in `v2/hooks/context.ts` before anything restores or trims, TypeScript mode only, compaction on):

- The boundary is the newest compartment that has an end id. The hook asks the host store whether that row exists (`V2StoreReader.sequenceForId`). Only a definite "no such row", from a store that holds rows for this session, counts as proof. Absence from the request is never used: the host leaves rows out of a request for ordinary reasons. A store that cannot answer, or has no rows for the session, changes nothing, and a failed lookup never blocks the turn.
- Proven gone: find the newest older compartment whose end the store still has. Under the compartment-state lease (skipped while a historian, recomp or wrapup is running), remove every compartment after it, their chunk embeddings and the compression-depth rows past the anchor, queue an m[0] mutation, and clear the cached m[0]/m[1] pair. This is the covered-history revert rule: truncate from the first affected compartment and let the historian rebuild that range from the raw rows that remain. Older compartments whose rows are gone keep rendering: their summaries are the history and none of them is the boundary.
- The same pass is made a cache-busting materialization (`historyRefreshSessions` and `pendingMaterializationSessions`), and the restore starts at the anchor, which is exactly where every later pass restores from once the new baseline is stored. So there is one rebuild pass, and then ordinary replay. The host test asserts the next turn's head is byte-identical to the rebuild pass's and that the repair is logged once.
- A cached baseline that names a row the store no longer has, while the compartments are sound, only clears the cached pair (`baseline-reset`).
- A cached pair whose boundary is empty (it was recorded before the first compartment existed) is left alone. Replaying it and serving the rows it does not cover until the next priced pass is the designed behavior; `fold-s3-owner` restores exactly those rows, and an earlier draft of this fix that reset this shape broke that test.

**Never serve an uncut over-window request** (`transform.ts`, `messages-transform.ts`, `unresolved-history-boundary.ts`): when the prefix trim reports `refused` (the boundary was not found and nothing was cut), the transform estimates the final request (also on defer passes, which normally skip the estimate) and, if it exceeds the context limit, throws `UnresolvedHistoryBoundaryError`. The messages wrapper first tries the existing LKG replay (the last request this session served successfully, with the new tail appended); if there is none it refuses the turn instead of falling back to the raw input messages. On OpenCode 2 the refusal interrupts the turn before the provider request and puts the reason on the TUI notification channel: new user-facing code **MC-H04**, "This request was not sent: the message that marks where this session's history summary ends is missing from the OpenCode store, and without it the request is larger than the model's context window. Run /ctx-recomp to rebuild the history summary." An uncut request that fits is still served as before.

### The fork shape

"injecting legacy compartments without visible-prefix trimming because latest stored compartment has no end_message_id" is logged whenever the trim boundary is empty, which has two causes:

1. The newest compartment really has no `end_message_id` (a legacy row, or one carried into a forked session). Before this change the trim boundary, the soft-refresh baseline and the materialized baseline all took the newest compartment's id, found it empty, and stored no boundary, so on OpenCode 2 after a host compaction every compacted row was restored and served uncut. Now all three use the newest compartment that has an end id (`newestCompartmentEndId` in `inject-compartments.ts`, `getLastCompartmentEndMessageId` in `compartment-storage.ts`). Nothing is removed: the id-less compartment keeps rendering; everything up to the newest id is covered, and the rows after it stay raw. Having no id says nothing about the store, so it never triggers a removal on its own.
2. The cached pair was recorded before the first compartment (empty baseline). The repair leaves it alone (see the last bullet of the fix above); the next priced pass folds the compartments in and records the boundary.

The report does not say which of the two the fork hit. The host test covers the first (the newest compartment's end id cleared in the throwaway context store, then a priced and a replayed turn).

## Isolation

Every host ran under `TMPDIR=$TMPDIR/magic-context/issue-590/`, so each test's private root (`mc-opencode2-*`) and the host's extract cache sit there. The 2.0.20 CLI was installed with the lane's own `ensureSharedOpenCode2("2.0.20")` into `~/.local/share/cortexkit/e2e-bin/opencode-cli/2.0.20` (outside the live Magic Context directory). The new tests record `lsof -Fn -p <host pid>` into the root (`lsof-*.txt`) before and after the deletion and assert that nothing is open under `~/.local/share/opencode`, `~/.local/share/cortexkit/magic-context` or `~/.config`. A sample: 19 open paths, all under the throwaway root (its `opencode2.db`, `context.db`, log and extract cache), none forbidden. The lane's own write fence and open-file guard ran on every host as well.

## Limits

- Positions: the anchor keeps its stored `end_message` ordinal. If rows before the anchor were also deleted, that ordinal is higher than the store's, and the historian's next chunk starts after it. The existing coordinate repair and MC-H03 cover misaligned positions; `/ctx-recomp`, which now works on OpenCode 2, rebuilds them.
- The store-proven repair is wired into the OpenCode 2 hook only. OpenCode 1 keeps its existing re-anchor; the size guard and the MC-H04 refusal apply to both hosts.
- The repair drops compartments whose end is gone, and the historian rebuilds them only from raw rows that still exist; history whose rows the host deleted is not recoverable from the store.
